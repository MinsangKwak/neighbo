# 기술 노트 · 쓰기 전에 한 번 만들어 본다

[문서 목차](../README.md) · [00 개요](../00-overview.md) · [결정 기록](../decisions/README.md)

**이 프로젝트에서 쓰는 핵심 기술마다 노트 한 장을 둡니다.** "쓸 줄 안다"와 "안다"는 다릅니다. 라이브러리가 감추는 부분을 모른 채 쓰면 문제가 났을 때 어디를 봐야 하는지 모르고, 그러면 같은 1년을 열 번 반복하게 됩니다. 그래서 노트마다 **밑바닥 구현**이 한 번씩 들어가고, 코드 단계에서 겪은 문제는 **원인 노트**로 그 기술 아래에 쌓입니다.

## 노트가 답해야 하는 다섯 질문

| 절 | 질문 | 분량 기준 |
| --- | --- | --- |
| 1. 왜 필요한가 | 이 기술이 없으면 이 서비스에서 **무엇이** 안 되는가. 대체재는 무엇이고 왜 이것인가 | 한 문단. [결정 기록](../decisions/README.md) 링크 |
| 2. 어떻게 동작하는가 | 요청 하나가 이 기술을 지나는 동안 실제로 일어나는 일. 그림 하나 | 한 쪽 |
| 3. 밑바닥 구현 | 라이브러리 없이 **최소 동작**을 직접 만든 코드와 그 과정에서 알게 된 것. 그 다음 라이브러리가 대신해 주는 것의 목록 | 코드 50~150줄 + 비교표 |
| 4. 이 프로젝트에서 쓰는 방식 | 우리 코드 어디에 어떤 설정으로 있는가. 바꾸면 안 되는 것 | 표 |
| 5. 겪은 문제와 원인 | 증상 → 가설 → 확인 방법 → 원인 → 수정 → 재발 방지. 날짜 역순 | 생길 때마다 |

1~3은 **스파이크 단계**(00 개요 "문서가 끝난 뒤" 2번)에서 쓰고, 4는 구현하면서, 5는 운영하면서 씁니다.

## 스파이크 규칙

- 저장소 밖(`~/spikes/`) 또는 저장소의 `spikes/` 폴더에서 한다. **운영 코드와 섞지 않는다.**
- 하나에 반나절을 넘기지 않는다. 넘기면 "모르는 것"을 노트에 적고 넘어간다 — 그게 결과다.
- 결과는 코드가 아니라 **노트의 3절**이다. 코드는 핵심만 50~150줄 발췌.
- 스파이크 중 결정이 뒤집히면 [결정 기록](../decisions/README.md)에 새 번호로 올린다. 기존 기록은 "대체됨"으로.

## 원인 노트 형식 (5절)

```markdown
### YYYY-MM-DD · 한 줄 증상
- 증상: 무엇이 보였나 (에러 메시지 · 화면 · 재현 조건)
- 가설: 처음 의심한 것
- 확인: 어떻게 확인했나 (로그 · 쿼리 · 실험)
- 원인: 실제 원인 — 기술의 어떤 동작 때문인가
- 수정: 무엇을 바꿨나 (커밋 링크)
- 재발 방지: 테스트 · lint · 문서 중 무엇을 추가했나
```

"고쳤다"만 있고 "원인"이 비어 있으면 아직 안 끝난 것입니다.
