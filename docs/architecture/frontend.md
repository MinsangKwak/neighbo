# 프론트엔드 설계

[문서 목차](../README.md) · [흐름 설계](flow.md) · [프론트엔드 설계](frontend.md) · [백엔드 설계](backend.md) · 기능별 요구사항: [features/](../features/00-common.md)

## 01 · 렌더링 전략

**초기 화면은 서버에서 렌더링하고, 이후 조회·변경은 클라이언트 캐시와 연결하도록 설계했습니다.** 사용자별 정보가 포함된 응답은 공유 캐시에 저장하지 않습니다. 페이지별 데이터 조회 범위, 인증 조건, 클라이언트 상호작용은 아래 표에서 구분합니다.

### 설계 판단

#### 1. 사용자별 데이터를 서버에서 그릴 때의 캐시 사고

Next.js 서버 컴포넌트의 `fetch`는 설정에 따라 결과를 서버에 저장해 다음 요청에 재사용할 수 있다. 상세 페이지 응답에는 `viewer.isSeller`가 들어 있는데, 이게 저장되면 **판매자 본인이 본 화면(수정 · 삭제 메뉴)이 다른 사람에게 보인다.**

| 규칙 | 방법 |
| --- | --- |
| 백엔드 호출은 전부 `cache: 'no-store'` | 서버용 API 함수 `serverFetch()` 한 곳에서 강제 — 개별 호출이 잊을 수 없게 |
| 쿠키를 백엔드로 전달 | `serverFetch()`가 `cookies()`를 읽어 `Cookie` 헤더로 |
| 백엔드가 준 `Set-Cookie`는 **버린다** | 서버 컴포넌트는 렌더 중에 쿠키를 쓸 수 없다. 쿠키 연장 · 삭제는 브라우저가 부르는 `/api/*` 프록시 응답에서만 일어나고, 로그인 상태의 화면은 모두 배지용 `/api/me/unread`를 부르므로 연장이 빠지지 않는다 [AC-CM-03] |
| 인증 화면 응답 헤더 | `Cache-Control: no-store` (로그아웃 후 뒤로가기로 보호 화면이 보이지 않게 [AC-LI-13]) |

이 사고를 일부러 재현해 보는 것이 [기술 노트](../tech-notes.md) `nextjs-app-router.md`의 스파이크 ②다.

#### 2. 서버 데이터를 클라이언트 캐시로 넘기기

서버에서 가져온 첫 페이지를 클라이언트가 다시 요청하면 낭비고, 그렇다고 서버 데이터를 props로만 내리면 [더 보기] · 뒤로가기 복원 · 소켓 갱신이 그 데이터와 따로 논다. 그래서:

```
서버 컴포넌트: queryClient.prefetchInfiniteQuery(['products', filters])
             → dehydrate(queryClient)
클라이언트:   <HydrationBoundary state={...}> → useInfiniteQuery(['products', filters])  // 같은 키, 요청 없음
```

서버와 클라이언트가 **같은 캐시 키**를 쓴다. 키 목록은 [03 캐시](#03--캐시와-낙관적-갱신).

#### 3. 보호 페이지 — 두 겹의 확인

| 겹 | 어디서 | 확인하는 것 | 못 하는 것 |
| --- | --- | --- | --- |
| 1 | `proxy.ts` (Next.js 16에서 `middleware.ts`가 이름을 바꾼 것, Node 런타임) | 세션 쿠키가 **있는가** — 없으면 즉시 `/login?next=` | 토큰이 유효한지 (DB의 `tokenVersion`을 모른다) |
| 2 | 페이지 서버 컴포넌트 | `serverFetch('/me')` → `401`이면 `redirect('/login?next=')` | — |

1겹만 있으면 만료 · 무효 토큰이 통과하고, 2겹만 있으면 비로그인 사용자도 페이지 렌더를 시작했다가 돌아간다. 1겹은 빠른 길, 2겹이 진짜 판단 [AC-CM-01]. 로그인 · 가입 화면은 반대로 쿠키가 있으면 홈으로 [AC-CM-05].

#### 4. 채팅방 첫 화면과 소켓의 연결

서버가 준 최신 50개의 마지막 메시지 `seq`를 소켓 `room:join`의 `after`로 넘긴다. 서버 렌더와 소켓 조인 사이(수백 ms)에 온 메시지가 빠지지 않는다. 서버 렌더가 없으면 "빈 화면 → HTTP 로드 → 조인" 순서가 되어 깜빡임과 같은 틈이 생긴다.

## 02 · 상태 소유권

**상태는 서버·URL·폼·UI·연결의 다섯 종류로 나누고, 값마다 저장 위치와 갱신 주체를 하나로 정했습니다.** 서버 데이터는 TanStack Query, 공유 가능한 선택값은 URL, 입력과 일시적인 화면 상태는 컴포넌트에서 관리합니다. 별도의 전역 상태 라이브러리는 도입하지 않습니다.

### 다섯 종류와 담는 곳

| 종류 | 무엇 | 담는 곳 | 진실은 어디 | 예 |
| --- | --- | --- | --- | --- |
| 서버 상태 | 서버에 있는 데이터의 사본 | TanStack Query 캐시 | 백엔드 DB | 상품 · 목록 · 채팅방 · 메시지 · 배지 수 · 내 정보 |
| URL 상태 | 공유 · 새로고침 · 뒤로가기에 살아남아야 하는 선택 | 경로 · 쿼리스트링 | URL | `q` · `hideSold` · 마이 탭 `status` · 채팅 목록 `productId` · `next` |
| 폼 상태 | 제출 전 입력값 · 오류 · 건드림 여부 | 폼 컴포넌트 로컬 (`useForm` 훅) | 그 폼 | 등록 폼 값 · 업로드 진행 · `idempotencyKey` |
| UI 상태 | 지금 화면에만 의미 있는 것 | 컴포넌트 로컬, 여러 곳이 쓰면 컨텍스트 | 그 화면 | 모달 열림 · 캐러셀 위치 · 토스트 대기열 |
| 연결 상태 | 소켓 연결과 전송 대기열 | 소켓 컨텍스트 (탭당 하나) | 그 탭 | `connected` · `reconnecting` · 방별 대기 메시지 |

### 상태 경계와 처리 기준

#### 1. 로그인 사용자는 서버 상태다

"로그인한 사용자"를 전역 스토어에 넣고 로그인 · 로그아웃 때 바꾸는 방식은 쿠키와 스토어가 어긋날 수 있다(쿠키 만료, 다른 탭 로그아웃). 그래서 사용자 정보는 `['me']` 쿼리의 데이터이고, 진실은 쿠키 + 백엔드다.

| 순간 | 처리 |
| --- | --- |
| 첫 렌더 | 루트 레이아웃(서버)이 `/me` 조회 → `['me']`로 하이드레이트. 깜빡임 없음 [AC-LI-03] |
| 로그인 · 가입 성공 | `queryClient.clear()` → `router.replace(next)` → `router.refresh()` |
| 로그아웃 | 소켓 끊기 → `queryClient.clear()` → 홈 [AC-LI-13] |
| 다른 탭이 로그아웃 · 다른 계정으로 로그인 | `storage` 이벤트(`neighbo:session` 키에 사용자 id)로 감지 → 로그인 화면 또는 "다른 계정으로 로그인됐어요" [AC-LI-14, 15] |
| 아무 요청에서 `401` | 전역 처리로 로그인 화면 ([04 에러 경계](#04--에러-경계)) |

#### 2. 필터는 URL에, 컴포넌트 상태에 두지 않는다

`hideSold` 토글을 `useState`에 두면 새로고침 · 공유 · 뒤로가기에서 사라진다. URL에 두면 서버 렌더도 같은 필터로 첫 페이지를 그릴 수 있다 [AC-PL-12, 13, AC-MP-02]. 쿼리 키에 URL 값을 그대로 넣어(`['products', { q, hideSold }]`) **URL이 바뀌면 캐시 항목도 바뀐다.**

URL에 두지 **않는** 것: 캐러셀 위치, 모달 열림, 스크롤 위치(브라우저 · 캐시가 복원). 공유할 이유가 없고 히스토리를 어지럽힌다.

#### 3. 서버 상태를 로컬로 복사하지 않는다

흔한 실수: `const [title, setTitle] = useState(product.title)`. 이후 상품이 바뀌어도 로컬 값은 옛것이다. 서버 데이터는 쿼리에서 바로 읽고, **편집이 시작되는 폼만** 초기값으로 한 번 복사한다(수정 폼). 그 복사본의 주인은 폼이고, 저장이 끝나면 버린다.

#### 4. 메시지 목록은 서버 상태 + 연결 상태의 합

화면에 보이는 메시지 = `['messages', roomId]` 캐시(서버에서 확정된 것) + 소켓 컨텍스트의 대기열(아직 확정 안 된 것 — 전송 중 · 연결 중 · 실패). 둘을 한 배열에 섞어 저장하지 않고 **그릴 때 합친다.** 확정되면 대기열에서 빼고 캐시에 넣는다. 섞어 저장하면 재조회가 대기 메시지를 지우거나, 실패 메시지가 서버 데이터인 척한다.

```
표시 = [...캐시 메시지(seq 순), ...대기열(만든 순)]
ack 성공  → 대기열에서 tempId 제거 → 캐시에 message 추가 (같은 id가 이미 있으면 무시)
```

#### 5. 폼 상태 — 라이브러리 없이 훅 하나

폼은 7개(가입 · 로그인 · 등록 · 수정 · 프로필 · 비밀번호 · 채팅 입력)이고 필요한 것은 같다: 값 · 오류 · 건드림 여부 · 칸을 떠날 때 정규화와 검증 · 서버 `fields` 반영 · 첫 오류 포커스. 공유 Zod 스키마가 검증을 맡으므로 남는 것은 상태 관리 80줄 정도라 `useForm` 훅 하나로 쓴다. 폼 라이브러리를 들이면 그 라이브러리의 등록 방식 · 리렌더 규칙을 함께 배워야 하는데, 얻는 것이 이 80줄이다 [개요 의존성 규칙]. 상세는 [05 폼](#05--폼).

#### 6. 컨텍스트는 셋뿐

| 컨텍스트 | 담는 것 | 왜 전역인가 |
| --- | --- | --- |
| `ToastContext` | 토스트 대기열 (최대 3) | 어느 화면에서든 띄움 [AC-NT-06] |
| `SocketContext` | 소켓 인스턴스 · 연결 상태 · 방별 대기열 | 탭당 연결 하나를 여러 화면이 공유 ([07 소켓 클라이언트](#07--소켓-클라이언트)) |
| `AnnouncerContext` | 시각 숨김 라이브 리전에 문장 넣기 | 화면 어디서든 스크린리더 알림 ([06 포커스](#06--포커스와-라이브-리전)) |

로그인 사용자 · 배지 수는 컨텍스트가 아니라 쿼리다(1번).

## 03 · 캐시와 낙관적 갱신

**쓰기 작업과 소켓 이벤트별로 갱신해야 할 캐시를 미리 정의했습니다.** 상품이나 메시지가 변경된 뒤 관련 화면에 이전 값이 남지 않도록 키와 무효화 범위를 함께 관리합니다. 이 표는 [변경 영향 매트릭스](../overview.md#24-변경-영향-매트릭스)를 프론트엔드 캐시에 적용한 설계입니다.

### 1. 캐시 키

키는 `queryKeys.ts` 한 파일에서만 만든다. 문자열을 직접 쓰면 오타 하나로 무효화가 조용히 실패한다.

| 키 | 데이터 | 종류 | `staleTime` | 서버 렌더 하이드레이트 |
| --- | --- | --- | --- | --- |
| `['me']` | 내 정보 + 개수 | 단건 | 5분 | 루트 레이아웃 |
| `['me', 'unread']` | 읽지 않은 방 수 | 단건 | ∞ (소켓이 갱신) | 탭 레이아웃 |
| `['me', 'products', status]` | 판매 탭 목록 | 무한 | 30초 | 마이 |
| `['me', 'purchases']` | 구매 내역 | 무한 | 30초 | 마이 |
| `['products', { q, hideSold }]` | 홈 · 검색 목록 | 무한 | 30초 | 홈 · 검색 |
| `['product', id]` | 상세 | 단건 | 30초 | 상세 · 수정 |
| `['product', id, 'chatPartners']` | 거래완료 바텀시트 목록 | 단건 | 0 (열 때마다) | — |
| `['chatRooms', { productId }]` | 채팅 목록 | 무한 | ∞ (소켓이 갱신) | 채팅 목록 |
| `['chatRoom', id]` | 방 · 상품 요약 · 상대 `lastReadSeq` | 단건 | ∞ (소켓이 갱신) | 채팅방 |
| `['messages', roomId]` | 메시지 (과거 방향 무한) | 무한 | ∞ (소켓이 갱신) | 채팅방 |

`staleTime ∞`인 키는 소켓 이벤트로만 갱신되므로, **소켓이 끊겼다 붙으면 반드시 재조회**한다 ([07 소켓 클라이언트](#07--소켓-클라이언트)). 이걸 빼먹으면 끊긴 동안의 변화가 영영 반영되지 않는다.

### 2. 캐시 갱신 범위

✏️ 응답으로 직접 갱신 · ♻️ 무효화(다시 가져옴) · ✂️ 캐시에서 제거

| 쓰기 | `product` | `products` | `me` | `me/products` | `me/purchases` | `chatRooms` | `chatRoom` | `messages` | `me/unread` |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 상품 등록 | ✏️ 새 상품 | ♻️ | ♻️ 개수 | ♻️ 판매중 | | | | | |
| 상품 수정 | ✏️ | ♻️ | | ♻️ 해당 탭 | | ♻️ (요약 가격 · 제목) | ♻️ 이 상품 방들 | | |
| 상태 변경 | ✏️ | ♻️ | ♻️ 개수 | ♻️ 전 탭 | | ♻️ (썸네일 배지) | ♻️ | | |
| 상품 삭제 | ✂️ | ✂️ 해당 항목 | ♻️ 개수 | ♻️ | | ♻️ ("삭제됨") | ♻️ | | |
| 채팅방 만들기 | ♻️ (`existingChatRoomId`) | | | | | ♻️ | ✏️ | | |
| 메시지 전송 (ack) | | | | | | ✏️ 행 맨 위로 | ✏️ 마지막 메시지 | ✏️ 추가 | |
| 읽음 | | | | | | ✏️ 행 배지 0 | | | ✏️ 낙관적 −1 |
| 닉네임 · 아바타 변경 | | | ✏️ | | | | | | |
| 로그인 · 로그아웃 | 전체 `queryClient.clear()` | | | | | | | | |

다른 사용자의 화면(예: 내가 거래완료로 바꿨을 때 구매자의 구매 내역)은 프론트가 고칠 수 없다. 그쪽은 다음 조회 · 포커스 복귀 · 소켓 이벤트가 맞춘다 [CM-CC-02].

#### 소켓 이벤트 → 캐시

| 이벤트 | 갱신 |
| --- | --- |
| `message:new` | `messages` 추가(같은 `id` 있으면 무시) · `chatRooms` 행 맨 위로 + 미리보기 · 그 방을 보고 있지 않으면 행 배지 +1 |
| `room:read` (상대) | `chatRoom`의 상대 `lastReadSeq` → "읽음" 표시 |
| `room:read` (내 다른 탭) | `chatRooms` 행 배지 0 |
| `notification:unread` | `me/unread` = `total` |
| `room:product_updated` | `chatRoom`의 상품 요약 · `product` 무효화 · `chatRooms` 행 |
| 재연결 | `me/unread` · `chatRooms` · 열린 방의 `chatRoom` 무효화 + 방마다 `room:join { after }` |

`chatRooms` 재정렬은 100ms 디바운스로 묶는다 [AC-CL-05].

### 3. 낙관적 갱신 — 쓰는 곳과 안 쓰는 곳

**세 조건을 모두 만족할 때만 낙관적으로 갱신합니다.** ① 서버가 거절할 일이 드물다 ② 거절됐을 때 되돌림이 눈에 보이고 이해된다 ③ 다음 단계에 서버가 만든 값(새 id 등)이 필요 없다.

| 작업 | 낙관적? | 이유 | 실패하면 |
| --- | --- | --- | --- |
| 메시지 전송 | ✅ | 즉시 보여야 대화가 된다. `tempId`로 그리고 ack로 확정 | 말풍선을 지우지 않고 "전송 실패 [재시도] [삭제]" — 쓴 글을 잃지 않게 [AC-CH-04] |
| 방 입장 시 배지 −1 | ✅ | 서버가 거절할 일이 거의 없음 | 재조회로 복구 [AC-NT-07] |
| 상태 `<select>` | ✅ | 선택한 값이 바로 보여야 함 | 이전 값으로 되돌리고 토스트 [AC-PD-08] |
| 상품 등록 · 수정 | ❌ | 성공해야 상세로 이동, 새 id 필요, 실패 시 폼을 유지해야 함 | 폼 유지 + 오류 |
| 상품 삭제 | ❌ | 되돌림이 이해하기 어려움 (사라졌다 다시 나타남) | 모달 유지 + 토스트 |
| 채팅방 만들기 | ❌ | 방 id가 있어야 이동 | 버튼 복구 + 토스트 |
| 닉네임 변경 | ❌ | 중복으로 거절될 수 있음 | 칸 오류 |
| 거래완료 + 구매자 지정 | ❌ | 구매자 검증에서 거절될 수 있고, 되돌림 시 바텀시트 상태가 꼬임 | 바텀시트 유지 + 오류 |

### 4. 재시도 정책

| 종류 | 자동 재시도 | 이유 |
| --- | --- | --- |
| 조회 | 네트워크 오류 · 5xx에 1번 (1초 뒤) | 순간 끊김은 한 번이면 대부분 회복 |
| 조회 4xx | 안 함 | 다시 해도 같다 |
| 쓰기 | 안 함 — 사용자가 누른다 | 서버에 닿았는지 모름 [AC-CM-22]. 재시도가 안전한 쓰기는 백엔드가 멱등키로 보장 ([백엔드 05](backend.md#05--멱등성)) |
| 포커스 복귀 | `refetchOnWindowFocus` — `staleTime`이 지난 것만 | 다른 탭 · 다른 기기의 변화 반영 |

## 04 · 에러 경계

**오류는 영향 범위에 따라 앱·페이지·영역 단위로 처리하도록 설계했습니다.** 목록 추가나 메시지 전송처럼 일부 작업이 실패하면 해당 영역에 재시도 방법을 표시하고, 나머지 화면과 입력은 유지합니다.

### 1. 세 겹

| 겹 | Next.js 파일 · 위치 | 받는 것 | 보이는 것 | 남는 것 |
| --- | --- | --- | --- | --- |
| 앱 | `app/global-error.tsx` | 루트 레이아웃 자체의 렌더 실패 | 최소 화면 "일시적인 문제가 생겼어요" + [새로고침] | 없음 (레이아웃까지 실패) |
| 페이지 | 경로마다 `error.tsx` · `not-found.tsx` | 페이지 서버 렌더 실패 · `notFound()` | 본문 자리에 에러 · 404 | 헤더 · 탭바 [AC-CM-21, 23] |
| 영역 | 컴포넌트 안 (쿼리 · 뮤테이션 결과) | [더 보기] 실패 · 이미지 실패 · 전송 실패 · 폼 제출 실패 | 그 자리에 문구 + [다시 시도] | 화면 나머지 전부 [AC-PL-15, AC-CH-04] |

**판단 기준**: 이 데이터 없이 페이지가 의미가 있나? 상품 상세에서 상품이 없으면 페이지 에러(404), 사진 한 장이 없으면 영역(플레이스홀더), 채팅방에서 첫 메시지 로드가 실패하면 본문 영역(입력창 비활성) [CH-NW-01].

### 2. API 클라이언트 — 에러를 한 모양으로

모든 요청은 `apiFetch()`를 지난다. 서버 응답 · 네트워크 실패 · 타임아웃을 모두 `ApiError` 하나로 바꿔서, 화면 코드는 `error.code`만 보면 된다.

```ts
class ApiError extends Error {
  status: number;        // 0 = 네트워크 · 타임아웃
  code: ErrorCode | 'NETWORK' | 'TIMEOUT';
  fields?: Record<string, string>;
  requestId?: string;    // 응답 헤더 X-Request-Id
  retryAfter?: number;   // 429
}
```

| 상황 | 변환 |
| --- | --- |
| 서버 에러 응답 | 본문의 `error.code` · `fields` + 헤더의 요청 ID |
| `fetch`가 던짐 (오프라인 · DNS) | `code: 'NETWORK'` |
| 10초 초과 (`AbortController`) | `code: 'TIMEOUT'` [CM-NW-01] |
| JSON 파싱 실패 | `code: 'INTERNAL'` [CM-NW-07] |

### 3. 전역 처리 — 화면이 신경 쓰지 않아도 되는 것

TanStack Query의 전역 `onError`에서 처리하고, 화면은 자기 영역의 표시만 한다.

| 코드 | 전역 처리 | 예외 |
| --- | --- | --- |
| `UNAUTHORIZED` | 캐시 비우기 → `/login?next=현재경로` | 로그인 화면 자신 (무한 이동 방지) |
| `RATE_LIMITED` | 토스트 "잠시 후 다시 시도해 주세요", 그 버튼을 `retryAfter`초 비활성 | — [AC-CM-26] |
| `INTERNAL` · 5xx | 토스트 "일시적인 문제가 생겼어요 (문의 번호 a1b2c3)" | 페이지 렌더 실패면 페이지 겹이 받음 |
| `NETWORK` · `TIMEOUT` | 영역에 "불러오지 못했어요 [다시 시도]" | 쓰기면 토스트 "저장하지 못했어요. 다시 시도해 주세요" + 입력 유지 [AC-CM-22] |
| `FORBIDDEN` | 토스트 "권한이 없어요" → 이전 화면 | — [CM-NW-09] |

`INVALID_CREDENTIALS`는 401이지만 코드가 달라서 전역 401 처리를 타지 않는다 — 백엔드가 코드를 나눈 이유다 ([백엔드 06](backend.md#코드를-나누고-합친-판단)).

### 4. 화면이 직접 처리하는 코드

| 코드 | 어디서 | 반응 | 근거 |
| --- | --- | --- | --- |

### 5. 사용자가 보는 문장

| 규칙 | 이유 |
| --- | --- |
| 서버 `message`를 기본으로 쓰되, 화면 맥락에 더 맞는 문구가 있으면 프론트 문구 | 서버 문구는 맥락을 모른다 (같은 `NOT_FOUND`라도 상세에선 404 화면, 저장 중엔 "삭제된 물건이에요") |
| "무엇이 · 왜 · 무엇을 할 수 있나" — [다시 시도] · [홈으로] 같은 다음 행동을 함께 | 막다른 화면 금지 |
| 5xx에는 문의 번호(요청 ID 앞 6자) | 사용자가 말해 주면 로그 한 줄로 찾는다 ([백엔드 08](backend.md#08--관찰-가능성)) |
| 에러 토스트는 `role="alert"`, 페이지 에러는 `h1`으로 포커스 | [06 포커스](#06--포커스와-라이브-리전) |

### 6. 배포 직후의 청크 오류

배포로 파일 이름이 바뀌면 열려 있던 탭이 옛 청크를 요청해 404가 난다 [CM-NW-12]. 전역 에러 경계에서 `ChunkLoadError`를 알아보고 "새 버전이 있어요 [새로고침]"을 보여준다. 폼 작성 중이면 자동 새로고침하지 않는다 — 사용자가 쓴 내용을 잃게 된다.

## 05 · 폼

### 2. 한 칸의 생애

```
입력 중 ──────────▶ 칸을 떠남(blur) ─────────────▶ 오류 있던 칸에 다시 입력 ─▶ 제출
 막지 않음            ① 정규화 → 칸 값 교체          입력마다 재검증              전체 정규화 · 검증
 (길이 카운터만)      ② 스키마 검증 → 오류 표시      (고치는 즉시 오류가 사라짐)   → 첫 오류 포커스
                     ③ (이메일 · 닉네임) 중복 확인                               → 서버 → fields 반영
```

| 단계 | 규칙 | 왜 | 근거 |
| --- | --- | --- | --- |
| 입력 중 | 글자를 지우거나 막지 않는다. 한글 조합 중(`isComposing`)엔 아무 판단도 안 한다 | 말없이 사라지는 글자는 스크린리더 사용자가 이유를 모르고, 조합 중 개입은 한글을 깨뜨린다 | AC-CM-61 |
| 칸을 떠날 때 ① | `normalizeEmail` 등 공유 함수로 고친 값을 **칸에 다시 넣는다** | 무엇이 바뀌었는지 사용자가 볼 수 있게 | AC-CM-62 |
| 칸을 떠날 때 ② | 공유 Zod 스키마의 그 칸 규칙 | 입력 도중 "8자 이상" 오류가 뜨는 건 방해 | AC-SU-03 |
| 다시 입력 | 오류가 있던 칸만 입력마다 재검증 | 고친 순간 오류가 사라져야 함 | AC-SU-03 |
| 제출 | 버튼은 항상 활성. 누르면 전체 검증 → 첫 오류로 포커스 + 상단 요약 | 비활성 버튼은 "왜 안 눌리는지" 알 수 없다 | AC-SU-04, 17 |
| 서버 응답 | `fields`를 그대로 칸에. 프론트 판단과 달라도 서버를 따른다 | 서버가 최종 | AC-SU-18 |
| 실패 | 입력값 유지 (로그인 비밀번호만 예외) | 다시 쓰게 하지 않는다 | AC-CM-22 |

### 3. `useForm` 훅

[02 상태 소유권 5절](#02--상태-소유권)에서 라이브러리 대신 훅 하나로 정했다. 훅이 맡는 것:

```ts
const form = useForm({
  schema: signupSchema,            // 공유 Zod
  normalize: { email: normalizeEmail, nickname: normalizeText },
  onSubmit: (values) => api.signup(values),
});
// form.field('email') → { value, onChange, onBlur, error, describedBy, invalid }
```

| 기능 | 구현 |
| --- | --- |
| 값 · 오류 · 건드림 | 칸별 상태 하나 |
| 칸 단위 검증 | `schema.shape[name].safeParse` (교차 검증 — 비밀번호 확인 — 은 `superRefine`을 칸 오류로 매핑) |
| 제출 | 정규화 → `safeParse` 전체 → 오류면 첫 칸 `focus()` → 아니면 `onSubmit` → `ApiError.fields` 반영 |
| 제출 중 | `submitting` — 버튼 비활성 + 스피너, 두 번 제출 방지 | 
| 변경 감지 | 초기값과 깊은 비교 → 이탈 확인 판단 (수정 폼 · 프로필) |

### 4. 칸 컴포넌트 — 접근성이 기본값

`<Field>` 하나가 레이블 · 입력 · 규칙 안내 · 오류 · 카운터를 묶는다. 매번 손으로 `aria-*`를 잇지 않게.

```html
<label for="email">이메일</label>
<input id="email" type="email" inputmode="email" autocapitalize="off" autocorrect="off"
       spellcheck="false" autocomplete="email" maxlength="254"
       aria-invalid="true" aria-describedby="email-hint email-error" required>
<p id="email-hint">로그인할 때 쓰는 주소예요</p>
<p id="email-error">이메일 형식이 아니에요</p>
```

| 규칙 | 근거 |
| --- | --- |
| 규칙 안내(`hint`)는 오류 전부터 보이고 `aria-describedby`에 항상 포함 | AC-SU-12, AC-CM-44 |
| 칸 종류마다 입력 속성 묶음을 미리 정의 (`email` · `newPassword` · `currentPassword` · `nickname` · `price` · `text`) | AC-CM-60, 65, AC-SU-06a, AC-LI-05c |
| grapheme 길이는 `maxlength`로 못 센다 → 카운터 + 검증. 붙여넣기 초과분은 잘라내고 알림 | AC-SU-13, AC-CM-64 |
| 비밀번호 보기 토글은 `<button aria-pressed>` | AC-SU-11 |

### 5. 이탈 확인

작성 중 나가면 내용이 사라진다 [AC-PC-04]. 그런데 **App Router에는 이동을 막는 공식 API가 없다** (Pages Router의 `routeChangeStart` 같은 것이 없음). 그래서 경로를 셋으로 나눠 막는다:

| 나가는 경로 | 막는 방법 |
| --- | --- |
| 탭 닫기 · 새로고침 · 주소창 | `beforeunload` (브라우저 기본 확인창) |
| 앱 안의 링크 클릭 | 내부 링크 컴포넌트가 "이탈 가드가 켜져 있으면" 이동 전에 확인 모달 |
| 뒤로가기 | 가드가 켜질 때 `history.pushState`로 한 칸 쌓고, `popstate`에서 확인 모달 → 취소면 다시 쌓음 |

**뒤로가기 가드는 구현하며 확인할 것**: App Router도 `history.pushState`에 자기 상태를 싣는다. 가드가 이력을 한 칸 더 추가하면 그 칸에는 라우터 상태가 없어, 확인 모달에서 [나가기]를 눌렀을 때 `history.go(-2)`가 맞는지 · 라우터가 그 칸을 만났을 때 다시 렌더하지 않는지가 브라우저마다 다를 수 있다. 구현 첫 단계에서 크롬 · 사파리(iOS 스와이프 뒤로가기 포함)로 확인하고, 깨지면 뒤로가기만 "모달 대신 임시 저장 후 이동"으로 낮춘다.

가드는 `useLeaveGuard(dirty)` 하나로 켜고 끈다. 제출 성공 직후엔 끄고 이동한다. 이 부분은 프레임워크가 도와주지 않는 영역이라 구현 후 [기술 노트](../tech-notes.md) `nextjs-app-router.md`에 겪은 문제를 남긴다.

### 6. 폼별 처리 기준

#### 거래 등록 — 업로드가 폼보다 먼저 끝나야

- 사진 선택 즉시 업로드(동시 3), 썸네일마다 진행률 · 실패 · 재시도 [AC-PC-10, 15]
- 클라이언트에서 먼저 **다시 인코딩**한다 (긴 변 1600px, JPEG 0.85, `createImageBitmap` + `canvas`) — 10MB 사진을 1MB로 보내 업로드 시간을 줄이고, 업로드가 지나는 프록시의 본문 한도(4.5MB) 아래를 보장하며, HEIC를 서버가 받을 수 있는 JPEG로 바꾸고, 위치 정보가 담긴 EXIF를 브라우저 밖으로 내보내지 않는다 [AC-PC-12, 13]
- 디코드 실패(`createImageBitmap`이 거부 — 데스크톱 크롬의 HEIC 등)는 업로드하지 않고 그 썸네일에 "이 사진은 열 수 없어요. jpg · png로 바꿔 올려 주세요" [AC-PC-12]
- 업로드 주소는 `/api/uploads?kind=PRODUCT` — `kind`를 쿼리로 둔다 (서버가 파일보다 먼저 알아야 함)
- 업로드 중 [등록하기] 비활성 + "사진 올리는 중 N/M" — 이 경우만 비활성 버튼을 쓰되 이유를 버튼 옆에 글로 [AC-PC-16]
- `idempotencyKey`는 폼이 처음 렌더될 때 만들고, 재시도에도 같은 값 [AC-PC-08]
- 가격: 입력 중 콤마 삽입 시 커서 위치 보존 (콤마 수 변화만큼 이동)

#### 회원가입 — 미리 확인은 편의일 뿐

이메일 칸을 떠날 때 중복을 미리 알려주지만, 확인과 제출 사이에 누가 가져갈 수 있다 [SU-CC-03]. 미리 확인이 실패하면 조용히 넘어가고, 제출의 `409`가 최종이다 [AC-SU-08].

#### 채팅 입력 — Enter의 의미가 기기마다 다르다

| 환경 | Enter | Shift+Enter | 판별 |
| --- | --- | --- | --- |
| PC | 전송 | 줄바꿈 | `matchMedia('(pointer: fine)')` |
| 모바일 | 줄바꿈 | — | 전송은 버튼만 |
| 한글 조합 중 | 무시 | 무시 | `e.nativeEvent.isComposing` — 마지막 글자 두 번 전송 버그 방지 [AC-CH-12] |

## 06 · 포커스와 라이브 리전

**화면 변화마다 포커스 위치와 스크린리더 안내를 정했습니다.** 경로 이동, 모달, 목록 추가, 실시간 메시지처럼 전체 새로고침 없이 일어나는 변화를 키보드·스크린리더 사용자도 확인할 수 있도록 처리합니다.

### 1. 화면 변화별 규칙

| 순간 | 포커스 | 스크린리더가 읽는 것 | 방법 | 근거 |
| --- | --- | --- | --- | --- |
| 경로 이동 | 새 페이지 `h1` | 페이지 제목 | 경로 변화 감지 → `h1`에 `tabIndex=-1` + `focus()`. **첫 진입(새로고침)에는 하지 않음** — 브라우저가 이미 처리 | AC-CM-41 |
| 모달 · 바텀시트 열림 | 안의 첫 조작 요소 (삭제 확인은 [취소]) | 대화상자 제목 | 네이티브 `<dialog>` `showModal()` | AC-CM-42, AC-PX-02 |
| 모달 닫힘 | 열었던 버튼 | — | 연 요소를 기억했다가 복귀 | AC-CM-42 |
| [더 보기] 완료 | 새로 붙은 첫 카드 | "20개 더 불러왔어요" | 라이브 리전 | AC-PL-03 |
| 폼 제출 실패 | 첫 오류 칸 | 상단 요약 "입력 내용 N곳을 확인해 주세요" | `role="alert"` | AC-SU-17, AC-CM-44 |
| 로그인 실패 | 이메일 칸 (비밀번호 칸 비움) | "이메일 또는 비밀번호가 맞지 않아요" | `role="alert"` | AC-LI-07 |
| 토스트 | 이동 없음 | 토스트 문장 | `role="status"` (에러는 `alert`) | AC-CM-43 |
| 상태 `<select>` 변경 | 그대로 | "예약중으로 바꿨어요" | 라이브 리전 | AC-PD-03 |
| 마이 탭 전환 | 탭에 유지 | "판매중 3개" | 라이브 리전 | AC-MP-02 |
| 상대 메시지 수신 | 그대로 | "{닉네임}: {내용}" | 채팅 전용 라이브 리전 (아래 3절) | AC-CH-42 |
| [새 메시지 ↓] 누름 | 마지막 메시지 | — | | CH-A11Y-04 |
| 채팅 목록 행이 위로 이동 | 그 행에 있었으면 유지 | — | 행 `key`를 방 id로 고정 (DOM 재사용) | AC-CL-13 |
| 페이지 에러 · 404 | `h1` | 에러 제목 | | AC-CM-23 |
| 로딩 | 그대로 | (busy 상태) | 스켈레톤 영역 `aria-busy="true"` | CM-A11Y-10 |

### 2. 설계 판단

#### 모달 — 라이브러리 대신 `<dialog>`

포커스 가두기 · Esc 닫기 · 뒤 배경 조작 막기는 직접 만들면 빠지는 경우가 많다(Shift+Tab 역방향, 동적으로 추가된 버튼). 네이티브 `<dialog>`의 `showModal()`은 셋을 브라우저가 처리하고, 배경을 `inert`로 만든다. 지원 범위(최신 2개 버전 [CM-UI-09])에서 모두 동작한다. 남는 일은 "닫힌 뒤 연 요소로 돌아가기" 하나다.

바텀시트(360px)와 중앙 다이얼로그(1024px)는 같은 `<dialog>`에 CSS만 다르게 [AC-PX-13].

#### 라이브 리전 — 미리 있어야 읽힌다

라이브 리전은 **문장이 들어가기 전에 DOM에 이미 있어야** 스크린리더가 변화를 감지한다. 문장과 함께 새로 그리면 읽히지 않는 경우가 많다. 그래서 루트 레이아웃에 빈 리전 두 개(`polite` · `assertive`)를 미리 두고, `AnnouncerContext`의 `announce(text)`가 문장을 넣는다 ([02 상태 소유권](#02--상태-소유권)).

같은 문장을 연속으로 넣으면 변화가 없어 다시 읽히지 않는다 ("20개 더 불러왔어요"를 두 번). 넣기 전에 비우고, 다음 프레임에 넣는다. 이 현상은 [기술 노트](../tech-notes.md) `accessibility.md` 스파이크 ②에서 재현한다.

#### 채팅 — 내가 보낸 것까지 읽으면 시끄럽다

메시지 목록 전체를 `aria-live`로 두면 ① 내가 보낸 메시지를 다시 읽고 ② 과거 메시지 50개를 불러올 때 50개를 읽는다. 그래서:

- 목록은 `role="log"`이되 `aria-live="off"`
- 시각 숨김 `role="status"` 영역에 **상대가 보낸 새 메시지만** "{닉네임}: {내용}"으로 넣는다
- 과거 메시지 로드는 "이전 메시지 50개를 불러왔어요" 한 문장

[AC-CH-42]

#### 경로 이동 포커스 — Next.js가 해 주지 않는 것

App Router는 경로 이동 후 포커스를 관리하지 않는다. 그대로 두면 포커스가 클릭한 링크(이제 없는 요소)에 남거나 `body`로 떨어져, 스크린리더 사용자는 페이지가 바뀐 걸 모른다. 루트에 `<RouteFocus />`를 두어 `usePathname` 변화 시 `h1`으로 옮긴다. 쿼리스트링만 바뀔 때(필터 · 탭)는 옮기지 않는다 — 같은 페이지 안의 변화는 라이브 리전으로 알린다.

## 07 · 소켓 클라이언트

**클라이언트는 연결 상태를 표시하고, 전송 대기 메시지를 보관하며, 재연결 후 누락 데이터를 복구하도록 설계했습니다.** Socket.IO의 재연결 기능과 서비스의 전송 재시도·DB 커서 복구를 구분합니다. 연결·버퍼 동작의 확인 범위는 [WebSocket 스파이크](../tech-notes.md#websocket과-socketio)에 기록했습니다.

### 1. 연결 상태 기계

```
           로그인됨                 연결 성공
  idle ──────────────▶ connecting ───────────▶ connected ◀─────────────┐
   ▲                       ▲                      │                    │
   │ 로그아웃               │ 토큰 받고 재시도       │ transport close     │ 재연결 성공
   │                       │                      ▼                    │ (+ 복구 절차)
   │                       └──────────────── reconnecting ─────────────┘
   │                                              │
   │                         connect_error         │ disconnect 이유 = io server disconnect
   │                         UNAUTHORIZED          ▼   (토큰 만료로 서버가 끊음)
   └─────────────────────────────────────── needs_login ── 재로그인 화면
```

| 상태 | 화면 | 전송 버튼 | 근거 |
| --- | --- | --- | --- |
| `connecting` · `connected` | 아무것도 없음 | 보냄 | |
| `reconnecting` (5초 미만) | 아무것도 없음 — 짧은 끊김에 경고를 띄우면 깜빡임만 | 대기열로 | AC-CH-39 |
| `reconnecting` (5초 이상) | 상단 얇은 바 "실시간 연결이 끊겼어요. 다시 연결 중…" (`role="status"`) | 대기열로 | AC-CH-39 |
| `needs_login` | 재로그인 화면 (`next` = 현재 경로) | — | AC-CH-31 |
| `paused` | 상단 바 "이 탭의 실시간 연결이 꺼졌어요 [다시 연결]" (`role="status"`) | 대기열로 | AC-CH-33, [I-13](../troubleshooting.md#i-13) |

**`needs_login`이 따로 있는 이유**: 서버가 직접 끊으면 Socket.IO는 자동 재연결을 하지 않는다([스파이크 ⑤](../tech-notes.md#websocket과-socketio)). `disconnect` 이유를 보지 않으면 클라이언트는 영원히 `reconnecting`처럼 보이는 채 멈춘다.

**`paused`가 따로 있는 이유**: 서버가 끊는 경우는 둘이다 — 세션 만료(직전에 `error: UNAUTHORIZED`를 보낸다)와 연결 수 초과(아무 말 없이 끊는다). 둘을 같은 `needs_login`으로 받으면 여섯 번째 탭을 연 순간 가장 오래된 탭이 로그인 화면으로 가고, 세션이 멀쩡하니 곧장 돌아와 다시 연결하면서 **다른 탭을 밀어낸다** — 탭들이 서로를 끝없이 밀어낸다. 이유 없이 끊긴 연결은 스스로 다시 붙지 않고 사용자가 누를 때만 붙는다 ([I-13](../troubleshooting.md#i-13)).

### 2. 연결 하나, 탭 하나

| 결정 | 이유 |
| --- | --- |
| 탭당 소켓 하나, `SocketContext`가 소유 | 화면마다 연결하면 이동할 때마다 끊고 다시 붙는다 |
| 로그인 상태에서만 연결 | 비로그인 사용자는 실시간이 필요 없다 [AC-NT-10] |
| 토큰은 연결 · 재연결마다 새로 | `auth: (cb) => fetch('/api/auth/socket-token').then(r => r.json()).then(({ token }) => cb({ token }))` — 60초 토큰이 재연결 때 만료돼 있지 않게 [AC-LI-18a] |
| 방 조인은 채팅방 화면이 마운트될 때, 나갈 때 `room:leave` | 열려 있는 방만 조인 — 서버가 보내는 이벤트를 줄인다 |
| 조인한 방 목록을 컨텍스트가 기억 | 재연결 시 다시 조인해야 한다 (서버 메모리는 재시작으로 사라짐) |

### 3. 메시지 보내기

```
[전송] ─▶ tempId 생성 · 대기열에 { status: 'sending' } ─▶ 연결됨?
                                                         ├─ 예 ─▶ emitWithAck(5초)
                                                         │         ├─ ok    ─▶ 대기열에서 제거 · 캐시에 추가
                                                         │         ├─ 거절  ─▶ status: 'failed' (코드별 문구)
                                                         │         └─ 타임아웃 ▶ status: 'failed'
                                                         └─ 아니오 ▶ status: 'queued' ("연결 중…")
                                                                    ├─ 재연결 ─▶ 순서대로 emitWithAck (같은 tempId)
                                                                    └─ 30초 경과 ▶ status: 'failed'
[재시도] ─▶ 같은 tempId로 다시 ─ 서버가 이미 저장했으면 기존 메시지를 ack로 돌려줌 (중복 없음)
[삭제]   ─▶ 대기열에서 제거 (서버에 보내지 않음)
```

| 규칙 | 이유 | 근거 |
| --- | --- | --- |
| **`socket.emit` 직접 호출 금지**, `emitWithAck(event, payload, 5000)`만 | 타임아웃 없이 보내면 끊긴 동안 버퍼에 남았다가 재연결 후 몰래 전송된다 — 화면엔 실패, 상대에겐 도착 (스파이크 ⑤ 실험 6) | AC-CH-37 |
| 끊긴 상태에선 emit하지 않고 **별도 전송 대기열**에 | Socket.IO 내부 버퍼의 동작(타임아웃 시 제거, 없으면 유지)에 기대지 않는다. 별도 전송 대기열에서 상태를 관리해 화면에 표시한다 | AC-CH-38 |
| 재시도는 같은 `tempId` | "보낸 줄 알았는데 서버엔 없음"과 "서버엔 있는데 ack만 못 받음"을 클라이언트는 구분할 수 없다. 같은 `tempId`면 둘 다 안전 | AC-CH-04 |
| 실패한 말풍선을 지우지 않음 | 쓴 글을 잃게 하지 않는다 | AC-CH-04 |
| **모든 전송**을 한 번에 하나씩 — 앞 메시지의 ack를 받은 뒤 다음을, **200ms 간격**으로 | 앞 메시지보다 뒤 메시지가 먼저 저장되면 대화 순서가 뒤집힌다. 끊긴 동안 쌓인 대기열만이 아니라 연결 중에 빠르게 이어 보낸 두 메시지도 그렇다 — 서버는 한 연결의 이벤트를 동시에 처리하므로 방 잠금을 누가 먼저 잡을지 정해져 있지 않다 ([I-14](../troubleshooting.md#i-14)). 간격은 서버 전송 한도(초당 5)에 맞춘 것 | AC-CH-33 |
| 보내는 중에 끊기면 실패가 아니라 대기(`queued`)로 | 서버가 저장했는지 알 수 없지만 같은 `tempId`로 다시 보내면 어느 쪽이든 안전하다. 끊기기 전 전송의 늦은 타임아웃은 버린다 | AC-CH-04, 38 |
| 대기 메시지가 `RATE_LIMITED`를 받으면 실패가 아니라 대기 | 사용자가 잘못한 것이 아니다. `retryAfterMs` 뒤 같은 `tempId`로 다시 | AC-CH-33 |

**lint로 막기**: ESLint `no-restricted-syntax`로 `socket.emit(` 패턴을 `emitWithAck` 파일 밖에서 금지한다. 규칙은 문서보다 도구가 지킨다.

### 4. 다시 붙었을 때 — 복구 절차

순서가 중요하다. 받기를 먼저 끝내고 보내기를 한다 — 그래야 대기열의 메시지가 놓친 메시지들 **뒤에** 저장된다.

| 순서 | 처리 | 근거 |
| --- | --- | --- |
| 1 | 조인했던 방마다 `room:join { roomId, after: 캐시의 마지막 seq }` | AC-CH-05 |
| 2 | 응답 `missed`를 캐시에 합침 (같은 `seq` 무시), `hasMore`면 HTTP로 나머지 | AC-CH-05 |
| 3 | 대기열(`queued`)을 순서대로 전송 | AC-CH-38 |
| 4 | `['me', 'unread']` · `['chatRooms']` · 열린 방의 `['chatRoom', id]` 무효화 — 끊긴 동안의 변화 | AC-NT-13, AC-CL-11 |
| 5 | 보고 있는 방이 있으면 `room:read` | AC-CH-01 |
| — | 끊긴 동안 온 메시지의 토스트는 띄우지 않음 | AC-NT-13 |

#### 연결 중에 생긴 틈

연결이 살아 있어도 `message:new` 하나가 빠질 수 있다 — 서버 emit 실패, 조인 직전 커밋 등. 방마다 받은 마지막 `seq`를 기억하고, 새로 온 메시지의 `seq`가 **마지막 + 1이 아니면** 그 자리에서 `room:join { after: 마지막 }`으로 채운다. 번호가 연속이므로 "빠졌다"를 클라이언트가 스스로 안다 — 시각 커서로는 불가능했던 일이다 [결정 0016].

#### 읽음은 그린 번호로

`room:read`에는 **화면에 실제로 그린** 마지막 메시지의 `seq`를 싣는다. 받기만 하고 아직 그리지 않은 메시지(가상 스크롤 밖, 렌더 전)를 읽음으로 올리지 않기 위해서다 [AC-CH-01].

### 5. 탭이 숨겨졌다 돌아올 때

모바일 브라우저는 백그라운드 탭의 소켓을 끊기도 한다(언제 끊는지는 실기기 확인 필요 — [WebSocket 기술 노트 4절 "검증하지 못한 것"](../tech-notes.md#websocket과-socketio)).

| 순간 | 처리 | 근거 |
| --- | --- | --- |
| 숨겨짐 | 소켓은 그대로. 토스트는 띄우지 않고 배지 · 탭 제목 `(N)`만 갱신 | AC-NT-14 |
| 보임 | 끊겨 있으면 `socket.connect()` → 4절 복구. 연결돼 있어도 `['me', 'unread']` 재조회. 방을 보고 있으면 `room:read` | AC-CH-01, AC-NT-04 |
| 돌아왔을 때 | 밀린 토스트를 몰아서 띄우지 않음 | AC-NT-14 |

### 6. 이벤트 → 화면

캐시 갱신 규칙은 [03 캐시](#소켓-이벤트--캐시). 화면 쪽 반응만:

| 이벤트 | 화면 반응 |
| --- | --- |
| `message:new` (보는 방) | 아래 100px 이내면 자동 스크롤, 아니면 [새 메시지 ↓] · 라이브 리전 · `room:read` [AC-CH-14] |
| `message:new` (다른 화면) | 토스트 (채팅 목록 · 그 방이 아닐 때, 5초 내 같은 방은 합침) [AC-NT-05, 06] |
| `room:read` (상대) | 상대 `lastReadSeq` ≥ 내 마지막 메시지 `seq`면 그 아래 "읽음" [AC-CH-02] |
| `room:product_updated` (삭제) | 입력창 비활성 + "삭제된 물건이라 메시지를 보낼 수 없어요" [AC-CH-41] |
| ack `RATE_LIMITED` | `retryAfterMs` 동안 [전송] 비활성 + "잠시 후 보낼 수 있어요". 쓰던 글과 대기 메시지는 그대로 [AC-CH-33] |

## 08 · 화면 명세

**13개 화면마다 보이는 것, 네 가지 상태(로딩 · 빈 · 오류 · 권한), 조작과 이동을 한 표로 고정합니다.** 서버 · 클라이언트 렌더 범위는 [01 렌더링 전략](#01--렌더링-전략)에, 세부 동작은 각 기능 문서의 수용 조건에 있고, 이 절은 화면 단위로 다시 묶은 색인입니다. 새 동작을 정하지 않습니다 — 여기 적힌 것은 모두 수용 조건에서 왔습니다.

### 1. 화면 구조

```
(tabs) 하단 탭바 있음            탭바 없음
├─ /            홈              ├─ /products/[id]        상세
├─ /search      검색            ├─ /products/new         등록
├─ /chats       채팅 목록        ├─ /products/[id]/edit   수정
└─ /me          마이            ├─ /chats/[roomId]       채팅방
                                ├─ /me/edit · /me/password
                                └─ /login · /signup
```

### 3. 화면을 구현할 때의 순서

화면 하나는 ① 서버 컴포넌트의 조회와 권한 분기(`notFound()` · `redirect()`) ② `loading.tsx` 스켈레톤 ③ 정상 상태 ④ 빈 상태 ⑤ 오류 상태 ⑥ 키보드 흐름 순서로 만들고, PR의 셀프 리뷰 체크리스트가 ②~⑥을 확인합니다([개발 규칙](../dev.md)).

## 09 · 공통 컴포넌트

**두 화면 이상에서 쓰이는 조각만 공통 컴포넌트로 두고, 접근성 요구를 props가 아니라 컴포넌트의 기본 동작으로 넣습니다.** 한 화면에서만 쓰는 조각은 그 화면 폴더에 둡니다. 아래 이름과 props는 구현 전 설계이며, 구현하며 바뀌면 이 표를 같은 PR에서 고칩니다.

## 10 · 폴더 구조

**경로(`app/`)에는 조립만 두고, 화면 조각 · 훅 · 서버 통신은 기능 폴더에 모읍니다.** 상품 규칙을 고칠 때 여는 폴더가 하나가 되게 하는 것이 기준이며, 백엔드의 [기능별 모듈 구조](backend.md#폴더-구조-예정)와 같은 이름을 씁니다.

└─ src/
   ├─ proxy.ts                 # 보호 경로의 1겹 검사 — 쿠키 유무만 [01]. `src/`를 쓰면 `app/`과 같은 층에 둬야 인식된다
   ├─ app/
   │  ├─ layout.tsx            # 루트 — Provider · 토스트 · 라이브 리전 · 로그인 사용자
   │  ├─ (tabs)/               # 탭바 있는 화면: / · /search · /chats · /me

   │  ├─ chats/[roomId]/

   │  ├─ (auth)/               # login · signup
   │  ├─ api/[...path]/route.ts  # 같은 오리진 프록시 — Origin · 원 IP · 비밀 헤더 [결정 0004]
   │  └─ error.tsx · not-found.tsx · global-error.tsx
   ├─ features/                # 기능 하나 = 폴더 하나
   │  ├─ auth/                 # 폼 · 훅 · 쿼리

   │  ├─ chat/                 # 목록 · 방 · 입력창 · 소켓 이벤트 → 캐시
   │  ├─ me/
   │  └─ notification/         # 배지 · 토스트 규칙
   ├─ components/              # 공통 컴포넌트 17개 [09]
   ├─ lib/
   │  ├─ api/                  # apiFetch(클라이언트) · serverFetch(서버, no-store) · ApiError [04]
   │  ├─ query/                # QueryClient · 키 팩토리 [03]

   │  ├─ a11y/                 # RouteFocus · 라이브 리전 [06]
