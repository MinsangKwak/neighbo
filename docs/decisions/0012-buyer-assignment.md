# 0012 · 거래완료 시 구매자를 지정하고 구매 내역을 둔다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | `Product.buyerId · soldAt` · 상태 변경 API · 거래 상세 바텀시트 · 마이페이지 구매 내역 탭 · 삭제 정책(0006) |

## 맥락

거래완료를 "상태 값 하나"로만 두면 서비스에 "누가 누구와 거래했다"는 사실이 남지 않는다. 구매자 쪽 마이페이지엔 아무것도 없고, 두 번째 핵심 시나리오(구매자 흐름)가 "채팅하고 끝"으로 닫힌다.

## 선택

- 판매자가 거래완료로 바꿀 때 바텀시트 "누구와 거래했나요?" — 이 상품의 채팅 상대 목록 + "선택 안 함". 채팅 상대가 0명이면 바로 완료.
- 지정하면 `Product.buyerId · soldAt` 저장. 서버는 `buyerId`가 이 상품 채팅방의 구매자인지 검증(`400 NOT_A_CHAT_PARTNER`).
- 마이페이지에 **구매 내역** 탭: `Product WHERE buyerId = me AND status = SOLD`.
- 거래완료 → 판매중 복귀 시 `buyerId · soldAt` 초기화 (확인 모달에 명시).
- 구매자에게 알림은 없음 (1차). 구매자는 마이페이지에서 발견.

## 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 구매자 지정 없음 (상태만) | 바텀시트 · 탭 · 검증이 전부 사라짐 | 구매자 흐름이 완결되지 않음. "거래" 서비스인데 거래 사실이 데이터에 없음 |
| 구매자가 "구매 확정" 버튼으로 스스로 지정 | 양쪽 합의 | 흐름이 하나 더 (판매자 완료 → 구매자 확정). 1차엔 판매자 단독 지정이 당근과 같고 단순 |
| 별도 `Trade` 테이블 | 거래 이력 · 후기 확장 | 1차엔 상품당 거래가 최대 1건. 컬럼 둘로 충분. 후기가 들어오면 그때 테이블로 |
| 예약중에도 예약자 지정 | 일관성 | 예약은 자주 바뀌고 취소됨. 요구가 없는데 UI가 늘어남 |

## 트레이드오프

- 거래완료가 두 단계(상태 선택 → 상대 선택)가 된다. "선택 안 함"으로 한 번에 끝낼 수 있게 열어 둔다.
- 상품 삭제 시 구매 내역에서도 사라진다 (0006과 일관). ❓ 거래완료된 상품은 구매자의 내역에 남겨야 한다는 주장도 가능 — 02에서 `withDeleted()` 적용 여부로 결정.
- `buyerId`가 `User`를 참조하므로 탈퇴(2차) 시 처리 규칙이 필요해진다.

## 바뀔 가능성과 되돌리는 법

낮음. 후기 · 매너온도 같은 기능이 들어오면 `Trade` 테이블로 승격하고 `buyerId · soldAt`을 거기로 옮긴다. 그때까지는 컬럼 둘.
