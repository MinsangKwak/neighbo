# 0009 · 목록은 무한 스크롤 대신 [더 보기] 버튼 + 커서

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 중고 목록 · 검색 결과 · 채팅 목록 · 마이페이지 목록 (채팅방 과거 메시지는 예외) |

**목록은 커서 페이지네이션과 [더 보기] 버튼으로 추가 조회합니다.** 키보드 접근, 새 항목 안내, 뒤로가기 복원 방식을 함께 정의했습니다.

## 맥락

목록이 20개를 넘으면 더 불러와야 한다. 무한 스크롤은 익숙하지만 키보드 사용자가 푸터에 도달할 수 없고, 스크린리더에 "더 불러왔다"를 알리기 어렵고, 뒤로가기 시 스크롤 복원이 복잡하다. 그리고 오프셋 페이지네이션은 새 항목이 끼어들면 중복 · 누락이 생긴다.

## 선택

- 목록 끝에 **[더 보기] 버튼.** 누르면 다음 20개를 붙이고, 새로 붙은 첫 항목으로 포커스를 옮기며, `aria-live`로 "20개 더 불러왔어요".
- 페이지네이션은 **커서** `(createdAt, id)` base64. `limit+1`개를 조회해 `nextCursor` 유무를 판단. 서버는 `nextCursor: null`이면 버튼을 그리지 않게 알려준다.
- 뒤로가기: TanStack Query 캐시에 불러온 페이지가 남아 있어 그대로 복원.
- **예외**: 채팅방의 과거 메시지는 위로 스크롤 시 자동 로드 + [이전 메시지 보기] 버튼 병행. 위 방향 로드는 푸터 문제가 없고, 대화 맥락은 끊김 없이 읽는 게 자연스럽다.

## 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 무한 스크롤 (`IntersectionObserver`) | 익숙, 조작 없음 | 접근성 셋(푸터 도달 · 알림 · 포커스)을 전부 따로 해결해야 함. 00 개요 7절 "키보드만으로 완료"와 충돌 |
| 무한 스크롤 + [더 보기] 병행 | 둘 다 | 둘을 유지하면 포커스 · 스크롤 복원 로직이 두 배. 버튼 하나로 충분 |
| 숫자 페이지 (1 2 3 …) | 특정 페이지로 점프 | 커서와 양립 불가(전체 수 필요). 최신순 피드에서 "3페이지"는 의미가 계속 바뀜 |
| 오프셋 (`?page=2`) | 구현 단순 | 새 상품이 끼어들면 2페이지 첫 항목이 1페이지 마지막과 중복 |

## 트레이드오프

- 클릭 한 번이 더 든다. 피드 체류 시간이 중요한 서비스라면 불리하지만 거래 목록은 "찾는" 행동이라 괜찮다.
- 커서는 정렬 기준이 바뀌면(가격순 등) 커서 구조도 바뀐다. 1차는 최신순 하나.
- "전체 N개"를 보여줄 수 없다 (커서는 count를 안 함). 필요하면 별도 count 쿼리.

## 바뀔 가능성과 되돌리는 법

낮음. 무한 스크롤을 원하게 되면 `[더 보기]` 버튼에 `IntersectionObserver`를 얹어 **자동으로 눌리게** 하면 되고, 버튼은 키보드용으로 남긴다. 데이터 계층(커서)은 그대로다.
