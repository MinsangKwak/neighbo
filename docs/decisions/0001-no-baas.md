# 0001 · 인증·거래·채팅 로직은 별도 백엔드에서 관리한다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 서버 전부 · 인증 · 데이터 모델 · 배포 |

**Node.js·Express·Prisma로 백엔드를 구성하고, 권한·트랜잭션·실시간 처리를 서비스 계층에서 관리합니다.** PostgreSQL의 제약과 애플리케이션 처리 순서를 함께 정의할 수 있도록 선택했습니다.

## 맥락

작성자만 상품을 변경할 수 있어야 하고, 같은 상품·구매자 조합에는 채팅방이 하나만 있어야 합니다. 메시지 저장과 채팅방 갱신은 함께 성공해야 하며, 저장된 메시지는 실시간으로 전달되어야 합니다. 이 동작을 관리할 계층과 배포 구성을 정해야 합니다.

## 선택

인증 미들웨어, 입력 검증, 서비스의 권한·트랜잭션 처리, 응답·오류 처리를 분리합니다. 소켓 이벤트도 HTTP와 같은 서비스 함수를 호출하도록 설계합니다. 기술별 실험 결과와 적용 계획은 [기술 노트](../tech/README.md)에 기록합니다.

## 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| Supabase | PostgreSQL 기반 인증·실시간·파일 기능 제공 | 이번 설계는 권한·거래·채팅 처리를 Express 서비스 계층에서 관리하는 구성으로 통일 |
| Firebase | 인증과 실시간 구독 제공 | PostgreSQL의 관계·유니크 제약·트랜잭션을 사용하는 데이터 모델 선택과 맞지 않음 |
| Next.js Route Handler만으로 백엔드 구성 | 저장소·배포 단순화 | Vercel 함수와 별도로 상시 소켓 서버가 필요해 백엔드 처리가 분산됨 |
| NestJS | 모듈·DI 기반 구조 제공 | 1차 범위는 Express 미들웨어와 서비스 계층으로 구성하고 프레임워크 도입 범위를 제한 |

## 트레이드오프

- 인증·업로드·소켓을 직접 구현하고 검증할 작업이 늘어납니다. 소요 시간은 아직 측정하지 않았습니다.
- 쿠키 속성, 요청 제한, 파일 검증 등 보안 설정과 점검을 직접 관리해야 합니다.
- 백엔드 실행 환경과 DB의 배포·운영 비용을 별도로 관리해야 합니다.

## 바뀔 가능성과 되돌리는 법

1차 범위에서는 유지합니다. 인증·권한·실시간 처리를 다른 플랫폼으로 옮기면 서비스 계층과 데이터 접근 방식을 함께 검토해야 합니다. 파일 저장소는 `ImageStorage` 인터페이스로 분리하므로 구현체를 교체할 수 있습니다 ([결정 0010](0010-upload-on-select.md)).
