# 0001 · BaaS 대신 백엔드를 직접 만든다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 서버 전부 · 인증 · 데이터 모델 · 배포 |

## 맥락

열 가지 기능 중 권한(작성자만 삭제) · 유니크 제약(채팅방) · 트랜잭션(메시지 저장 + 방 갱신) · 실시간(소켓)이 핵심이다. Firebase · Supabase를 쓰면 이 네 가지가 각각 보안 규칙 · RLS · 트리거 · Realtime 구독이라는 **플랫폼 설정**으로 바뀐다. 동작은 하지만 "왜 이렇게 동작하는가"가 코드 밖에 있다.

## 선택

Node.js + Express + Prisma로 백엔드를 직접 쓴다. 인증 미들웨어 → 입력 검증 → 권한 검사 → 트랜잭션 → 응답의 순서가 코드로 읽혀야 한다.

전제: 백엔드 경험이 적다는 것을 알고 시작한다. 그래서 각 기술의 원리를 [기술 노트](../tech/README.md)로 먼저 익히고, 프레임워크가 감추는 부분을 한 번씩 직접 만든다.

## 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| Supabase (Postgres + Auth + Realtime + Storage) | 가입 · 로그인 · 실시간 · 파일이 하루면 붙음. Postgres라 2번 결정과도 맞음 | 권한이 RLS 정책 문자열에, 읽음 처리 같은 로직이 DB 트리거나 Edge Function으로 흩어짐. 문제가 나면 원인이 플랫폼 안에 있어 추적이 어려움 |
| Firebase (Firestore + Auth) | 실시간 구독이 기본 | NoSQL이라 "채팅방은 상품 × 구매자당 하나" 같은 제약을 DB가 보장하지 않음. 클라이언트에서 막아야 하고 그건 보장이 아님 |
| Next.js Route Handler만으로 백엔드 (서버 분리 없음) | 저장소 · 배포가 하나 | Vercel 서버리스는 WebSocket 상시 연결을 못 유지함. 소켓 서버를 따로 두는 순간 백엔드가 둘이 됨 |
| NestJS | 구조가 강제되어 배우기 좋음 | 데코레이터 · DI가 Express 위에 한 겹 더 숨김. 처음엔 숨기는 게 적은 쪽 |

## 트레이드오프

- 구현 시간이 BaaS보다 2~3배 든다. 특히 인증 · 파일 업로드.
- 보안 실수가 내 책임이 된다 (쿠키 속성, rate limit, 파일 검증). 대신 그 실수를 경우의 수 문서에서 미리 나열했다.
- 서버 비용이 생긴다 (Railway). BaaS 무료 티어라면 0원.

## 바뀔 가능성과 되돌리는 법

낮다. 이 프로젝트의 목적 자체가 "직접 만든 것"이라 BaaS로 돌아가면 목적이 사라진다. 다만 **파일 저장소**만은 `ImageStorage` 인터페이스 뒤에 있으므로 Supabase Storage · R2로 바꿔도 구현체 한 파일이다 (→ 0010).
