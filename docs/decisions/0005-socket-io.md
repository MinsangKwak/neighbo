# 0005 · 실시간은 Socket.IO로 하되 밑바닥을 먼저 만든다

| 상태 | 결정 2026-11-09 · 스파이크 결과 반영 2026-11-09 |
| --- | --- |
| 영향 | 채팅방 · 채팅 목록 · 배지 · 소켓 서버 · 인증(0003) |

## 맥락

필요한 것: 메시지 수신 · 읽음 동기화 · 배지 push · 재연결 후 누락분 복구 · 회사 프록시에서 WebSocket이 막혔을 때의 폴백. 그리고 이 영역은 처음이다.

## 선택

Socket.IO 4. 룸(`room:{id}` · `user:{id}`) · ack · 자동 재연결 · 폴링 폴백을 쓴다. **단, 쓰기 전에 다음을 직접 만든다** — 라이브러리가 무엇을 대신해 주는지 모르면 문제가 났을 때 어디를 봐야 하는지 모른다.

1. `ws` 패키지만으로 에코 서버: 핸드셰이크 헤더 확인 · 프레임 수신 · ping/pong
2. 거기에 재연결(지수 백오프)과 "끊긴 동안 놓친 메시지 복구"를 직접 구현
3. 그 다음 Socket.IO로 같은 것을 다시 만들어 **무엇이 사라졌는지** 비교

결과는 [기술 노트 `websocket.md`](../tech/websocket.md)에. 스파이크로 정해진 것:

- Socket.IO가 대신해 주지 **않는** 것 네 가지 — 서버 재시작을 넘는 복구(DB `after` 커서), 보낸 줄 알았던 메시지의 유실 · 중복(`tempId` + 유니크 + 재시도), 서버가 끊었을 때의 재연결, 연결 중 토큰 만료 검사.
- `connectionStateRecovery`는 **쓰지 않는다.** 짧은 순단엔 동작했지만 서버 재시작을 넘지 못해 DB 커서가 어차피 필요하고, 복구 경로가 둘이면 중복 처리가 두 배가 된다.
- 타임아웃 없는 emit은 금지 — 끊긴 동안 버퍼에 남았다가 재연결 후 몰래 전송되는 것을 확인했다.

## 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| `ws`만으로 끝까지 | 가장 얇음. 원리가 다 보임 | 재연결 · 룸 · ack · 폴백을 전부 직접 유지해야 함. 배우는 건 스파이크로 충분, 운영 코드는 검증된 것으로 |
| SSE (Server-Sent Events) + HTTP POST | 단방향이라 단순. 프록시 친화적 | 읽음 · 타이핑 같은 클라이언트 → 서버 이벤트가 전부 HTTP가 됨. 양방향이 자연스러운 채팅엔 어색 |
| 폴링만 (5초마다 GET) | 소켓 없음 | "실시간"이 아님. 배우려는 것이 이것 |
| Pusher · Ably 같은 호스팅 서비스 | 서버 확장 고민 없음 | 0001과 같은 이유. 플랫폼 안에 숨음 |

## 트레이드오프

- Socket.IO는 표준 WebSocket이 아니라 자체 프로토콜이다. 다른 클라이언트(네이티브 앱)가 붙으려면 Socket.IO 클라이언트가 필요하다.
- 서버 인스턴스가 2개 이상이 되면 Redis 어댑터가 필요하다. 1차는 단일 인스턴스.
- 번들 크기 약 40KB(gzip 전).

## 바뀔 가능성과 되돌리는 법

낮다. 소켓 이벤트 이름 · 페이로드는 04 API 문서에 REST와 같은 수준으로 적고, 클라이언트는 `useChatSocket()` 훅 하나로 감싼다. 라이브러리를 바꾸게 되면 훅 안쪽과 서버 `socket/` 폴더만 바뀐다.
