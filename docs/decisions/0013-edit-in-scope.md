# 0013 · 거래 수정을 1차 범위에 넣는다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 등록 폼 재사용 · `PATCH /products/{id}` · 상세 `⋯` 메뉴 · 사진 삭제 · 수정 URL 권한 |

## 맥락

00 개요의 열 가지 기능에 "수정"이 없다. 그런데 오타 하나, 가격 조정 하나 때문에 삭제 후 재등록하면 채팅방이 끊기고(0006에서 삭제된 방은 전송 불가) 구매자는 새 글을 찾아 다시 채팅을 걸어야 한다. 수정이 없으면 삭제 정책이 사용자에게 가혹해진다.

## 선택

- 수정을 1차에 넣는다. 화면은 등록 폼 재사용 (`/products/{id}/edit`), 기존 사진 삭제 · 새 사진 추가 · 제목 · 가격 · 설명 변경.
- 상태는 수정 폼에서 바꾸지 않는다 (상태 변경은 별도 API · 별도 UI — 0012).
- 거래완료 상품도 수정 가능 (제목 · 설명 정정 용도). 가격 변경은 허용하되 구매 내역의 가격도 함께 바뀜 — ❓ 02에서 `soldPrice` 스냅샷을 둘지.
- 수정 이력 · "(수정됨)" 표시 없음.
- 동시 수정은 마지막 저장 승리 (낙관적 잠금 없음 — 1인 판매자가 두 탭에서 동시에 고치는 경우뿐).

## 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 수정 없음 (삭제 후 재등록) | 기능 하나 적음 | 채팅방 단절. 0006의 "삭제된 방 전송 불가"와 결합하면 사용자가 손해 |
| 가격만 수정 (인라인) | 가장 흔한 수정만 | 제목 오타 · 사진 교체도 흔함. 폼 재사용이라 전체 수정이 비용 차이 없음 |
| 수정 시 채팅 상대에게 시스템 메시지 "가격이 바뀌었어요" | 투명 | 시스템 메시지 타입이 생김 (0005 범위 확장). 2차 |

## 트레이드오프

- 폼이 두 모드(생성 · 수정)를 가진다. 초기값 · 제출 API · 성공 후 이동이 분기한다.
- 기존 사진 삭제는 파일 삭제를 수반한다 — 저장 실패 시 파일만 먼저 지워지는 순서 문제. 파일 삭제는 DB 커밋 후.
- 구매 내역의 가격이 사후에 바뀔 수 있다.

## 바뀔 가능성과 되돌리는 법

낮음. 빼려면 라우트 · `⋯` 메뉴 항목 · `PATCH` 하나를 제거하면 된다. 폼 컴포넌트는 생성 모드만 남는다.
