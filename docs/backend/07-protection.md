# 백엔드 07 · 보호 장치와 배치

[백엔드 설계](README.md) · 앞: [06 에러 코드](06-errors.md) · 다음: [08 관찰 가능성](08-observability.md)

**정상 사용자는 느끼지 못하고, 비정상 사용 · 실수 · 시간이 쌓인 찌꺼기만 걸러 내는 장치들입니다.** 각 장치마다 "무엇을 막는가 · 정상 사용자가 걸릴 확률 · 걸렸을 때 무엇을 보나"를 함께 정합니다.

## 1. rate limit

| 대상 | 키 | 한도 | 막는 것 | 근거 |
| --- | --- | --- | --- | --- |
| 로그인 · 회원가입 · 이메일/닉네임 확인 | IP | 분당 10 | 비밀번호 대입, 계정 존재 여부 수집 | AC-CM-32 |
| 그 외 HTTP 쓰기 | 사용자 | 분당 30 | 상품 · 방 대량 생성 | AC-CM-32 |
| `GET /me/unread` | 사용자 | 분당 60 | 폴링 버그로 인한 폭주 | AC-NT-12 |
| 소켓 `message:send` | 사용자 | 초당 5, 넘으면 10초 차단 | 메시지 폭탄 | AC-CH-33 |
| 소켓 연결 수 | 사용자 | 5개 (넘으면 가장 오래된 연결 끊음) | 탭 폭주 · 재연결 루프 버그 | AC-CH-33 |
| 업로드 | 사용자 | 분당 30 (= 쓰기 한도) | 저장소 채우기 | — |

| 결정 | 이유 |
| --- | --- |
| 저장소는 **프로세스 메모리** (고정 창 카운터) | 단일 인스턴스 [결정 0005]. 인스턴스가 늘면 Redis로 — 인터페이스 `RateLimitStore` 뒤에 둔다 |
| 계정 잠금은 하지 않음 | 남의 이메일로 실패를 반복해 그 사람을 잠글 수 있다 (서비스 거부). IP 한도로 대입만 막는다 [LI-ST-01] |
| 프록시 뒤의 IP | Railway가 붙이는 `X-Forwarded-For`의 첫 값. Express `trust proxy`를 플랫폼 홉 수에 맞게 — 잘못 설정하면 모든 요청이 같은 IP로 보여 정상 사용자가 함께 막힌다 |
| 응답 | `429 RATE_LIMITED` + `Retry-After` 초 |

## 2. 업로드 검증 파이프라인

순서가 중요하다 — 싼 검사를 먼저 해서 비싼 처리(디코딩)에 도달하는 나쁜 파일을 줄인다.

| 단계 | 검사 | 실패 시 | 이유 |
| --- | --- | --- | --- |
| 1 | 인증 · rate limit | 401 · 429 | 익명 업로드 차단 |
| 2 | `Content-Length` ≤ 10MB, 스트림도 10MB에서 끊음 | 413 | 헤더를 속여도 스트림에서 잘림 |
| 3 | 앞 12바이트 매직 바이트 → jpeg · png · webp · heic | 400 `UNSUPPORTED_IMAGE` | 확장자 · `Content-Type`은 클라이언트가 정함 [AC-CM-33] |
| 4 | 메타데이터만 읽어 픽셀 수 ≤ 5,000만 | 400 `INVALID_FILE` | 디코딩 전에 압축 폭탄 차단 [AC-PC-13] |
| 5 | 디코딩 · EXIF 회전 적용 · EXIF 제거 · 1600px / 400px webp | 400 `INVALID_FILE` (손상) | 위치 정보 제거 [AC-PC-14] |
| 6 | `ImageStorage.put()` 두 벌 | 500 | — |
| 7 | `Upload` 행 생성 | 500 (파일은 배치가 정리) | — |

이미지 처리는 CPU를 많이 쓴다. 단일 인스턴스에서 동시에 여러 장이 오면 다른 요청이 느려지므로 **동시 처리 수를 2로 제한하는 대기열**을 둔다. 프론트는 이미 동시 3장으로 보내고 [AC-PC-10], 서버 대기열이 넘치면 `429`.

## 3. 비밀번호 · 인증 비용

| 항목 | 값 | 이유 |
| --- | --- | --- |
| bcrypt cost | 12 | 측정 후 확정 — 목표 해시 1회 200~300ms ([기술 노트](../tech/README.md) `password-hashing.md`) |

| JWT 비밀키 | 환경 변수, 32바이트 이상, 없으면 부팅 실패 | — |

## 4. 배치 작업

| 작업 | 주기 | 대상 | 처리 | 근거 |
| --- | --- | --- | --- | --- |
| 고아 업로드 정리 | 하루 1회 (새벽) | `Upload.createdAt < now - 24h` | 파일 두 벌 삭제 → 행 삭제 | AC-PC-19 |
| 삭제 상품 이미지 정리 | 하루 1회 | `Product.deletedAt < now - 30d AND imagesPurgedAt IS NULL` | 파일 삭제 → `ProductImage` 삭제 → `imagesPurgedAt` 기록 | AC-PX-12 |
| 고아 파일 정리 | 주 1회 | 저장소에 있지만 DB(`ProductImage` · `Upload` · `User.avatarUrl`) 어디에도 없는 키 | 7일 넘은 것만 삭제 | 커밋 후 파일 삭제 실패분 ([03 트랜잭션](03-transactions.md)) |

| 결정 | 이유 |
| --- | --- |
| 서버 프로세스 안의 스케줄러 (`setInterval` + 다음 실행 시각 계산) | 외부 크론 서비스 · 라이브러리 없이 20줄 [00 개요 의존성 규칙] |
| 실행 전 `pg_try_advisory_lock` | 인스턴스가 둘이 되거나 재시작이 겹쳐도 한 번만 실행 |
| 한 번에 100건씩, 다 끝날 때까지 반복 | 큰 삭제가 DB를 오래 잡지 않게 |
| 파일 먼저 지우고 행을 지움 | 행을 먼저 지우면 파일 키를 잃어 영영 못 지운다. 파일 삭제 실패 시 행이 남아 다음 실행에서 재시도 |
| 결과를 로그 한 줄로 (`job`, `deleted`, `failed`, `ms`) | [08 관찰 가능성](08-observability.md) |
