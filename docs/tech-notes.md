# 기술 노트

[문서 목차](README.md)

**기술 노트는 서비스에 필요한 동작과 실험에서 확인한 결과를 기록합니다.** 사용 목적, 동작 원리, 최소 구현, 적용 방식, 문제 원인을 구분합니다. 현재 WebSocket 노트와 스파이크 6개가 있으며, 다른 항목은 아래 표의 계획 단계입니다.

## 기록 항목

| 항목 | 내용 |
| --- | --- |
| 사용 목적 | 필요한 서비스 동작과 대안. 관련 [결정 기록](decisions.md) 연결 |
| 동작 원리 | 요청·연결·데이터 처리 순서 |
| 최소 구현·실험 | 실행 코드, 관찰 결과, 라이브러리가 담당하는 범위 |
| 적용 방식 | 서비스에 적용할 설정·인터페이스·처리 규칙 |
| 문제 원인 | 증상, 가설, 확인 방법, 원인, 수정, 재발 방지 |

실험 결과와 적용 계획은 별도로 표시합니다. 구현·테스트 중 확인한 내용은 해당 노트와 문제 기록에 추가합니다.

## 실험 코드 관리

- 재현 가능한 코드는 `spikes/`에서 서비스와 분리해 관리합니다.
- 실행 조건, 관찰 결과, 확인하지 못한 범위를 노트에 함께 기록합니다.
- 결과에 따라 설계가 달라지면 [결정 기록](decisions.md)과 관련 명세를 갱신합니다.

```markdown
### YYYY-MM-DD · 한 줄 증상
```

## WebSocket과 Socket.IO

**WebSocket 스파이크에서는 연결·하트비트·재연결·메시지 복구와 Socket.IO 버퍼 동작을 확인했습니다.** Socket.IO가 제공하는 재연결·룸·ack와 별도로, 누락 메시지 조회와 `tempId` 재시도는 서비스에서 처리하도록 설계했습니다. 아래 기록은 실험 결과이며 서비스 통합 검증은 구현 후 진행합니다.

---

### 1. 왜 필요한가

채팅 수신 · 읽음 동기화 · 배지 갱신은 **서버가 먼저** 클라이언트에게 알려야 하는 일입니다. 주기적 폴링은 조회 간격만큼 수신이 지연되고 반복 요청이 발생합니다. WebSocket은 한 번 연결하면 양쪽이 아무 때나 보낼 수 있는 통로입니다.

대안 비교와 Socket.IO를 고른 이유는 [결정 0005](decisions.md#0005--실시간-전달은-socketio-누락-복구는-db-커서로-처리한다)에 있습니다.

---

### 2. 어떻게 동작하는가

```
브라우저                                   서버
  │  GET /  HTTP/1.1                        │
  │  Upgrade: websocket                     │
  │  Sec-WebSocket-Key: F1gLd1Ja...==       │   ← 매번 무작위 16바이트
  │ ──────────────────────────────────────▶ │
  │                                         │   accept = base64(sha1(key + 고정 GUID))
  │  HTTP/1.1 101 Switching Protocols       │
  │  Sec-WebSocket-Accept: <accept>         │
  │ ◀────────────────────────────────────── │
  │                                         │
  │  ═══════ 이제부터 HTTP가 아니라 프레임 ═══════
  │  [FIN|opcode][MASK|len][mask 4B][payload]│   ← 클라→서버는 반드시 마스킹
  │ ──────────────────────────────────────▶ │
  │  [FIN|opcode][len][payload]             │   ← 서버→클라는 마스킹 안 함
  │ ◀────────────────────────────────────── │
  │  ping (opcode 9) ◀── / ──▶ pong (10)    │   ← 살아 있는지 확인
```

- 핸드셰이크는 평범한 HTTP 요청이라 **쿠키 · Origin 헤더가 실린다** — 인증을 여기서 한다.
- 101 이후는 TCP 위의 프레임 흐름. **TCP는 메시지 경계를 모른다** — 프레임 두 개가 한 덩어리로 오거나 하나가 반으로 쪼개져 올 수 있다.
- 상대가 FIN 없이 사라지면(와이파이 끊김, 노트북 덮음) **TCP는 그걸 모른다.** 그래서 ping/pong이 필요하다.

---

### 3. 최소 구현과 관찰

스파이크 6개, 총 430줄. Node 22, `ws` 8, `socket.io` 4.

#### ① 라이브러리 없이 핸드셰이크 · 프레임 파싱 — `01-raw-handshake.mjs`

`node:http`의 `upgrade` 이벤트에서 `Sec-WebSocket-Accept`를 직접 계산하고, 마스크를 XOR로 풀어 텍스트를 꺼냈다.

**첫 실행에서 버그가 났다.** 클라이언트가 `send('안녕')`, `send('hello')`를 연달아 보냈는데 서버는 첫 번째만 받았다. 로그를 보니 `data` 이벤트가 23바이트 한 번 — 프레임 두 개(12 + 11바이트)가 한 덩어리로 왔고, 코드는 첫 프레임만 읽고 나머지를 버렸다.

```js
// 2026-11-09 수정: 버퍼에 쌓고, 프레임 하나가 다 찰 때까지 기다리며, 찼으면 잘라내고 반복
let pending = Buffer.alloc(0);
socket.on('data', (chunk) => {
  pending = Buffer.concat([pending, chunk]);
  while (pending.length >= 2) {
    // ... 길이 계산
    if (pending.length < offset + 4 + len) return; // 반쪽 — 다음 data를 기다림
    // ... 마스크 풀기
    pending = pending.subarray(offset + len);
  }
});
```

→ `ws` · Socket.IO가 대신해 주는 첫 번째 것: **프레임 경계 복원.**

#### ② 반쯤 열린 연결과 하트비트 — `02-heartbeat.mjs`

클라이언트 소켓의 읽기를 멈춰(`_socket.pause()`) 프로세스가 얼어붙은 상황을 만들었다.

| 조건 | 서버가 끊김을 안 시점 |
| --- | --- |
| 하트비트 없음 | **끝까지 모름.** 3.5초 뒤 테스트가 정리하며 끊을 때까지 `clients.size = 1` |
| 1초 간격 ping, 직전 pong 없으면 종료 | 2.0초 (간격 × 2) |

부수 발견: `terminate()` 뒤에도 `setInterval`이 한 번 더 돌았다. 연결마다 만든 타이머를 `close`에서 지우지 않으면 연결 수만큼 새어 나간다.

→ 대신해 주는 두 번째 것: **ping/pong과 끊김 판정.** Socket.IO 기본값은 `pingInterval 25s + pingTimeout 20s` = **최대 45초 동안 끊긴 걸 모른다.**

#### ③ 재연결 · ④ 놓친 메시지 복구 — `03-reconnect-recover.mjs`

서버를 내렸다 올리는 사이 두 메시지가 DB에 저장된 상황. 클라이언트 둘 중 하나만 재연결 시 `join { after: 마지막 id }`를 보낸다.

| 클라이언트 | 받은 메시지 |
| --- | --- |
| `after` 커서 있음 | m1 · **m2 · m3** · m4 |
| 커서 없음 | m1 · m4 — **m2 · m3 영영 유실** |

재연결은 지수 백오프 + 지터(112 → 297 → 466ms)로 서버가 다시 뜨자마자 붙었다. 지터가 없으면 서버 재시작 순간 모든 클라이언트가 같은 박자로 몰린다.

순서 규칙도 확인: **저장이 먼저, 전송이 나중.** 반대면 전송은 됐는데 저장 전에 죽은 메시지는 복구 쿼리에도 없다.

#### ⑤ Socket.IO로 다시 — `04-socketio.mjs` · `05-socketio-buffer-recovery.mjs` · `06-buffer-no-timeout.mjs`

| 실험 | 관찰 | 의미 |
| --- | --- | --- |
| 쿠키 없는 연결 | 미들웨어에서 `next(new Error('UNAUTHORIZED'))` → 클라이언트 `connect_error` | 핸드셰이크 인증이 미들웨어 한 곳에 모인다 |
| 같은 사용자 두 탭, `user:{id}` 룸 | 탭 A의 `room:read`를 탭 B가 받음 | 다른 세션 동기화는 룸 하나로 해결 |
| **서버가 명시적으로 끊음** (`disconnectSockets`) | 이유 `io server disconnect`, **자동 재연결 안 함** | 토큰 만료로 서버가 끊으면 클라이언트가 직접 재로그인 후 `connect()`해야 한다 |
| **서버 크래시** 순간 emit (클라이언트는 아직 `connected=true`) | ack 즉시 `socket has been disconnected`, 버퍼에도 없음, **재연결 후 DB에 없음.** 같은 `tempId`로 재시도해야 저장 | 보낸 줄 알았는데 사라지는 창이 실제로 있다 → `tempId` 재시도 필수 |
| `connected=false`일 때 emit, **ack 타임아웃 있음** | `sendBuffer=1` → 타임아웃 시 버퍼에서 제거 → 재연결 후에도 전송 안 됨 | 실패 표시와 실제가 일치 |
| `connected=false`일 때 emit, **타임아웃 없음** | 버퍼에 남았다가 **재연결 후 1.9초 늦게 몰래 전송** | 사용자는 실패로 보는데 상대에겐 도착하는 유령 전송 가능 → 타임아웃 없이 보내지 않는다 |
| 내장 복구 `connectionStateRecovery`, 순단 · 서버 살아 있음 · 사전에 메시지 1개 받음 | `recovered=true`, 순단 중 메시지 받음 | 짧은 순단엔 동작 |
| 내장 복구, 사전에 받은 메시지 없음 | `recovered=false` | "마지막으로 받은 위치"가 없으면 복구 불가 |
| 내장 복구, **서버 재시작** | `recovered=false`, 재연결 전 메시지 **유실** | 복구 저장소가 서버 메모리라 재시작을 못 넘는다 → DB 커서가 여전히 필요 |

#### Socket.IO가 지운 코드 · 남긴 일

| 최소 구현에서 처리한 동작 | Socket.IO의 처리 범위 |
| --- | --- |
| 핸드셰이크 · `Sec-WebSocket-Accept` | 사라짐 |
| 프레임 버퍼링 · 마스크 · 경계 복원 | 사라짐 |
| ping/pong · 끊김 판정 · 타이머 정리 | 사라짐 (간격만 설정) |
| 지수 백오프 + 지터 재연결 | 사라짐 (`reconnectionDelay` · `randomizationFactor`) |
| 룸 · 브로드캐스트 · 요청-응답(ack) | 사라짐 |
| WebSocket 막힌 네트워크 대응 | 사라짐 (long-polling 폴백) |
| **놓친 메시지 복구 (서버 재시작 포함)** | **남음** — DB `after` 커서 |
| **보낸 줄 알았던 메시지의 유실 · 중복 방지** | **남음** — `tempId` + 서버 유니크 + 재시도 |
| **서버가 끊었을 때의 재연결** | **남음** — `io server disconnect` 처리 |
| **인증 토큰 만료 검사 (연결 중)** | **남음** — 이벤트마다 `exp` 확인 |

### 4. 이 프로젝트에서 쓰는 방식

| 항목 | 값 · 규칙 | 근거 |
| --- | --- | --- |
| 하트비트 | `pingInterval 10s` · `pingTimeout 5s` → 최대 15초 안에 끊김 감지. 기본 45초는 "보낸 줄 아는 창"이 너무 길다 | ② |
| 재연결 | Socket.IO 기본 지수 백오프, `reconnectionDelayMax 5s`, `randomizationFactor 0.5` | ③ |
| 메시지 전송 | **반드시** `socket.timeout(5000).emit('message:send', { roomId, tempId, content }, cb)`. 타임아웃 없는 emit 금지 (lint 규칙으로) | ⑤ 유령 전송 |
| 끊긴 상태의 전송 | `connected=false`면 emit하지 않고 앱 대기열에 넣고 말풍선을 "연결 중…"으로. `connect` 이벤트에서 같은 `tempId`로 순서대로 재전송. 30초 넘으면 "전송 실패" | ⑤ 버퍼 동작에 기대지 않음 |

| 복구 | 재연결 시 열려 있는 방마다 `room:join { roomId, after }` → 서버가 DB에서 누락분 반환. **`connectionStateRecovery`는 켜지 않는다** — 재시작을 못 넘어서 어차피 DB 커서가 필요하고, 복구 경로가 둘이면 중복 처리가 두 배 | ④ · ⑤ |
| 다른 세션 동기화 | 연결 시 `user:{userId}` 룸에 조인. 읽음 · 배지는 이 룸으로 | ⑤ 두 탭 |
| 상품 변경 실시간 반영 | 상태 변경 · 삭제 · 가격 수정 시 그 상품의 모든 방(`room:{id}`)에 `room:product_updated` | 룸 비용 낮음 |

| 인증 | 프론트(같은 오리진)가 `/api/auth/socket-token`으로 **60초짜리 소켓 전용 토큰**을 받아 `io(SOCKET_URL, { auth: { token } })`. 서버 미들웨어가 검증. 재연결마다 새 토큰(`auth`를 함수로) | ⑤ `handshake.auth` 동작 확인 · [결정 0004 갱신](decisions.md#0004--프론트가-백엔드를-프록시해-같은-오리진을-유지한다) |
| 저장 순서 | DB 커밋 → emit. 반대 금지 | ③ |
| 폴링 폴백 | Socket.IO 기본(`websocket` → 실패 시 `polling`). 별도 HTTP 폴링 루프는 두지 않음 | ⑤ |

#### 검증하지 못한 것

- **브라우저의 쿠키 · `SameSite` 동작.** Node 클라이언트는 쿠키를 헤더로 직접 넣어 실험했다. 실제 브라우저에서 교차 사이트 소켓 핸드셰이크에 쿠키가 실리는지는 확인 못 했고, 그래서 쿠키 대신 단기 토큰을 `auth`로 넘기는 쪽으로 정했다 — 이 방식은 쿠키 정책과 무관하다.
- **모바일 사파리 백그라운드 탭에서 소켓이 언제 끊기는가.** 실기기가 필요하다. 구현 단계 워크스루에서 확인 후 5절에 적는다.
- **Railway의 유휴 연결 타임아웃.** 배포 후 확인.

### 5. 겪은 문제와 원인

#### 2026-11-09 · 연달아 보낸 두 메시지 중 두 번째가 사라짐 (스파이크 ①)

- 증상: 클라이언트가 `send` 두 번, 서버 로그엔 첫 번째만.
- 가설: 두 번째 `send`가 전송되지 않았다.
- 확인: `data` 이벤트 바이트 수를 찍어 보니 23바이트 한 번 = 두 프레임 합.
- 원인: **TCP는 메시지 경계를 보존하지 않는다.** `data` 한 번 ≠ 프레임 하나.
- 수정: 버퍼 누적 + 프레임 길이만큼 잘라내는 루프.
- 재발 방지: 운영 코드는 `ws` · Socket.IO가 처리. 같은 원리가 HTTP 스트리밍 · 업로드 파싱에도 해당한다는 것을 `image-pipeline.md`에 연결.

#### 2026-11-09 · 연결 종료 뒤에도 하트비트 타이머가 돎 (스파이크 ②)

- 증상: `terminate` 로그가 같은 연결에 대해 두 번.
- 원인: 연결마다 만든 `setInterval`을 `close`에서 지우지 않음.
- 재발 방지: 운영 코드는 Socket.IO 내장 하트비트를 쓰고 직접 타이머를 만들지 않는다. 직접 만들 일이 생기면 `close` 핸들러에서 정리하는 것을 리뷰 체크리스트에.

#### 2026-11-09 · 서버를 다시 올려도 클라이언트가 붙지 않음 (스파이크 ⑤)

- 증상: 실험 3에서 서버 재기동 후에도 `bob.connected = false`.
- 가설: 재연결 지연이 길다.
- 확인: `disconnect` 이유를 찍으니 `io server disconnect`.
- 원인: 서버가 `disconnectSockets()`로 **명시적으로** 끊으면 Socket.IO는 "의도된 종료"로 보고 자동 재연결하지 않는다. 배포 재시작(프로세스 종료)은 `transport close`라 재연결된다 — 실험이 실제 재시작을 잘못 흉내 냈다.
- 수정: 실험은 TCP를 직접 끊는 방식으로 변경. 설계에는 "서버가 끊는 경우(토큰 만료) 클라이언트가 수동 재연결"을 추가.
- 재발 방지: AC-CH-31에 클라이언트 동작까지 명시.

## JWT와 비밀번호 해시

**JWT는 `node:crypto`만으로 서명·검증해 보고, bcrypt는 비용·입력 한계·응답 시간을 측정했습니다.** 실험 코드는 [`spikes/auth/`](../spikes/auth/README.md)에 있고, 2026-11-10에 Node 22 · 샌드박스 환경에서 실행했습니다. 쿠키 `SameSite`와 CSRF의 브라우저 동작은 브라우저가 필요해 아직 확인하지 않았습니다.

### 1. 왜 필요한가

| 기술 | 없으면 |
| --- | --- |
| JWT | 요청마다 세션 테이블을 조회하거나, 서버가 사용자 식별값을 믿을 방법이 없다 |
| HMAC 서명 | 쿠키의 `sub`를 바꿔 다른 사람이 될 수 있다 |
| bcrypt (느린 해시 + salt) | DB가 유출되면 같은 비밀번호가 같은 해시로 보이고, 빠른 해시는 초당 수억 번 대입된다 |

### 2. 어떻게 동작하는가

- JWT는 `base64url(헤더).base64url(페이로드).base64url(HMAC-SHA256(앞 두 조각, 비밀))`입니다. 페이로드는 **암호화가 아니라 인코딩**이라 비밀 없이 누구나 읽습니다 — 이메일 · 권한 같은 정보를 넣지 않고 `sub` · `ver` · `exp`만 넣습니다.
- 검증은 같은 계산을 다시 해 서명을 비교하는 것입니다. 비교는 `timingSafeEqual`로 하고, 길이가 다르면 그 함수가 예외를 던지므로 길이를 먼저 봅니다.
- bcrypt 해시 `$2b$12$<salt 22자><해시 31자>`에는 cost와 salt가 들어 있어, 검증할 때 따로 저장한 값이 필요 없습니다. cost가 1 오르면 시간이 두 배가 됩니다.

### 3. 관찰

| 실험 | 관찰 | 설계에 준 것 |
| --- | --- | --- |
| 01 ③ 페이로드 변조 | `sub`를 바꾸고 서명을 그대로 두면 `서명 불일치` | — |
| 01 ④ `alg: none` | 헤더의 `alg`를 보고 검증 방식을 고르면 서명 없는 토큰이 통과할 수 있다. 서버가 `HS256` 하나만 허용하면 거부 | 라이브러리를 쓸 때도 `algorithms: ['HS256']`을 명시 |
| 01 ⑥ 다른 비밀 | 비밀이 바뀌면 모든 토큰이 `서명 불일치` | `JWT_SECRET`은 환경 변수로 고정, 없으면 부팅 실패 [CM-AU-10] |
| 01 ⑦ 비밀번호 변경 뒤의 옛 토큰 | 서명과 만료는 유효하다. 서명만으로는 못 막는다 | `ver === user.tokenVersion` 비교가 필요한 이유 |
| 01 ⑧ 소켓 토큰을 세션 자리에 | 같은 비밀로 서명했으므로 **통과한다** | 세션 토큰에 `purpose: session`을 넣고 검증기마다 자기 용도만 허용 — 명세에 추가 |
| 02 ① salt | 같은 비밀번호의 해시 두 개가 다르고 둘 다 검증 통과 | — |
| 02 ② cost별 시간 | 네이티브 `bcrypt`: 10 → 51ms, 11 → 103, 12 → 205, 13 → 409, 14 → 829. 순수 JS `bcryptjs`는 약 25% 느림 | cost 12가 목표(200~300ms) 안. 배포 환경에서 다시 측정 |
| 02 ③ 이벤트 루프 | cost 12 해시 4개 동시 실행 중 타이머 지연 — 네이티브 0ms, 순수 JS 394ms | **네이티브 `bcrypt`를 쓴다.** 순수 JS는 해시 동안 다른 요청과 소켓 하트비트가 멈춘다 |
| 03 ② 72바이트 한계 | 한글 34자(102바이트) 비밀번호 두 개가 앞 24자만 같으면 **서로의 해시로 검증된다** | "64자 이하" 규칙이 한계를 지키지 못함 → [T-12](troubleshooting.md#t-12) |
| 03 ③ 이모지 | 가족 이모지 3자가 75바이트 — 3자 뒤의 글자는 무시된다 | 같음 |
| 04 응답 시간 | 단순 구현: 있는 이메일 204ms · 없는 이메일 0ms. 더미 해시 비교: 204ms · 204ms | 없는 이메일도 더미 해시와 비교 [AC-LI-06] |

### 4. 이 프로젝트에서 쓰는 방식

| 항목 | 방식 |
| --- | --- |
| 서명 | HS256 하나만. 검증기가 알고리즘을 고정 |
| 페이로드 | `sub` · `ver` · `purpose`(`session` · `socket`) · `iat` · `exp` |
| 무효화 | `ver`를 DB의 `tokenVersion`과 비교 (요청마다 사용자 조회 1회) |
| 해시 | 네이티브 `bcrypt`, cost 12 (`BCRYPT_COST`로 조정) |
| 비밀번호 길이 | 8자 이상 64자 이하 **그리고** NFC 정규화 후 UTF-8 72바이트 이하 |
| 동시 로그인 | 해시는 libuv 스레드 풀(기본 4)에서 돈다. 동시에 5개째부터는 줄을 서므로, IP · 계정 rate limit이 그 위를 막는다 |

## PostgreSQL 제약과 트랜잭션

**동시에 도는 두 커넥션으로 명세의 경합 처리 다섯 가지를 재현했습니다.** 실험 코드는 [`spikes/postgres/`](../spikes/postgres/README.md)에 있고, 2026-11-10에 PostgreSQL 16.15 · 격리 수준 `READ COMMITTED`에서 실행했습니다. Prisma를 거치지 않고 `pg` 드라이버로 SQL을 직접 보냈습니다.

### 1. 왜 필요한가

단일 요청 테스트는 "먼저 조회하고 없으면 생성"도 통과시킵니다. 경합 처리는 두 트랜잭션의 순서를 손으로 조작해야만 맞는지 볼 수 있습니다.

### 2. 어떻게 동작하는가

- `READ COMMITTED`에서 각 **문장**은 시작 시점에 커밋된 데이터만 봅니다. 다른 트랜잭션이 잠근 행을 고치려 하면 기다렸다가, 잠금이 풀리면 `WHERE`를 **새 값으로 다시 평가**합니다.
- 유니크 인덱스에 같은 키를 넣으려는 두 번째 INSERT는 첫 번째의 커밋 · 롤백을 기다립니다. 커밋되면 `23505`로 실패합니다.
- `now()`는 트랜잭션 시작 시각, `clock_timestamp()`는 호출 시각입니다.

### 3. 관찰

| 실험 | 관찰 | 설계에 준 것 |
| --- | --- | --- |
| 01 ① 조회 후 생성 | 두 요청 모두 "방 없음"을 본다 | 유니크 제약이 최종 판단 [B03 원칙](architecture/backend.md#원칙) |
| 01 ③ ④ 유니크 경합 | 두 번째 INSERT는 첫 번째 커밋까지 **대기**, 커밋 직후 `23505` | T6의 "위반 → 기존 방 반환"이 성립 |
| 01 ⑦ 위반 뒤의 트랜잭션 | `23505`를 잡은 뒤 같은 트랜잭션의 다음 쿼리는 `25P02`(중단된 트랜잭션)로 실패 | 기존 행 재조회는 **트랜잭션을 끝낸 뒤 새 쿼리로** — 명세에 규칙 추가 [S-07](troubleshooting.md#s-07) |
| 01 ⑥ `ON CONFLICT DO NOTHING` | 0행 반환, 트랜잭션은 계속 쓸 수 있다 | 뒤에 다른 쓰기가 이어지는 T7의 `tempId` 중복은 사전 조회 + 방 행 잠금으로 처리(변경 없음) |
| 02 ① `now()` | 한 트랜잭션 안 200ms 간격에서 `now()` 변화 0ms, `clock_timestamp()` 201ms | [T-01](troubleshooting.md#t-01)의 전제 확인 |
| 02 ③ ④ 시각 커서 복구 | 먼저 시작해 늦게 커밋된 A가 `after = B` 조회에서 **0건** — DB에는 A가 있는데 영영 안 온다 | T-01을 실제로 재현 |
| 02 ⑤ serial id 커서 | A = 1, B = 2. 먼저 커밋된 B의 id가 더 커 `id > B`에서도 A가 빠진다 | 전역 시퀀스가 대안이 못 되는 이유 [결정 0016](decisions.md#0016--방-안-순서와-읽음-위치는-시각이-아니라-방별-번호seq로-센다) |
| 02 ⑥ 커서의 시각 정밀도 | DB 값 `46.351231`을 JS `Date`로 받으면 `46.351` — 그 값으로 `>` 조회하면 마지막으로 받은 행이 **다시 나온다** | 목록 커서 주의 [S-06](troubleshooting.md#s-06) |
| 03 ② ④ 방 행 잠금 | 두 번째 저장은 `UPDATE chat_room`에서 첫 번째 커밋까지 대기(304ms), 번호 1 → 2 | 번호 순서 = 커밋 순서 |
| 03 ③ 대기 중 조회 | 보이는 메시지 0건 — "먼저 커밋된 뒤 번호"가 생길 수 없다 | 복구 조회에 구멍이 없음 |
| 03 ⑥ 롤백 | 롤백된 번호 3을 다음 메시지가 다시 받는다 | 번호에 구멍이 없어 클라이언트의 틈 감지가 성립 |
| 03 ⑦ 다른 방 | 방 1이 잠긴 동안 방 2 저장 0ms | 방끼리는 서로 막지 않음 |
| 03 ⑧ 읽음 | 늦게 온 작은 번호는 무시(2 유지), 없는 큰 번호 999는 `last_seq`(3)에서 멈춤 | T8 |
| 04 ① 읽고 쓰기 | 두 탭 모두 "전이 가능"으로 보고 둘 다 성공 응답, 나중 것이 구매자를 덮어씀 | 쓰면 안 되는 방식 |
| 04 ② 조건부 UPDATE | 첫 번째 1행, 두 번째는 대기 후 **0행** | T4 · 0행이면 다시 읽어 `409` |
| 05 `FOR SHARE` | 잠금 없이 읽으면 삭제 커밋 전 값(살아 있음)을 보고 메시지를 저장. `FOR SHARE`는 삭제 커밋을 기다렸다가 "삭제됨"을 본다 | T7 ② |

### 4. 이 프로젝트에서 쓰는 방식

실험이 명세를 바꾼 곳은 둘입니다 — 유니크 위반 뒤의 재조회 위치(S-07)와 목록 커서의 시각 정밀도(S-06). 나머지는 [트랜잭션 경계](architecture/backend.md#03--트랜잭션-경계)의 설계가 그대로 성립함을 확인했습니다.

### 검증하지 못한 것

- Prisma 클라이언트를 거쳤을 때의 동작 — 인터랙티브 트랜잭션에서 `P2002`가 난 뒤의 상태, `$queryRaw`의 `FOR SHARE`. 구현 0단계의 통합 테스트로 확인합니다.
- 부분 유니크 인덱스(`WHERE deletedAt IS NULL`) — 1차 범위에서 쓰지 않아 미뤘습니다.
- 커넥션 풀이 가득 찼을 때 잠금 대기가 타임아웃(5초)과 만나는 지점.
