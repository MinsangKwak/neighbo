# 00 · 프로젝트 개요

[문서 목차](README.md) · 다음 문서: [경우의 수](cases/README.md) → [01 요구사항](01-requirements.md)

**neighbo는 이웃과 중고 물건을 거래하고 채팅으로 약속을 잡는 동네 거래 서비스입니다.** 당근마켓의 핵심 흐름을 열 가지 기능으로 좁혀, 명세 → 구현 → 검증 순서로 한 기능씩 끝까지 만듭니다. 기능을 많이 보여주는 것보다 **적은 기능이 빈 상태·에러·권한·동시성까지 빠짐없이 동작하는 것**을 목표로 합니다.

## 1. 목표

**이 프로젝트가 증명하려는 것은 "꼼꼼함"입니다.** 기능의 수가 아니라, 한 서비스가 실제 사용자를 만났을 때 깨지지 않는다는 근거를 문서와 코드로 남깁니다.

구체적으로 다음을 증명합니다.

| 증명할 것 | 어떻게 보이게 하는가 |
| --- | --- |
| 설계 능력 | 코드보다 먼저 쓴 공통 명세와 역할별 설계 문서. 결정과 이유가 남아 있음 |
| 완성도 | 모든 화면에 로딩 · 빈 상태 · 에러 상태가 정의되고 구현됨 |
| 권한 · 데이터 무결성 | "작성자만 삭제", "채팅방은 상품·구매자당 하나" 같은 규칙이 서버에서 강제됨 |
| 접근성 | 키보드만으로 모든 흐름 완료, 폼 오류는 스크린리더로 읽힘, 명암비 AA |
| 검증 | 요구사항의 수용 조건이 테스트 코드와 1:1로 대응 |
| 이력 추적 | 역할별 커밋과 PR 본문으로 변경 이유를 찾을 수 있음 |
| 기술 이해 | 핵심 기술마다 "왜 필요한가 · 어떻게 동작하는가 · 밑바닥 구현 · 겪은 문제의 원인"을 [기술 노트](tech/README.md)로 남김. 라이브러리를 쓰기 전에 그 라이브러리가 감추는 것을 한 번 직접 만든다 |
| 전체 그림 | 어떤 변경이 어느 테이블 · 어느 화면 · 어느 API에 닿는지 [지도](#2-지도--엔티티--프로세스--영향-범위)에서 읽을 수 있음 |
| 판단 근거 | 모든 아키텍처 결정은 [결정 기록](decisions/README.md)에 대안 · 트레이드오프 · 바뀔 가능성과 함께 남김 |

### 하지 않는 것

- 실제 운영 · 실사용자 유입. 데모 계정과 시드 데이터로 시연합니다.
- 당근마켓 UI의 픽셀 단위 복제. 흐름과 정보 구조를 참고하되 디자인은 직접 정합니다.
- 1차 범위 밖 기능을 "일단 넣어두기". 범위 밖은 범위 밖입니다.

## 2. 지도 — 엔티티 · 프로세스 · 영향 범위

**이 절은 서비스 전체를 한 장에 담은 지도입니다.** 어떤 요구사항이 들어와도 "어느 테이블 · 어느 화면 · 어느 API가 바뀌는가"를 여기서 먼저 찾고, 그 다음에 상세 문서로 내려갑니다. 지도가 틀리면 지도부터 고칩니다.

### 2.1 사용자와 핵심 시나리오

**사용자는 둘입니다 — 판매자와 구매자. 같은 사람이 두 역할을 오갑니다.** 관리자는 없습니다.

```
판매자: 회원가입 → 로그인 → 거래 등록 → (채팅 알림) → 채팅 → 거래 상태 변경(구매자 지정) → 마이페이지에서 확인
구매자: 회원가입 → 로그인 → 중고 목록 → 거래 상세 → 채팅 시작 → 채팅 → 마이페이지 구매 내역에서 확인
```

이 두 줄이 끝까지 끊기지 않고 동작하면 1차 범위는 완료입니다. 나머지(삭제, 알림 배지, 목록 갱신)는 이 흐름을 받치는 기능입니다.

### 2.2 핵심 엔티티와 핵심 필드

여섯 개면 서비스 전체가 설명됩니다. [백엔드 02 데이터 모델](backend/02-data-model.md)이 이 표를 Prisma 스키마 · 제약 · 인덱스로 옮긴 것입니다.

| 엔티티 | 한 줄 정의 | 핵심 필드 | 생명주기 |
| --- | --- | --- | --- |
| **User** | 가입한 사람. 판매자이자 구매자 | `email` `nickname` `avatarUrl` `tokenVersion` | 가입 → (탈퇴는 2차) |
| **Product** | 팔려고 올린 물건 하나 | `sellerId` `title` `price` `status` `buyerId` `deletedAt` | 등록 → 판매중 ⇄ 예약중 → 거래완료 → (삭제는 어느 상태에서든, soft) |
| **ProductImage** | 물건 사진. 순서 있음 | `productId` `url` `thumbnailUrl` `order` | 상품과 함께. 삭제 30일 후 파일 정리 |
| **ChatRoom** | 상품 하나 × 구매자 한 명의 방. 유니크 | `productId` `sellerId` `buyerId` `lastMessageAt` `lastMessagePreview` | 구매자가 [채팅하기] → 영구 |
| **ChatRoomMember** | 방 참여자의 읽음 위치 | `roomId` `userId` `lastReadAt` | 방 생성 시 두 행 |
| **Message** | 텍스트 한 줄 | `roomId` `senderId` `content` `tempId` `createdAt` | 전송 → 영구 (삭제 · 수정 없음) |

보조: **Upload** (상품에 연결되기 전 임시 파일, 24시간 후 정리). 1차에 **없는** 엔티티: Notification · Category · Favorite · Report · Review · Location. 없는 이유는 3절 "2차 이후" 표에.

### 2.3 핵심 업무 프로세스

| 프로세스 | 단계 | 걸치는 엔티티 | 규칙의 핵심 |
| --- | --- | --- | --- |
| **P1 물건 올리기** | 사진 업로드 → 상품 생성 → 목록 노출 | Upload → Product · ProductImage | 사진은 선택 즉시 업로드, 등록은 URL만 전송. 고아 업로드는 배치 정리 |
| **P2 거래 시작 (채팅)** | 상세 → [채팅하기] → 방 생성(또는 기존 방) → 첫 메시지 | Product → ChatRoom · ChatRoomMember → Message | 방은 `(productId, buyerId)` 유니크. 판매자는 자기 물건에 방을 못 만듦 |
| **P3 거래 마무리** | 판매자가 상태 변경 → 거래완료 시 구매자 지정 → 양쪽 마이페이지 반영 | Product(`status` `buyerId` `soldAt`) | 전이 표(05 상세) 밖의 전이는 `409`. 구매자는 채팅 상대 중에서만 |
| **P4 읽음과 알림** | 메시지 저장 → 방 `lastMessageAt` 갱신 → 수신자 배지 push → 방 입장 시 `lastReadAt` 갱신 | Message → ChatRoom → ChatRoomMember | 배지 = 읽지 않은 **방** 수. Notification 테이블 없음 |
| **P5 내리기** | 삭제 확인 → `deletedAt` → 목록 · 검색 제외, 채팅방은 열람만 | Product → (ChatRoom 표시만) | 항상 soft. 모든 Product 조회에 `deletedAt IS NULL` 자동 주입 |

### 1차 범위 (이번에 만드는 것)

| # | 기능 | 한 줄 정의 | 비고 |
| --- | --- | --- | --- |

| 7 | 채팅 목록 | 내가 참여한 채팅방을 최근 활동순으로 본다 | 읽지 않은 수 표시 |

| 9 | 마이페이지 | 내 정보 · 판매 목록(상태별) · 구매 내역 · 닉네임 · 아바타 · 비밀번호 변경 | 구매 내역은 [0012](decisions/0012-buyer-assignment.md) |
| 10 | 채팅 알림 | 새 메시지가 오면 탭 배지 · 목록 순서 · 토스트가 바뀐다 | 배지는 읽지 않은 방 수 ([0008](decisions/0008-badge-means-rooms.md)). 브라우저 푸시 없음 |

### 2차 이후 (지금은 만들지 않는 것)

| 기능 | 제외 이유 |

| 소셜 로그인 | OAuth 설정은 데모 가치가 낮고 비밀키 관리 부담 |

## 4. 기술 결정

**프론트와 백엔드를 한 저장소에 두고, 백엔드는 직접 짭니다.** BaaS(Firebase, Supabase)를 쓰면 권한 규칙 · 채팅방 유일성 · soft delete 같은 "꼼꼼함"이 설정 화면 뒤로 숨습니다. 직접 짜야 코드로 보여줄 수 있습니다.

2026-11-09 기준 아래 표는 모두 **확정**입니다. 각 결정의 대안과 트레이드오프는 [결정 기록](decisions/README.md)에, 기술 자체의 원리와 밑바닥 구현은 [기술 노트](tech/README.md)에 있습니다. 바꾸려면 새 결정 기록을 올리는 PR로 이유를 남깁니다.

표의 "바뀔 가능성"은 이 선택이 1차 범위 안에서 뒤집힐 확률이고, "바꾸면 닿는 곳"은 그때 고쳐야 하는 범위입니다. **바뀔 가능성이 높은데 닿는 곳이 넓은 것**이 가장 조심해야 할 결정이며, 그런 항목은 인터페이스 뒤에 숨겨 교체 비용을 줄입니다.

| 영역 | 결정 | 왜 필요한가 (없으면 무엇이 안 되나) | 바뀔 가능성 | 바꾸면 닿는 곳 |
| --- | --- | --- | --- | --- |
| 프론트엔드 | Next.js (App Router) + TypeScript | 목록 · 상세를 서버에서 렌더해 첫 화면과 OG 메타를 바로 제공. 없으면 SSR · 라우팅 · 이미지 리사이즈를 직접 조립 | 낮음 | 전부 |
| 스타일 | Tailwind CSS | 디자인 토큰을 `tailwind.config` 한 곳에 두고 05 컴포넌트 문서의 근거로 삼음. 임의 값(`w-[137px]`) 금지 | 낮음 | 모든 컴포넌트 |
| 백엔드 | Node.js + Express + TypeScript | 권한 · 트랜잭션 · 소켓을 **코드로** 보여주기 위해 BaaS 대신 직접. 미들웨어 체인으로 인증 → 검증 → 처리 → 에러의 순서가 드러남 | 낮음 | 서버 전부 |
| DB · ORM | PostgreSQL 16 + Prisma 7 (`prisma.config.ts` · `@prisma/adapter-pg`) — 로컬 Docker Compose · 운영 Railway | 유니크 제약(채팅방 · 이메일) · 트랜잭션(메시지 저장 + 방 갱신)이 데이터 무결성의 근거. 개발 · 운영 같은 엔진으로 동작 차이 제거 | 낮음 | 스키마 · 리포지토리 계층 |
| 인증 | 이메일 · 비밀번호 · bcrypt · JWT를 httpOnly 쿠키에 | 세션 테이블 없이 stateless. 쿠키라 JS가 토큰을 못 읽음(XSS 완화). `tokenVersion`으로 비밀번호 변경 시 무효화 | 중간 (리프레시 토큰 · 소셜 로그인) | 인증 미들웨어 · 로그인 · 소켓 핸드셰이크 |

| 실시간 | Socket.IO (WebSocket + 폴링 폴백) | 채팅 수신 · 읽음 동기화 · 배지 push가 같은 연결. 재연결 · 룸 · ack가 기본 제공 — 단, 그 아래의 WebSocket 핸드셰이크 · 하트비트 · 재연결은 [기술 노트](tech/README.md)에서 직접 만들어 본다 | 낮음 | 채팅 · 알림 · 소켓 서버 |

| 데이터 조회 (프론트) | TanStack Query | 캐시 · 재조회 · 낙관적 갱신 · 뒤로가기 복원을 한 규칙으로 | 낮음 | 모든 조회 훅 |
| 테스트 | 백엔드 API 통합 테스트(Vitest + supertest) · 프론트 컴포넌트(Testing Library) · E2E 핵심 시나리오 2개(Playwright) | 수용 조건과 1:1. 시나리오 커버가 기준 | 낮음 | — |
| 배포 | 프론트 Vercel · 백엔드 Railway | GitHub 연결 자동 배포, Postgres 원클릭, WebSocket · 상시 실행. 환경 매핑은 [브랜치 · 배포 전략](dev/BRANCHING.md) | 중간 | 환경 변수 · 워크플로 |

### 의존성 추가 규칙

**1차 범위의 의존성은 위 표로 닫혀 있습니다.** 새 라이브러리는 다음 셋을 적은 [결정 기록](decisions/README.md) 없이는 추가하지 않습니다.

1. 기존 구조로 해결하기 어려운 **구체적인** 이유 (예: "날짜 포맷이 필요해서"는 이유가 아님 — `Intl.DateTimeFormat`이 있음)
2. 그 라이브러리가 **감추는 것**이 무엇인지 (한 문단으로 설명할 수 없으면 아직 쓸 때가 아님)
3. 빼게 되면 닿는 곳

유틸리티 하나 때문에 패키지를 넣지 않습니다. 20줄로 쓸 수 있으면 씁니다.

### 아직 열린 것

없습니다. 구조를 가르는 결정은 [결정 기록](decisions/README.md)에, 세부 결정은 [경우의 수](cases/README.md)에서 모두 닫았습니다. 확인받지 못한 채 내린 판단은 [검토 요청](review-queue.md)에 모아 둡니다.

## 5. 폴더 구조 (제안)

**폴더 이름은 예시입니다.** 저장소를 처음 여는 사람에게 역할이 한눈에 보이는 것이 기준이며, 코드 시작 전에 확정합니다.

```
neighbo/
├─ README.md              # 소개 · 역할별 입구 · 문서 링크
├─ frontend-next/         # 프론트엔드 (예시 이름) — README가 프론트 설계 문서의 입구
├─ backend-node/          # 백엔드 (예시 이름) — README가 백엔드 설계 문서의 입구
├─ spikes/                # 기술 스파이크 (운영 코드 아님)
├─ docs/
│  ├─ README.md           # 문서 목차
│  ├─ 00-overview.md
│  ├─ 01-requirements.md  # 수용 조건마다 프론트 · 백엔드 역할이 나뉨
│  ├─ cases/              # 기능별 경우의 수 (01의 입력)
│  ├─ frontend/           # 프론트 설계 — 렌더링 · 상태 · 캐시 · 에러 · 폼 · 포커스 · 소켓 클라이언트 (+ 화면 명세 · 컴포넌트 예정)
│  ├─ backend/            # 백엔드 설계 — 계층 · 데이터 모델 · 트랜잭션 · 권한 · 멱등성 · 에러 코드 · 보호 · 로그 · 소켓 서버 · API 명세
│  ├─ decisions/          # 결정 기록 — 대안 · 트레이드오프 · 바뀔 가능성
│  ├─ tech/               # 기술 노트 — 원리 · 밑바닥 구현 · 겪은 문제
│  ├─ dev/                # 커밋 규칙 · 브랜치 · 배포 전략
│  └─ review-queue.md     # 검토 요청
└─ .github/               # 워크플로 · PR 템플릿 (코드 단계에서 추가)
```

**문서를 역할별로 나눈 이유**: 같은 요구사항을 프론트와 백엔드가 각자 다르게 고민합니다. "두 번 눌러도 채팅방은 하나"는 프론트에선 버튼 잠금과 응답 처리, 백엔드에선 유니크 제약과 충돌 시 기존 방 반환입니다. 기능 단위 문서(01)만 있으면 이 차이가 한 문장에 묻히므로, 역할 단위 문서로 같은 내용을 다시 꿰어 각 역할의 판단 근거를 드러냅니다. 처음 계획한 02~06 문서는 역할 폴더로 흡수했습니다 — 02 데이터 모델 · 04 API는 `docs/backend/`, 03 화면 · 05 컴포넌트는 `docs/frontend/`, 06 규칙은 각 역할 문서와 `dev/`.

이름 후보: `frontend-next` / `backend-node` (기술 스택이 이름에 보임) 또는 `web` / `server` (커밋 범위와 같은 낱말). 둘 중 하나로 확정하면 커밋 규칙의 범위 표에 실제 경로를 적습니다.

1. 폴더 이름 확정 → 커밋 규칙 범위 표 갱신

4. 기능 1번(회원가입)부터 순서대로 — 기능 하나 = 브랜치 하나 = PR 하나
5. 각 PR에 수용 조건 체크리스트와 검증 결과 첨부
6. 기능 묶음마다 **워크스루** — 두 계정(판매자 · 구매자)으로 2.1의 두 시나리오를 처음부터 끝까지 직접 쓴다. 어긋난 곳은 이슈로

## 7. 품질 기준

**아래 항목은 "있으면 좋은 것"이 아니라 각 기능의 완료 조건입니다.** 01 요구사항의 수용 조건에 기능별로 구체화합니다.

| 영역 | 기준 |
| --- | --- |
| 상태 | 모든 데이터 화면은 로딩 · 빈 목록 · 에러 세 상태의 UI가 정의되어 있다 |
| 권한 | 소유자 검사는 서버에서 한다. 프론트의 버튼 숨김은 편의이고 보안이 아니다 |
| 입력 검증 | 프론트와 서버가 같은 스키마로 검증한다. 서버 검증 실패는 필드별 메시지로 돌아온다 |
| 접근성 | 키보드만으로 열 가지 기능을 완료할 수 있다. 폼 오류는 `aria-describedby`로 연결된다. 명암비 WCAG AA |
| 반응형 | 모바일(360px) 우선, PC(1024px 이상)에서도 깨지지 않는다 |
| 동시성 | 채팅방 생성 · 거래 상태 변경은 중복 요청에도 한 번만 반영된다 |
| 테스트 | 수용 조건마다 대응하는 테스트가 있다. 테스트 이름은 수용 조건 문장을 그대로 쓴다 |
| 문서 | 코드가 문서와 다르면 같은 PR에서 문서를 고친다 |
| 원인 노트 | 버그를 고칠 때 "무엇을 고쳤다"가 아니라 **"왜 생겼다"**를 남긴다. 증상 → 가설 → 확인 방법 → 원인 → 수정 → 재발 방지. [기술 노트](tech/README.md)의 해당 기술 아래에 쌓는다 |
| 영향 범위 | 변경 PR은 2.4 매트릭스의 해당 행을 인용하고, 표시된 열을 모두 확인했음을 적는다 |
