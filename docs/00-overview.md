# 00 · 프로젝트 개요

[문서 목차](README.md) · 다음 문서: 01 요구사항 (예정)

**neighbo는 이웃과 중고 물건을 거래하고 채팅으로 약속을 잡는 동네 거래 서비스입니다.** 당근마켓의 핵심 흐름을 열 가지 기능으로 좁혀, 명세 → 구현 → 검증 순서로 한 기능씩 끝까지 만듭니다. 기능을 많이 보여주는 것보다 **적은 기능이 빈 상태·에러·권한·동시성까지 빠짐없이 동작하는 것**을 목표로 합니다.

| 항목 | 내용 |
| --- | --- |
| 저장소 | `github.com/MinsangKwak/neighbo` |
| 상태 | 명세 작성 중 (2026-11-09 시작) |
| 1차 범위 | 로그인 · 회원가입 · 중고 목록 · 거래 등록 · 거래 상세 · 거래 삭제 · 채팅 목록 · 채팅 · 마이페이지 · 채팅 알림 |
| 작업 방식 | 문서 먼저 (00 → 06), 문서가 끝난 뒤 코드 시작 |

## 1. 목표

**이 프로젝트가 증명하려는 것은 "꼼꼼함"입니다.** 기능의 수가 아니라, 한 서비스가 실제 사용자를 만났을 때 깨지지 않는다는 근거를 문서와 코드로 남깁니다.

구체적으로 다음을 증명합니다.

| 증명할 것 | 어떻게 보이게 하는가 |
| --- | --- |
| 설계 능력 | 코드보다 먼저 쓴 명세 문서 7개. 결정과 이유가 남아 있음 |
| 완성도 | 모든 화면에 로딩 · 빈 상태 · 에러 상태가 정의되고 구현됨 |
| 권한 · 데이터 무결성 | "작성자만 삭제", "채팅방은 상품·구매자당 하나" 같은 규칙이 서버에서 강제됨 |
| 접근성 | 키보드만으로 모든 흐름 완료, 폼 오류는 스크린리더로 읽힘, 명암비 AA |
| 검증 | 요구사항의 수용 조건이 테스트 코드와 1:1로 대응 |
| 이력 추적 | 역할별 커밋과 PR 본문으로 변경 이유를 찾을 수 있음 |

### 하지 않는 것

- 실제 운영 · 실사용자 유입. 데모 계정과 시드 데이터로 시연합니다.
- 당근마켓 UI의 픽셀 단위 복제. 흐름과 정보 구조를 참고하되 디자인은 직접 정합니다.
- 1차 범위 밖 기능을 "일단 넣어두기". 범위 밖은 범위 밖입니다.

## 2. 사용자와 핵심 시나리오

**사용자는 둘입니다 — 판매자와 구매자. 같은 사람이 두 역할을 오갑니다.**

```
판매자: 회원가입 → 로그인 → 거래 등록 → (채팅 알림) → 채팅 → 거래 상태 변경 → 마이페이지에서 확인
구매자: 회원가입 → 로그인 → 중고 목록 → 거래 상세 → 채팅 시작 → 채팅 → 마이페이지에서 확인
```

이 두 줄이 끝까지 끊기지 않고 동작하면 1차 범위는 완료입니다. 나머지(삭제, 알림 배지, 목록 갱신)는 이 흐름을 받치는 기능입니다.

## 3. 범위

### 1차 범위 (이번에 만드는 것)

| # | 기능 | 한 줄 정의 | 비고 |
| --- | --- | --- | --- |
| 1 | 회원가입 | 이메일 · 비밀번호 · 닉네임으로 계정을 만든다 | 휴대폰 인증 없음 |
| 2 | 로그인 | 이메일 · 비밀번호로 로그인하고 세션을 유지한다 | 로그아웃 포함 |
| 3 | 중고 목록 | 판매중 · 예약중 상품을 최신순으로 본다 | 무한 스크롤 또는 페이지, 01에서 결정 |
| 4 | 거래 등록 | 제목 · 가격 · 설명 · 사진으로 상품을 올린다 | 사진 최대 장수 01에서 결정 |
| 5 | 거래 상세 | 상품 정보와 판매자, 상태를 보고 채팅을 시작한다 | 판매자 본인은 수정 · 삭제 · 상태 변경 |
| 6 | 거래 삭제 | 작성자가 자기 상품을 내린다 | 채팅방이 있으면 soft delete |
| 7 | 채팅 목록 | 내가 참여한 채팅방을 최근 메시지순으로 본다 | 읽지 않은 수 표시 |
| 8 | 채팅 | 1:1 실시간 메시지를 주고받는다 | 텍스트만, 이미지 전송 없음 |
| 9 | 마이페이지 | 내 정보 · 판매 목록 · 거래 상태별 필터 | 프로필 사진 변경은 2차 |
| 10 | 채팅 알림 | 새 메시지가 오면 상단 배지와 목록 순서가 바뀐다 | 브라우저 푸시 없음, 앱 안에서만 |

### 2차 이후 (지금은 만들지 않는 것)

| 기능 | 제외 이유 |
| --- | --- |
| 결제 · 송금 | PG 연동은 범위 밖. 거래는 "직접 만나서"가 전제 |
| 위치 기반 검색 · 동네 인증 | 지도 API와 GPS 권한이 필요하고, 1차 목표(흐름 완성)와 무관 |
| 관심(찜) · 끌어올리기 | 있으면 좋지만 핵심 흐름이 아님 |
| 신고 · 차단 · 리뷰 | 운영 기능. 실사용자가 없는 단계에서는 검증 불가 |
| 이미지 메시지 · 파일 전송 | 채팅은 텍스트로 흐름을 완성한 뒤 확장 |
| 브라우저 푸시 알림 | Service Worker · 권한 UX가 별도 주제 |
| 소셜 로그인 | OAuth 설정은 데모 가치가 낮고 비밀키 관리 부담 |

## 4. 기술 결정

**프론트와 백엔드를 한 저장소에 두고, 백엔드는 직접 짭니다.** BaaS(Firebase, Supabase)를 쓰면 권한 규칙 · 채팅방 유일성 · soft delete 같은 "꼼꼼함"이 설정 화면 뒤로 숨습니다. 직접 짜야 코드로 보여줄 수 있습니다.

2026-11-09 기준 아래 표는 모두 **확정**입니다. 바꾸려면 이 문서를 고치는 PR로 이유를 남깁니다.

| 영역 | 결정 | 이유 |
| --- | --- | --- |
| 프론트엔드 | Next.js (App Router) + TypeScript | 라우팅 · 서버 컴포넌트 · 이미지 최적화를 기본 제공. 생태계와 문서가 가장 넓음 |
| 스타일 | Tailwind CSS | 디자인 토큰을 `tailwind.config`에 모아 05 컴포넌트 문서의 근거로 삼는다. 임의 값(`w-[137px]`)은 금지하고 토큰만 쓴다 |
| 백엔드 | Node.js + Express + TypeScript | 프론트와 언어 통일. 미들웨어로 인증 · 권한 · 에러 처리 계층을 명시적으로 보여줄 수 있음 |
| DB · ORM | PostgreSQL + Prisma — 로컬은 Docker Compose, 배포는 Railway Postgres | 개발 · 운영 DB를 같은 엔진으로 두어 "로컬에선 되는데" 류의 버그를 차단. Prisma 스키마가 그대로 02 데이터 모델 문서의 근거가 됨 |
| 인증 | 이메일 · 비밀번호, JWT를 httpOnly 쿠키에 저장, bcrypt | localStorage JWT는 XSS에 노출. 세션 테이블 없이 stateless로 단순하게 |
| 실시간 | Socket.IO | 채팅 · 알림 두 기능이 같은 연결을 공유. 재연결 · 룸 · 끊김 감지가 기본 제공. 04 API 문서에서 Socket 이벤트를 REST와 같은 수준으로 명세 |
| 이미지 저장 | 로컬 디스크 (개발) → S3 호환 스토리지 (운영) | 저장 경로를 인터페이스 하나로 추상화해 두 환경을 같은 코드로 |
| 검증 | Zod 스키마를 프론트 · 백엔드가 공유 | 같은 규칙을 두 번 쓰지 않음 |
| 테스트 | 백엔드: API 통합 테스트 · 프론트: 컴포넌트 테스트 + E2E 핵심 시나리오 2개(판매자 흐름 · 구매자 흐름) | 수용 조건과 1:1 대응이 목표. 단위 테스트 수가 아니라 시나리오 커버가 기준 |
| 배포 | 프론트 Vercel · 백엔드 Railway | GitHub 연결만으로 자동 배포, Postgres 원클릭, WebSocket 지원, 콜드 스타트 없음. 환경 매핑은 [브랜치 · 배포 전략](dev/BRANCHING.md) |

## 5. 폴더 구조 (제안)

**폴더 이름은 예시입니다.** 저장소를 처음 여는 사람에게 역할이 한눈에 보이는 것이 기준이며, 코드 시작 전에 확정합니다.

```
neighbo/
├─ README.md              # 소개 · 문서 링크 · 실행 방법
├─ docs/                  # 명세 (이 문서들)
│  ├─ README.md           # 문서 목차
│  ├─ 00-overview.md
│  ├─ 01-requirements.md
│  ├─ 02-data-model.md
│  ├─ 03-screens.md
│  ├─ 04-api.md
│  ├─ 05-components.md
│  ├─ 06-conventions.md
│  └─ dev/
│     └─ COMMITS.md       # 커밋 규칙
├─ frontend-next/         # 프론트엔드 (예시 이름)
├─ backend-node/          # 백엔드 (예시 이름)
└─ .github/               # 워크플로 · PR 템플릿 (코드 단계에서 추가)
```

이름 후보: `frontend-next` / `backend-node` (기술 스택이 이름에 보임) 또는 `web` / `server` (커밋 범위와 같은 낱말). 둘 중 하나로 확정하면 커밋 규칙의 범위 표에 실제 경로를 적습니다.

## 7. 품질 기준

**아래 항목은 "있으면 좋은 것"이 아니라 각 기능의 완료 조건입니다.** 01 요구사항의 수용 조건에 기능별로 구체화합니다.

| 영역 | 기준 |
| --- | --- |
| 상태 | 모든 데이터 화면은 로딩 · 빈 목록 · 에러 세 상태의 UI가 정의되어 있다 |
| 권한 | 소유자 검사는 서버에서 한다. 프론트의 버튼 숨김은 편의이고 보안이 아니다 |
| 입력 검증 | 프론트와 서버가 같은 스키마로 검증한다. 서버 검증 실패는 필드별 메시지로 돌아온다 |
| 접근성 | 키보드만으로 열 가지 기능을 완료할 수 있다. 폼 오류는 `aria-describedby`로 연결된다. 명암비 WCAG AA |
| 반응형 | 모바일(360px) 우선, PC(1024px 이상)에서도 깨지지 않는다 |
| 동시성 | 채팅방 생성 · 거래 상태 변경은 중복 요청에도 한 번만 반영된다 |
| 테스트 | 수용 조건마다 대응하는 테스트가 있다. 테스트 이름은 수용 조건 문장을 그대로 쓴다 |
| 문서 | 코드가 문서와 다르면 같은 PR에서 문서를 고친다 |

## 8. 용어

| 용어 | 뜻 |
| --- | --- |
| 상품 (Product) | 거래 등록으로 올린 글 하나. "거래", "게시글"과 같은 뜻으로 쓰되 코드와 문서에서는 Product로 통일 |
| 거래 상태 | 상품의 상태. `판매중` · `예약중` · `거래완료` 세 값 |
| 채팅방 (ChatRoom) | 상품 하나에 대한 판매자 · 구매자 1:1 방. 같은 상품 · 같은 구매자 조합은 하나만 존재 |
| 알림 | 새 메시지 도착을 앱 안에서 알리는 것. 브라우저 푸시가 아님 |
| soft delete | 행을 지우지 않고 `deletedAt`을 기록해 목록에서 숨기는 것 |
