# 프론트 07 · 소켓 클라이언트

[프론트엔드 설계](README.md) · 앞: [06 포커스](06-focus.md) · 근거: [WebSocket 기술 노트](../tech/websocket.md) · 서버 쪽: [백엔드 09 소켓 서버](../backend/09-socket-server.md)

**클라이언트는 연결 상태를 표시하고, 전송 대기 메시지를 보관하며, 재연결 후 누락 데이터를 복구하도록 설계했습니다.** Socket.IO의 재연결 기능과 서비스의 전송 재시도·DB 커서 복구를 구분합니다. 연결·버퍼 동작의 확인 범위는 [WebSocket 스파이크](../tech/websocket.md)에 기록했습니다.

## 1. 연결 상태 기계

```
           로그인됨                 연결 성공
  idle ──────────────▶ connecting ───────────▶ connected ◀─────────────┐
   ▲                       ▲                      │                    │
   │ 로그아웃               │ 토큰 받고 재시도       │ transport close     │ 재연결 성공
   │                       │                      ▼                    │ (+ 복구 절차)
   │                       └──────────────── reconnecting ─────────────┘
   │                                              │
   │                         connect_error         │ disconnect 이유 = io server disconnect
   │                         UNAUTHORIZED          ▼   (토큰 만료로 서버가 끊음)
   └─────────────────────────────────────── needs_login ── 재로그인 화면
```

| 상태 | 화면 | 전송 버튼 | 근거 |
| --- | --- | --- | --- |
| `connecting` · `connected` | 아무것도 없음 | 보냄 | |
| `reconnecting` (5초 미만) | 아무것도 없음 — 짧은 끊김에 경고를 띄우면 깜빡임만 | 대기열로 | AC-CH-39 |
| `reconnecting` (5초 이상) | 상단 얇은 바 "실시간 연결이 끊겼어요. 다시 연결 중…" (`role="status"`) | 대기열로 | AC-CH-39 |
| `needs_login` | 재로그인 화면 (`next` = 현재 경로) | — | AC-CH-31 |

**`needs_login`이 따로 있는 이유**: 서버가 직접 끊으면 Socket.IO는 자동 재연결을 하지 않는다([스파이크 ⑤](../tech/websocket.md)). `disconnect` 이유를 보지 않으면 클라이언트는 영원히 `reconnecting`처럼 보이는 채 멈춘다.

## 2. 연결 하나, 탭 하나

| 결정 | 이유 |
| --- | --- |
| 탭당 소켓 하나, `SocketContext`가 소유 | 화면마다 연결하면 이동할 때마다 끊고 다시 붙는다 |
| 로그인 상태에서만 연결 | 비로그인 사용자는 실시간이 필요 없다 [AC-NT-10] |
| 토큰은 연결 · 재연결마다 새로 | `auth: (cb) => fetch('/api/auth/socket-token').then(r => r.json()).then(({ token }) => cb({ token }))` — 60초 토큰이 재연결 때 만료돼 있지 않게 [AC-LI-18a] |
| 방 조인은 채팅방 화면이 마운트될 때, 나갈 때 `room:leave` | 열려 있는 방만 조인 — 서버가 보내는 이벤트를 줄인다 |
| 조인한 방 목록을 컨텍스트가 기억 | 재연결 시 다시 조인해야 한다 (서버 메모리는 재시작으로 사라짐) |

## 3. 메시지 보내기

```
[전송] ─▶ tempId 생성 · 대기열에 { status: 'sending' } ─▶ 연결됨?
                                                         ├─ 예 ─▶ emitWithAck(5초)
                                                         │         ├─ ok    ─▶ 대기열에서 제거 · 캐시에 추가
                                                         │         ├─ 거절  ─▶ status: 'failed' (코드별 문구)
                                                         │         └─ 타임아웃 ▶ status: 'failed'
                                                         └─ 아니오 ▶ status: 'queued' ("연결 중…")
                                                                    ├─ 재연결 ─▶ 순서대로 emitWithAck (같은 tempId)
                                                                    └─ 30초 경과 ▶ status: 'failed'
[재시도] ─▶ 같은 tempId로 다시 ─ 서버가 이미 저장했으면 기존 메시지를 ack로 돌려줌 (중복 없음)
[삭제]   ─▶ 대기열에서 제거 (서버에 보내지 않음)
```

| 규칙 | 이유 | 근거 |
| --- | --- | --- |
| **`socket.emit` 직접 호출 금지**, `emitWithAck(event, payload, 5000)`만 | 타임아웃 없이 보내면 끊긴 동안 버퍼에 남았다가 재연결 후 몰래 전송된다 — 화면엔 실패, 상대에겐 도착 (스파이크 ⑤ 실험 6) | AC-CH-37 |
| 끊긴 상태에선 emit하지 않고 **별도 전송 대기열**에 | Socket.IO 내부 버퍼의 동작(타임아웃 시 제거, 없으면 유지)에 기대지 않는다. 별도 전송 대기열에서 상태를 관리해 화면에 표시한다 | AC-CH-38 |
| 재시도는 같은 `tempId` | "보낸 줄 알았는데 서버엔 없음"과 "서버엔 있는데 ack만 못 받음"을 클라이언트는 구분할 수 없다. 같은 `tempId`면 둘 다 안전 | AC-CH-04 |
| 실패한 말풍선을 지우지 않음 | 쓴 글을 잃게 하지 않는다 | AC-CH-04 |
| 대기열 순서대로 하나씩, **200ms 간격** | 앞 메시지보다 뒤 메시지가 먼저 저장되면 대화 순서가 뒤집힌다. 간격은 서버 전송 한도(초당 5)에 맞춘 것 | AC-CH-33 |
| 대기 메시지가 `RATE_LIMITED`를 받으면 실패가 아니라 대기 | 사용자가 잘못한 것이 아니다. `retryAfterMs` 뒤 같은 `tempId`로 다시 | AC-CH-33 |

**lint로 막기**: ESLint `no-restricted-syntax`로 `socket.emit(` 패턴을 `emitWithAck` 파일 밖에서 금지한다. 규칙은 문서보다 도구가 지킨다.

## 4. 다시 붙었을 때 — 복구 절차

순서가 중요하다. 받기를 먼저 끝내고 보내기를 한다 — 그래야 대기열의 메시지가 놓친 메시지들 **뒤에** 저장된다.

| 순서 | 처리 | 근거 |
| --- | --- | --- |
| 1 | 조인했던 방마다 `room:join { roomId, after: 캐시의 마지막 seq }` | AC-CH-05 |
| 2 | 응답 `missed`를 캐시에 합침 (같은 `seq` 무시), `hasMore`면 HTTP로 나머지 | AC-CH-05 |
| 3 | 대기열(`queued`)을 순서대로 전송 | AC-CH-38 |
| 4 | `['me', 'unread']` · `['chatRooms']` · 열린 방의 `['chatRoom', id]` 무효화 — 끊긴 동안의 변화 | AC-NT-13, AC-CL-11 |
| 5 | 보고 있는 방이 있으면 `room:read` | AC-CH-01 |
| — | 끊긴 동안 온 메시지의 토스트는 띄우지 않음 | AC-NT-13 |

### 연결 중에 생긴 틈

연결이 살아 있어도 `message:new` 하나가 빠질 수 있다 — 서버 emit 실패, 조인 직전 커밋 등. 방마다 받은 마지막 `seq`를 기억하고, 새로 온 메시지의 `seq`가 **마지막 + 1이 아니면** 그 자리에서 `room:join { after: 마지막 }`으로 채운다. 번호가 연속이므로 "빠졌다"를 클라이언트가 스스로 안다 — 시각 커서로는 불가능했던 일이다 [결정 0016].

### 읽음은 그린 번호로

`room:read`에는 **화면에 실제로 그린** 마지막 메시지의 `seq`를 싣는다. 받기만 하고 아직 그리지 않은 메시지(가상 스크롤 밖, 렌더 전)를 읽음으로 올리지 않기 위해서다 [AC-CH-01].

## 5. 탭이 숨겨졌다 돌아올 때

모바일 브라우저는 백그라운드 탭의 소켓을 끊기도 한다(언제 끊는지는 실기기 확인 필요 — [websocket.md 4절 "검증하지 못한 것"](../tech/websocket.md)).

| 순간 | 처리 | 근거 |
| --- | --- | --- |
| 숨겨짐 | 소켓은 그대로. 토스트는 띄우지 않고 배지 · 탭 제목 `(N)`만 갱신 | AC-NT-14 |
| 보임 | 끊겨 있으면 `socket.connect()` → 4절 복구. 연결돼 있어도 `['me', 'unread']` 재조회. 방을 보고 있으면 `room:read` | AC-CH-01, AC-NT-04 |
| 돌아왔을 때 | 밀린 토스트를 몰아서 띄우지 않음 | AC-NT-14 |

## 6. 이벤트 → 화면

캐시 갱신 규칙은 [03 캐시](03-cache.md#소켓-이벤트--캐시). 화면 쪽 반응만:

| 이벤트 | 화면 반응 |
| --- | --- |
| `message:new` (보는 방) | 아래 100px 이내면 자동 스크롤, 아니면 [새 메시지 ↓] · 라이브 리전 · `room:read` [AC-CH-14] |
| `message:new` (다른 화면) | 토스트 (채팅 목록 · 그 방이 아닐 때, 5초 내 같은 방은 합침) [AC-NT-05, 06] |
| `room:read` (상대) | 상대 `lastReadSeq` ≥ 내 마지막 메시지 `seq`면 그 아래 "읽음" [AC-CH-02] |
| `room:product_updated` (삭제) | 입력창 비활성 + "삭제된 물건이라 메시지를 보낼 수 없어요" [AC-CH-41] |
| ack `RATE_LIMITED` | `retryAfterMs` 동안 [전송] 비활성 + "잠시 후 보낼 수 있어요". 쓰던 글과 대기 메시지는 그대로 [AC-CH-33] |
