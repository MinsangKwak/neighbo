## 설계 판단

### 1. 사용자별 데이터를 서버에서 그릴 때의 캐시 사고

Next.js 서버 컴포넌트의 `fetch`는 설정에 따라 결과를 서버에 저장해 다음 요청에 재사용할 수 있다. 상세 페이지 응답에는 `viewer.isSeller`가 들어 있는데, 이게 저장되면 **판매자 본인이 본 화면(수정 · 삭제 메뉴)이 다른 사람에게 보인다.**

| 규칙 | 방법 |
| --- | --- |
| 백엔드 호출은 전부 `cache: 'no-store'` | 서버용 API 함수 `serverFetch()` 한 곳에서 강제 — 개별 호출이 잊을 수 없게 |
| 쿠키를 백엔드로 전달 | `serverFetch()`가 `cookies()`를 읽어 `Cookie` 헤더로 |
| 백엔드가 준 `Set-Cookie`는 **버린다** | 서버 컴포넌트는 렌더 중에 쿠키를 쓸 수 없다. 쿠키 연장 · 삭제는 브라우저가 부르는 `/api/*` 프록시 응답에서만 일어나고, 로그인 상태의 화면은 모두 배지용 `/api/me/unread`를 부르므로 연장이 빠지지 않는다 [AC-CM-03] |
| 인증 화면 응답 헤더 | `Cache-Control: no-store` (로그아웃 후 뒤로가기로 보호 화면이 보이지 않게 [AC-LI-13]) |

이 사고를 일부러 재현해 보는 것이 [기술 노트](../tech/README.md) `nextjs-app-router.md`의 스파이크 ②다.

### 2. 서버 데이터를 클라이언트 캐시로 넘기기

서버에서 가져온 첫 페이지를 클라이언트가 다시 요청하면 낭비고, 그렇다고 서버 데이터를 props로만 내리면 [더 보기] · 뒤로가기 복원 · 소켓 갱신이 그 데이터와 따로 논다. 그래서:

```
서버 컴포넌트: queryClient.prefetchInfiniteQuery(['products', filters])
             → dehydrate(queryClient)
클라이언트:   <HydrationBoundary state={...}> → useInfiniteQuery(['products', filters])  // 같은 키, 요청 없음
```

서버와 클라이언트가 **같은 캐시 키**를 쓴다. 키 목록은 [03 캐시](03-cache.md).

### 3. 보호 페이지 — 두 겹의 확인

| 겹 | 어디서 | 확인하는 것 | 못 하는 것 |
| --- | --- | --- | --- |
| 1 | `proxy.ts` (Next.js 16에서 `middleware.ts`가 이름을 바꾼 것, Node 런타임) | 세션 쿠키가 **있는가** — 없으면 즉시 `/login?next=` | 토큰이 유효한지 (DB의 `tokenVersion`을 모른다) |
| 2 | 페이지 서버 컴포넌트 | `serverFetch('/me')` → `401`이면 `redirect('/login?next=')` | — |

1겹만 있으면 만료 · 무효 토큰이 통과하고, 2겹만 있으면 비로그인 사용자도 페이지 렌더를 시작했다가 돌아간다. 1겹은 빠른 길, 2겹이 진짜 판단 [AC-CM-01]. 로그인 · 가입 화면은 반대로 쿠키가 있으면 홈으로 [AC-CM-05].

### 4. 채팅방 첫 화면과 소켓의 연결

서버가 준 최신 50개의 마지막 메시지 `seq`를 소켓 `room:join`의 `after`로 넘긴다. 서버 렌더와 소켓 조인 사이(수백 ms)에 온 메시지가 빠지지 않는다. 서버 렌더가 없으면 "빈 화면 → HTTP 로드 → 조인" 순서가 되어 깜빡임과 같은 틈이 생긴다.
