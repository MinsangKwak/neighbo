# 결정 기록

[문서 목차](README.md)

**결정 기록은 구조에 영향을 주는 선택과 대안, 제약, 재검토 조건을 정리합니다.** 기능 범위나 운영 조건이 바뀔 때 기존 판단의 전제를 확인하고 변경 범위를 찾는 데 사용합니다.

## 언제 쓰는가

다음 중 하나면 결정 기록을 씁니다.

- 개요 2.4 변경 영향 매트릭스에서 **열이 3개 이상**인 결정
- 새 의존성 추가 (개요 "의존성 추가 규칙")
- 데이터 모델의 유니크 제약 · 삭제 정책 · 상태 기계처럼 **되돌리기 어려운** 것
- 두 사람이 다르게 판단할 수 있는 것 (한 가지 답만 있으면 기록하지 않음)

입력 길이 · 문구 · 색처럼 바꾸는 데 한 줄이면 되는 것은 [경우의 수](features/00-common.md#경우의-수-표기) 표 안에서 끝냅니다.

## 트레이드오프

## 0001 · 인증·거래·채팅 로직은 별도 백엔드에서 관리한다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 서버 전부 · 인증 · 데이터 모델 · 배포 |

**Node.js·Express·Prisma로 백엔드를 구성하고, 권한·트랜잭션·실시간 처리를 서비스 계층에서 관리합니다.** PostgreSQL의 제약과 애플리케이션 처리 순서를 함께 정의할 수 있도록 선택했습니다.

### 맥락

작성자만 상품을 변경할 수 있어야 하고, 같은 상품·구매자 조합에는 채팅방이 하나만 있어야 합니다. 메시지 저장과 채팅방 갱신은 함께 성공해야 하며, 저장된 메시지는 실시간으로 전달되어야 합니다. 이 동작을 관리할 계층과 배포 구성을 정해야 합니다.

### 선택

인증 미들웨어, 입력 검증, 서비스의 권한·트랜잭션 처리, 응답·오류 처리를 분리합니다. 소켓 이벤트도 HTTP와 같은 서비스 함수를 호출하도록 설계합니다. 기술별 실험 결과와 적용 계획은 [기술 노트](tech-notes.md)에 기록합니다.

### 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| Supabase | PostgreSQL 기반 인증·실시간·파일 기능 제공 | 이번 설계는 권한·거래·채팅 처리를 Express 서비스 계층에서 관리하는 구성으로 통일 |
| Firebase | 인증과 실시간 구독 제공 | PostgreSQL의 관계·유니크 제약·트랜잭션을 사용하는 데이터 모델 선택과 맞지 않음 |
| Next.js Route Handler만으로 백엔드 구성 | 저장소·배포 단순화 | Vercel 함수와 별도로 상시 소켓 서버가 필요해 백엔드 처리가 분산됨 |
| NestJS | 모듈·DI 기반 구조 제공 | 1차 범위는 Express 미들웨어와 서비스 계층으로 구성하고 프레임워크 도입 범위를 제한 |

### 트레이드오프

- 인증·업로드·소켓을 직접 구현하고 검증할 작업이 늘어납니다. 소요 시간은 아직 측정하지 않았습니다.
- 쿠키 속성, 요청 제한, 파일 검증 등 보안 설정과 점검을 직접 관리해야 합니다.
- 백엔드 실행 환경과 DB의 배포·운영 비용을 별도로 관리해야 합니다.

### 바뀔 가능성과 되돌리는 법

1차 범위에서는 유지합니다. 인증·권한·실시간 처리를 다른 플랫폼으로 옮기면 서비스 계층과 데이터 접근 방식을 함께 검토해야 합니다. 파일 저장소는 `ImageStorage` 인터페이스로 분리하므로 구현체를 교체할 수 있습니다 ([결정 0010](#0010--사진은-선택-즉시-업로드하고-등록은-url만-보낸다)).

## 0002 · 개발 · 운영 DB를 PostgreSQL로 통일한다

| 상태 | 결정 2026-11-09 (개요 초안의 "SQLite → Postgres 전환"을 대체) |
| --- | --- |
| 영향 | Prisma 스키마 · 로컬 환경 · 테스트 환경 |

**개발·테스트·운영 DB를 PostgreSQL 16으로 통일합니다.** 날짜 처리, 검색, 제약, 트랜잭션의 환경별 차이를 줄이기 위한 선택입니다.

### 맥락

처음엔 "로컬은 SQLite(설치 불필요), 운영은 Postgres"로 제안했다. 그러나 두 엔진은 날짜 타입(SQLite는 문자열) · 대소문자 비교(`ILIKE` 없음) · 부분 유니크 인덱스(`WHERE deletedAt IS NULL`) · 트랜잭션 격리 수준에서 다르게 동작한다. 이 프로젝트는 그 네 가지를 전부 쓴다.

### 선택

로컬 · 테스트 · 운영 모두 PostgreSQL 16. 로컬은 `docker compose up db` 한 줄, 테스트는 같은 컨테이너의 별도 데이터베이스, 운영은 Railway Postgres.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| SQLite 로컬 → Postgres 운영 | 로컬 설치 0 | "로컬에선 되는데 운영에서 깨진다"가 가장 찾기 어려운 버그. 특히 유니크 인덱스 조건이 SQLite에서 조용히 무시되면 채팅방 중복이 운영에서만 생김 |
| Postgres 로컬 네이티브 설치 | Docker 불필요 | 버전 · 포트 · 권한이 기기마다 달라짐. Docker Compose가 환경을 파일로 고정 |
| Neon · Supabase 무료 Postgres를 개발 DB로 | Docker도 불필요 | 네트워크 없이 개발 불가, 테스트가 외부 DB를 때림. 다만 Docker가 정 어려우면 **허용** — `DATABASE_URL`만 바꾸면 됨 |
| MySQL | 익숙한 사람이 많음 | 부분 유니크 인덱스가 없어 soft delete + 유니크를 생성 컬럼 트릭으로 우회해야 함 |

### 트레이드오프

- Docker Desktop이 필요하다. 처음 설치 · 메모리 1GB.
- 테스트가 실제 DB를 쓰므로 인메모리 테스트보다 느리다 (수초 → 수십 초). 대신 제약 조건 · 트랜잭션이 실제로 검증된다.

### 바뀔 가능성과 되돌리는 법

매우 낮다. Postgres 고유 기능(부분 인덱스 · `ILIKE` · CHECK 제약 · `FOR SHARE`)에 의도적으로 기대므로, 바꾸려면 그 기능들을 애플리케이션 레벨로 옮겨야 한다. 바꿀 이유가 생기면 그건 DB가 아니라 요구사항이 바뀐 것이다.

## 0003 · 인증은 JWT를 httpOnly 쿠키에 담는다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 인증 미들웨어 · 로그인 · 로그아웃 · 비밀번호 변경 · 소켓 핸드셰이크 · 프록시(0004) |

**HTTP 인증은 httpOnly 쿠키의 JWT로 처리하고, 비밀번호 변경 시 `tokenVersion`으로 기존 토큰을 무효화합니다.** 1차 범위에는 별도 세션 저장소와 리프레시 토큰을 두지 않습니다.

### 맥락

세 가지가 필요하다. ① 새로고침해도 로그인이 유지된다 ② JS에서 토큰을 읽을 수 없다(XSS로 탈취 불가) ③ 소켓 연결도 같은 인증을 쓴다. 그리고 서버는 단일 인스턴스, 세션 저장소(Redis)는 두지 않는다.

### 선택

로그인 시 `{ sub: userId, ver: tokenVersion, iat, exp }`를 HS256으로 서명한 JWT를 `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=7d` 쿠키로 내린다. 요청마다 서명 · 만료 · `ver` 검증. 남은 기간이 절반 아래면 새 쿠키로 연장(슬라이딩). 리프레시 토큰 없음. 비밀번호 변경 시 `User.tokenVersion += 1`로 모든 기존 토큰 무효화.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 서버 세션 (세션 ID 쿠키 + DB/Redis 테이블) | 즉시 무효화 · 기기 목록 가능 | 요청마다 세션 조회. 저장소가 하나 더 늘어남. 1차엔 "다른 기기 로그아웃" 요구가 없음 |
| JWT를 `localStorage`에 + `Authorization` 헤더 | CORS가 단순 | XSS 한 번이면 토큰이 통째로 나감. 쿠키는 같은 XSS에서도 토큰 자체는 못 읽음 (요청은 위조 가능 — 그래서 CSRF 대비 필요) |
| 액세스(15분) + 리프레시(7일) 두 토큰 | 액세스 탈취 피해를 15분으로 제한 | 리프레시 로테이션 · 재사용 감지까지 하면 세션 테이블과 복잡도가 같아짐. 1차엔 단일 토큰 + `tokenVersion`이 비용 대비 충분 |
| 세션 쿠키 (브라우저 닫으면 만료) | 공용 PC 안전 | 모바일 브라우저는 닫혀도 세션이 남는 경우가 많아 의미가 약함. 7일 고정 |

### 트레이드오프

- **즉시 로그아웃이 안 된다.** 한 기기에서 로그아웃해도 다른 기기 토큰은 만료까지 산다. `tokenVersion`은 비밀번호 변경 때만 올린다.
- **CSRF 대비가 필요하다.** 쿠키는 자동 전송되므로 `SameSite=Lax` + 쓰기 요청의 `Origin` 검사. 0004(같은 오리진)가 이를 단순하게 만든다.
- 토큰에 `nickname` 같은 걸 넣지 않으므로 요청마다 사용자 조회가 한 번 있다 (`ver` 검증에 어차피 필요).

### 바뀔 가능성과 되돌리는 법

중간. 소셜 로그인이나 "다른 기기 모두 로그아웃"이 들어오면 리프레시 토큰 또는 세션 테이블로 간다. 그때 고치는 곳은 `auth` 모듈(발급 · 검증 두 함수)과 소켓 핸드셰이크뿐이도록, 토큰 형식을 다른 모듈이 모르게 한다.

## 0004 · 프론트가 백엔드를 프록시해 같은 오리진을 유지한다

| 상태 | 결정 2026-11-09 · 소켓 인증 방식 확정 2026-11-09 (스파이크 후) |
| --- | --- |
| 영향 | 쿠키 속성 · CORS 설정 · 배포 구성 · 소켓 연결 주소 |

**HTTP API는 같은 오리진의 Next.js 프록시를 경유하고, 소켓은 단기 전용 토큰으로 백엔드에 직접 연결합니다.** 두 배포 도메인 사이의 쿠키 전달과 상시 연결 경로를 구분한 설계입니다.

### 맥락

프론트는 Vercel(`neighbo.vercel.app`), 백엔드는 Railway(`xxx.up.railway.app`) — 도메인이 다르다. 브라우저 입장에서 교차 사이트이므로 0003의 쿠키가 `SameSite=Lax`로는 백엔드에 전송되지 않는다.

### 선택

Next.js Route Handler `app/api/[...path]/route.ts`가 `/api/*` 요청을 백엔드로 그대로 전달한다(헤더 · 쿠키 · 본문 포함). 브라우저는 항상 프론트 오리진하고만 통신한다.

**소켓은 예외** — Vercel 함수는 WebSocket 상시 연결을 중계할 수 없으므로 브라우저가 백엔드에 직접 연결한다. 이때 교차 사이트 쿠키에 기대지 않는다:

1. 프론트가 같은 오리진의 `GET /api/auth/socket-token`을 호출 (일반 세션 쿠키로 인증, 프록시 경유)
2. 백엔드가 `{ sub, purpose: "socket", exp: 60초 }` JWT를 발급
3. `io(SOCKET_URL, { auth: (cb) => fetchToken().then((token) => cb({ token })) })` — `auth`를 함수로 두어 재연결마다 새 토큰
4. 소켓 미들웨어가 `handshake.auth.token`을 검증 (`purpose`가 다르면 거부)

[스파이크 ⑤](tech-notes.md#websocket과-socketio)에서 `handshake.auth`로 인증 · 거부가 동작하는 것을 확인했다. 쿠키를 쿼리스트링에 넣는 안은 URL이 로그에 남아 버렸다.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| `SameSite=None; Secure` + CORS `credentials: true` | 프록시 코드 없음 | 모든 쓰기 요청에 CSRF 대비가 필수가 됨. Safari ITP가 서드파티 쿠키를 제한해 iOS에서 로그인이 풀리는 사례가 있음 |
| 커스텀 도메인으로 서브도메인 통일 (`app.neighbo.kr` · `api.neighbo.kr`) | 가장 정석. 쿠키 `Domain=.neighbo.kr` | 도메인 구매 · DNS가 필요. 가능하면 **이쪽으로 가고 프록시를 제거**한다 — 바뀔 가능성 항목 |
| 백엔드가 프론트도 서빙 (Express가 Next를 호스팅) | 오리진 하나 | Vercel의 이미지 최적화 · 엣지 캐시를 버림. 배포도 하나로 묶여 롤백 단위가 커짐 |

### 트레이드오프

- 모든 API 요청이 Vercel 함수를 한 번 거친다 — 지연 수십 ms 추가, Vercel 함수 호출 수 증가.
- 파일 업로드가 프록시를 지나간다. Vercel 함수 요청 본문 한도(4.5MB)가 있으므로 **업로드 한도를 4MB로 두고 클라이언트가 재인코딩해 그 아래를 보장한다** (2026-11-10, 처음 정한 10MB는 이 한도와 모순이었다 — [트러블슈팅 T-04](troubleshooting.md)).
- 백엔드가 보는 IP가 사용자 IP가 아니라 Vercel 함수의 IP다 → 프록시가 비밀 헤더와 함께 원 IP를 넘긴다 ([07 보호 장치](architecture/backend.md#07--보호-장치와-배치), 트러블슈팅 T-02).
- 서버 쪽 `fetch`는 `Origin`을 붙이지 않는다 → 프록시가 브라우저의 `Origin`을 명시적으로 복사해야 백엔드의 CSRF 검사가 동작한다.
- 서버 컴포넌트에서 부른 백엔드 응답의 `Set-Cookie`는 브라우저에 닿지 않는다 → 쿠키 연장은 `/api/*` 경유 요청에서만 ([프론트 01](architecture/frontend.md#01--렌더링-전략)).
- 프록시 한 파일이 장애 지점이 된다.

### 바뀔 가능성과 되돌리는 법

**중간~높음.** 커스텀 도메인을 사면 서브도메인 방식이 더 낫다. 그때 ① 프록시 파일 삭제 ② 프론트의 `API_BASE`를 `api.` 도메인으로 ③ 쿠키에 `Domain` 추가 ④ CORS 허용 목록에 프론트 추가. 이 네 곳 외엔 닿지 않도록 API 호출을 `apiFetch()` 한 함수로 모은다.

## 0005 · 실시간 전달은 Socket.IO, 누락 복구는 DB 커서로 처리한다

| 상태 | 결정 2026-11-09 · 스파이크 결과 반영 2026-11-09 |
| --- | --- |
| 영향 | 채팅방 · 채팅 목록 · 배지 · 소켓 서버 · 인증(0003) |

**채팅·읽음·배지 전달에는 Socket.IO 4를 사용하고, 누락 복구와 전송 재시도는 서비스에서 처리합니다.** 연결·버퍼 동작은 [WebSocket 스파이크](tech-notes.md#websocket과-socketio)에서 확인했습니다.

### 맥락

메시지 수신, 읽음 동기화, 배지 갱신, 재연결 후 누락 복구가 필요합니다. WebSocket 연결이 제한된 환경에서도 사용할 수 있도록 폴링 폴백을 포함합니다.

### 선택

룸(`room:{id}` · `user:{id}`), ack, 자동 재연결, 폴링 폴백은 Socket.IO를 사용합니다. 별도 스파이크에서 핸드셰이크·프레임 처리·하트비트·재연결·커서 복구를 확인하고, 다음 처리 규칙을 정했습니다.

- 서버 재시작 후 누락 메시지는 DB의 `after` 커서로 조회합니다.
- 저장 여부가 불명확한 메시지는 같은 `tempId`로 재시도하고, 중복은 유니크 제약으로 처리합니다.
- 서버가 명시적으로 연결을 끊으면 클라이언트에서 인증 상태를 확인하고 다시 연결합니다. 연결 중 토큰 만료도 별도로 검사합니다.
- `connectionStateRecovery`는 사용하지 않습니다. 짧은 순단의 복구와 서버 재시작 후 DB 복구를 하나의 경로로 관리합니다.
- 전송에는 타임아웃이 있는 `emitWithAck`를 사용합니다. 타임아웃 없는 `emit`이 버퍼에 남았다가 재연결 후 전송되는 동작을 실험에서 확인했습니다.

### 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| `ws` 기반 구현 | 프로토콜·연결 처리를 직접 제어 | 재연결·룸·ack·폴백을 모두 구현하고 유지해야 함 |
| SSE + HTTP POST | 서버 발신 이벤트 전달과 요청 처리를 분리 | 메시지·읽음 등 양방향 이벤트를 같은 연결로 처리하는 구성을 선택 |
| 주기적 폴링 | 소켓 연결 없이 구현 가능 | 조회 주기에 따른 수신 지연과 반복 요청 발생 |
| Pusher·Ably | 연결·확장 운영을 서비스에 위임 | 현재 선택한 별도 백엔드·DB 기반 처리와 외부 실시간 플랫폼의 책임 범위를 다시 나눠야 함 |

### 트레이드오프

- Socket.IO 자체 프로토콜을 사용하므로 클라이언트도 Socket.IO를 지원해야 합니다.
- 1차는 단일 서버 인스턴스입니다. 여러 인스턴스로 확장하면 Redis 어댑터 등 연결 간 이벤트 전달 구성을 추가해야 합니다.
- 클라이언트·서버에 라이브러리 의존성이 추가됩니다. 번들 크기는 구현 후 측정합니다.

### 바뀔 가능성과 되돌리는 법

1차 범위에서는 유지합니다. 이벤트 이름과 페이로드는 [API 명세](architecture/backend.md#10--api-명세)로 관리하고, 클라이언트 연결은 `useChatSocket()` 훅으로 감쌀 예정입니다. 라이브러리를 교체하면 해당 훅과 서버 소켓 계층을 수정합니다.

## 0006 · 상품 삭제는 항상 soft delete, 채팅방은 열람만

| 상태 | 결정 2026-11-09 (개요 초안의 "채팅방이 있으면 soft"를 대체) |
| --- | --- |
| 영향 | Product 모든 조회 · 목록 · 상세 · 채팅 목록 · 채팅방 · 마이페이지 · 배지 · 파일 정리 배치 — 2.4 매트릭스에서 가장 넓은 행 |

**상품은 `deletedAt`으로 삭제 처리하고, 기존 채팅방은 열람만 허용합니다.** 거래 목록에서는 숨기되 상대의 대화 기록은 보존하도록 정했습니다.

### 맥락

상품이 삭제되면 그 상품에 달린 채팅방이 문제다. 메시지를 지우면 상대의 대화 기록이 사라지고, 남기면 "없는 상품의 방"을 어떻게 보여줄지 정해야 한다. 초안은 "채팅방 있으면 soft, 없으면 hard"였는데 분기가 하나 늘고 복구도 불가능해진다.

### 선택

- 삭제 = `Product.deletedAt = now()`. 어느 상태(판매중 · 예약중 · 거래완료)에서든 가능. 하드 삭제 없음.
- 모든 `Product` 조회에 `deletedAt IS NULL`을 Prisma 클라이언트 확장으로 **자동 주입.** 삭제된 것까지 봐야 하는 곳만 `withDeleted()`를 명시 — 채팅방 · 채팅 목록의 상품 요약, 구매 내역(0012). 이 둘 외에 늘어나면 결정을 다시 본다.
- 삭제된 상품의 채팅방: **열람 가능, 전송 불가.** 상단에 "삭제된 물건이에요", 입력창 비활성.
- 읽지 않은 수 · 배지에는 삭제된 상품의 방도 포함 (대화는 살아 있음).
- 30일 후 배치가 이미지 **파일**만 삭제. `Product` · `Message` 행은 영구.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 하드 삭제 + 채팅방 cascade | 모델이 단순, 데이터가 안 남음 | 상대의 대화 기록이 사라짐. 실수 삭제 복구 불가. 거래완료 후 분쟁 시 근거 없음 |
| 채팅방 있으면 soft, 없으면 hard (초안) | 쓸모없는 행이 안 남음 | 분기가 둘. "채팅방 없음"을 확인하는 순간과 삭제 사이에 방이 생기는 경합. 얻는 건 행 몇 개 절약 |
| 삭제된 방도 전송 허용 | 거래 후 연락 가능 | 삭제는 "이 물건 얘기는 끝"이라는 신호. 연락이 필요하면 삭제 대신 거래완료로 바꾸면 됨 — 그래서 PX-OK-03 확인 모달에 이 안내를 넣음 |
| 삭제된 방은 목록에서도 숨김 | 깔끔 | 상대 입장에서 대화가 증발. "삭제됨" 라벨이 더 정직 |

### 트레이드오프

- **모든 Product 쿼리가 조건 하나를 더 가진다.** 자동 주입을 빠뜨리면 삭제된 상품이 노출된다 — 그래서 수동이 아니라 클라이언트 확장으로 강제하고, 이를 검증하는 테스트를 둔다.
- 테이블이 영구히 자란다. 1차 규모에선 무시 가능.
- `withDeleted()`를 쓰는 곳이 늘어나면 "자동 주입"의 의미가 약해진다. 사용처를 API 명세에 명시적으로 나열한다.

### 바뀔 가능성과 되돌리는 법

낮다. 정책이 바뀐다면 "N일 후 하드 삭제"가 추가되는 방향이고, 그건 배치 하나다. 반대로 하드 삭제로 돌아가려면 채팅방 cascade 규칙을 다시 정해야 하므로 사실상 새 결정이다.

## 0007 · 읽음은 방 단위 위치 하나로 센다

| 상태 | 결정 2026-11-09 · **시각 비교 부분은 [0016](#0016--방-안-순서와-읽음-위치는-시각이-아니라-방별-번호seq로-센다)으로 대체** (2026-11-10) |
| --- | --- |
| 영향 | ChatRoomMember · 채팅방 · 채팅 목록 · 배지 · 소켓 이벤트 |

**읽음 상태는 방 참여자별 마지막 위치 하나로 관리합니다.** 위치의 단위는 후속 [결정 0016](#0016--방-안-순서와-읽음-위치는-시각이-아니라-방별-번호seq로-센다)에 따라 시각에서 방별 번호로 변경했습니다.

### 맥락

"읽지 않은 메시지 N개"와 "상대가 읽음"을 보여주려면 읽음을 어딘가 기록해야 한다. 메시지마다 기록하면 정확하지만 쓰기가 메시지 수만큼 늘고, 방마다 하나만 기록하면 가볍지만 "방을 보는 중에 온 메시지"를 언제 읽은 것으로 칠지 정해야 한다.

### 선택

- `ChatRoomMember(roomId, userId)`에 읽음 위치 하나. 메시지별 `readAt` 없음. 위치의 단위는 처음엔 시각(`lastReadAt`)이었으나, 동시 트랜잭션에서 순서가 어긋나 방별 번호(`lastReadSeq`)로 바꿨다 → [0016](#0016--방-안-순서와-읽음-위치는-시각이-아니라-방별-번호seq로-센다).
- **읽음의 정의**: 방 화면이 보이는 상태(탭 활성 + `document.visibilityState === "visible"`)에서 메시지 목록이 렌더된 시점. 세 순간에 `room:read`를 보낸다 — 방 입장 · 보이는 동안 새 메시지 수신 · 백그라운드에서 복귀.
- 읽지 않은 수 = `COUNT(Message WHERE roomId AND senderId != me AND seq > lastReadSeq)`. 목록 화면에선 비정규화 컬럼 `ChatRoom.lastSeq > lastReadSeq`로 **방 단위 유무**만 판단(0008).
- 상대 읽음 표시: 내 마지막 메시지 아래 "읽음" 한 번. 상대 `lastReadSeq >= message.seq`이면.
- 내가 보낸 메시지는 저장 트랜잭션에서 내 `lastReadSeq`도 그 번호로 갱신(내 메시지는 내가 읽은 것).

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 메시지별 `readAt` (또는 `MessageRead` 테이블) | 정확. 그룹 채팅 확장 가능 | 1:1에선 과함. 방 입장 시 N개 행 갱신. 1차 요구에 "어느 메시지까지 읽었는지"는 없음 |
| `ChatRoom`에 `sellerLastReadAt` · `buyerLastReadAt` 두 컬럼 | 조인 없음. 가장 단순 | 역할이 둘로 고정됨 — 1:1 전제라 사실 문제없음. **차선으로 허용.** 02 데이터 모델에서 `ChatRoomMember` 테이블 vs 두 컬럼 중 쿼리 단순성을 보고 최종 선택 |
| 클라이언트가 읽음을 로컬에만 저장 | 서버 쓰기 0 | 기기 간 동기화 불가, 상대 읽음 표시 불가 |
| "방 입장 시에만" 읽음 (보는 중 수신은 미읽음) | 구현 단순 | 방을 보고 있는데 배지가 오르는 모순 |

### 트레이드오프

- "보이는 상태"의 판단이 브라우저마다 미묘하다 (모바일 사파리의 백그라운드 탭). `visibilitychange`에 의존하고, 틀려도 다음 입장에서 맞춰진다 — 1차엔 허용.
- 방 단위라 "상대가 내 메시지 3개 중 2개까지 읽음"은 표현 못 한다. 1:1에선 필요 없음.
- `room:read`가 소켓으로만 가면 소켓이 끊겼을 때 읽음이 안 올라간다 → HTTP 폴백 `POST /chat-rooms/{id}/read` 병행.

### 바뀔 가능성과 되돌리는 법

낮다. 그룹 채팅이 들어오면 메시지별 기록으로 가야 하지만 1차 · 2차 범위에 없다. 읽음 계산은 `unread.ts` 한 모듈에 모아 두어, 방식이 바뀌어도 호출부(목록 · 배지 · 방)는 함수 시그니처만 유지하면 된다.

## 0008 · 배지 숫자는 읽지 않은 방의 수다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 하단 탭 배지 · 브라우저 제목 · `GET /me/unread` · `notification:unread` 페이로드 |

**하단 채팅 탭의 배지는 읽지 않은 메시지가 있는 방 수를 표시합니다.** 각 방의 정확한 미읽음 메시지 수는 채팅 목록에서 별도로 표시합니다.

### 맥락

탭 배지에 "3"이 떠 있을 때 그 3이 메시지 3개인지 방 3개인지 정해야 한다. 카카오톡은 메시지 수, 슬랙은 채널 수에 가깝다.

### 선택

**읽지 않은 메시지가 있는 방의 수.** 방 3개에 메시지 50개면 "3". 배지는 "들어가 봐야 할 방이 몇 개"라는 행동 단위와 일치해야 하고, 방 수는 비정규화 컬럼(`ChatRoom.lastSeq` vs `ChatRoomMember.lastReadSeq`, [0016](#0016--방-안-순서와-읽음-위치는-시각이-아니라-방별-번호seq로-센다))만으로 Message 테이블 조인 없이 계산된다. 방 안의 정확한 미읽음 수는 채팅 목록의 행별 배지가 보여준다.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 읽지 않은 메시지 총수 | 익숙함 (카카오톡) | 계산에 Message 조인 필요. 한 방에서 50개 오면 "50"이 떠서 압박만 줌. 1:1 거래 채팅은 방 수가 더 의미 있음 |
| 점만 표시 (숫자 없음) | 가장 단순 | "몇 개"가 사라짐. 접근성 이름에도 숫자가 없음 |
| 둘 다 내려주고 UI가 선택 | 유연 | 두 숫자를 유지하면 불일치 버그 여지. 1차엔 하나만 |

### 트레이드오프

- 사용자가 "메시지 수"를 기대했다면 처음엔 낯설다. 채팅 목록에 들어가면 행별 숫자가 있어 금방 이해된다.
- 한 방에서 연속으로 와도 배지가 안 오른다 — 의도한 동작.

### 바뀔 가능성과 되돌리는 법

낮음~중간. 메시지 수로 바꾸려면 `GET /me/unread` 응답에 `messages` 필드를 추가하고 배지 컴포넌트가 읽는 필드만 바꾼다. 계산은 `unread.ts`(0007) 안이다.

## 0009 · 목록은 무한 스크롤 대신 [더 보기] 버튼 + 커서

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 중고 목록 · 검색 결과 · 채팅 목록 · 마이페이지 목록 (채팅방 과거 메시지는 예외) |

**목록은 커서 페이지네이션과 [더 보기] 버튼으로 추가 조회합니다.** 키보드 접근, 새 항목 안내, 뒤로가기 복원 방식을 함께 정의했습니다.

### 맥락

목록이 20개를 넘으면 더 불러와야 한다. 무한 스크롤은 익숙하지만 키보드 사용자가 푸터에 도달할 수 없고, 스크린리더에 "더 불러왔다"를 알리기 어렵고, 뒤로가기 시 스크롤 복원이 복잡하다. 그리고 오프셋 페이지네이션은 새 항목이 끼어들면 중복 · 누락이 생긴다.

### 선택

- 목록 끝에 **[더 보기] 버튼.** 누르면 다음 20개를 붙이고, 새로 붙은 첫 항목으로 포커스를 옮기며, `aria-live`로 "20개 더 불러왔어요".
- 페이지네이션은 **커서** `(createdAt, id)` base64. `limit+1`개를 조회해 `nextCursor` 유무를 판단. 서버는 `nextCursor: null`이면 버튼을 그리지 않게 알려준다.
- 뒤로가기: TanStack Query 캐시에 불러온 페이지가 남아 있어 그대로 복원.
- **예외**: 채팅방의 과거 메시지는 위로 스크롤 시 자동 로드 + [이전 메시지 보기] 버튼 병행. 위 방향 로드는 푸터 문제가 없고, 대화 맥락은 끊김 없이 읽는 게 자연스럽다.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 무한 스크롤 (`IntersectionObserver`) | 익숙, 조작 없음 | 접근성 셋(푸터 도달 · 알림 · 포커스)을 전부 따로 해결해야 함. 개요 7절 "키보드만으로 완료"와 충돌 |
| 무한 스크롤 + [더 보기] 병행 | 둘 다 | 둘을 유지하면 포커스 · 스크롤 복원 로직이 두 배. 버튼 하나로 충분 |
| 숫자 페이지 (1 2 3 …) | 특정 페이지로 점프 | 커서와 양립 불가(전체 수 필요). 최신순 피드에서 "3페이지"는 의미가 계속 바뀜 |
| 오프셋 (`?page=2`) | 구현 단순 | 새 상품이 끼어들면 2페이지 첫 항목이 1페이지 마지막과 중복 |

### 트레이드오프

- 클릭 한 번이 더 든다. 피드 체류 시간이 중요한 서비스라면 불리하지만 거래 목록은 "찾는" 행동이라 괜찮다.
- 커서는 정렬 기준이 바뀌면(가격순 등) 커서 구조도 바뀐다. 1차는 최신순 하나.
- "전체 N개"를 보여줄 수 없다 (커서는 count를 안 함). 필요하면 별도 count 쿼리.

### 바뀔 가능성과 되돌리는 법

낮음. 무한 스크롤을 원하게 되면 `[더 보기]` 버튼에 `IntersectionObserver`를 얹어 **자동으로 눌리게** 하면 되고, 버튼은 키보드용으로 남긴다. 데이터 계층(커서)은 그대로다.

## 0010 · 사진은 선택 즉시 업로드하고 등록은 URL만 보낸다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 거래 등록 · 수정 · 아바타 · `Upload` 모델 · `ImageStorage` 인터페이스 · 고아 파일 정리 배치 |

**사진은 선택 즉시 업로드하고, 상품 등록 요청에는 업로드 식별자만 전달합니다.** 사진별 진행·재시도와 상품 연결 전 임시 파일 정리를 분리합니다.

### 맥락

상품 등록 폼에 사진 최대 10장이 들어간다. 업로드 시점은 둘 중 하나다 — 사진을 고르는 즉시 올리거나, [등록] 버튼을 누를 때 폼과 함께 한 번에 올리거나.

### 선택

- 사진을 고르면 즉시 `POST /uploads` (multipart, 1장씩, 동시 3개). 서버는 매직 바이트 검사 → EXIF 회전 적용 · 제거 → 긴 변 1600 원본 + 400 썸네일 webp 생성 → `ImageStorage.put()` → `Upload` 행 생성 → URL 반환.
- 폼은 썸네일과 진행률을 사진별로 보여준다. 실패한 사진만 재시도.
- [등록]은 `imageIds: string[]`만 보낸다. 서버는 업로더가 본인인지 확인 후 `ProductImage`로 연결.
- 24시간 안에 연결되지 않은 `Upload`는 하루 한 번 배치가 파일과 행을 삭제.
- `ImageStorage { put, delete, url }` 인터페이스. 개발은 로컬 디스크, 운영은 S3 호환.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 등록 시 일괄 업로드 (multipart에 폼 + 사진 10장) | 고아 파일 없음, 배치 불필요 | 한 요청이 수십 MB. 한 장 실패하면 전부 재전송. 진행률을 사진별로 못 보여줌. 프록시(0004) 본문 한도에 걸림 |
| 클라이언트가 S3에 직접 업로드 (presigned URL) | 서버 대역폭 0 | 리사이즈 · 형식 검증 · EXIF 제거를 클라이언트가 해야 하고 클라이언트는 신뢰할 수 없음. 람다로 후처리하면 구조가 하나 더 |
| Base64로 JSON에 포함 | 요청이 하나 | 33% 커지고 메모리에 다 올라감 |

### 트레이드오프

- **고아 파일이 생긴다.** 등록을 취소하면 올린 사진이 남는다 → 배치가 필요하다. 배치는 Railway cron 또는 서버 내 스케줄러.
- `Upload` 임시 모델이 하나 더 있다 (❓ 02에서 `ProductImage.productId nullable`로 합칠지 결정).
- 업로드 API가 상품 없이도 열려 있으므로 rate limit · 용량 제한 · 업로더 검사가 필수.

### 바뀔 가능성과 되돌리는 법

업로드 시점 자체는 낮음. **저장소 구현은 높음** — R2 · Supabase Storage · Vercel Blob 어디로든 갈 수 있고, 그래서 인터페이스 뒤에 뒀다. 바꿀 때 닿는 곳은 구현체 한 파일과 환경 변수.

## 0011 · 목록 · 상세는 비로그인으로 볼 수 있다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 중고 목록 · 검색 · 거래 상세 · OG 메타 · 인증 미들웨어의 선택적 인증 |

**상품 목록·검색·상세는 로그인 없이 열람할 수 있도록 설계합니다.** 등록·변경·채팅·개인 내역은 인증 후 이용합니다.

### 맥락

당근은 앱이라 로그인이 전제지만, 웹은 링크를 공유하고 검색에 걸리는 매체다. 비로그인 사용자가 상품을 볼 수 있어야 공유 링크가 의미 있고, 처음 온 사람이 가입 전에 서비스를 이해할 수 있다.

### 선택

- 비로그인 열람 가능: 중고 목록 · 검색 · 거래 상세.
- 로그인 필요: 거래 등록 · 수정 · 삭제 · 상태 변경 · [채팅하기] · 채팅 목록 · 채팅방 · 마이페이지.
- 보호 화면에 비로그인 접근 시 로그인으로 보내고 `?next=`로 돌아온다. [채팅하기]를 눌러 로그인하면 돌아와서 **버튼을 다시 눌러야** 한다 (자동으로 방을 만들지 않음 — 의도 확인).
- 인증 미들웨어는 두 모드: `requireAuth`(401) · `optionalAuth`(있으면 사용자 주입). 상세 API는 `optionalAuth`로 `viewer.isSeller` 등을 계산.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 전부 로그인 필요 | 인증 경로 하나, 판매자 정보 노출 없음 | 공유 링크 · OG · 첫 방문이 전부 로그인 벽. 웹의 장점을 버림 |
| 목록만 공개, 상세는 로그인 | 중간 | 공유 링크가 상세인데 그게 막힘. 어중간 |
| 비로그인에게 가격 · 판매자 가림 | 가입 유도 | 다크 패턴. 서비스 신뢰에 반함 |

### 트레이드오프

- 판매자 닉네임 · 아바타가 공개된다. 공개용 사용자 객체(`id, nickname, avatarUrl, createdAt`)로 제한하고 이메일은 절대 안 나간다.
- 크롤링에 노출된다. 1차 규모에선 rate limit으로 충분.
- `optionalAuth`에서 만료된 쿠키를 어떻게 다룰지(무시 vs 401) 정해야 한다 → 무시하고 비로그인으로 처리, 쿠키 삭제 헤더.

### 바뀔 가능성과 되돌리는 법

낮음. 전부 비공개로 바꾸려면 두 라우트의 미들웨어를 `requireAuth`로 바꾸고 `proxy.ts`(Next.js 16의 이전 `middleware.ts`)의 공개 경로 목록에서 빼면 된다.

## 0012 · 거래완료 시 구매자를 지정하고 구매 내역을 둔다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | `Product.buyerId · soldAt` · 상태 변경 API · 거래 상세 바텀시트 · 마이페이지 구매 내역 탭 · 삭제 정책(0006) |

**판매자는 거래완료 시 구매자를 지정하고, 지정된 상품은 구매자의 구매 내역에 표시합니다.** 구매자는 해당 상품의 채팅 상대 중에서 선택하며, 미지정 완료도 허용합니다.

### 맥락

거래완료를 "상태 값 하나"로만 두면 서비스에 "누가 누구와 거래했다"는 사실이 남지 않는다. 구매자 쪽 마이페이지엔 아무것도 없고, 두 번째 핵심 시나리오(구매자 흐름)가 "채팅하고 끝"으로 닫힌다.

### 선택

- 판매자가 거래완료로 바꿀 때 바텀시트 "누구와 거래했나요?" — 이 상품의 채팅 상대 목록 + "선택 안 함". 채팅 상대가 0명이면 바로 완료.
- 지정하면 `Product.buyerId · soldAt` 저장. 서버는 `buyerId`가 이 상품 채팅방의 구매자인지 검증(`400 NOT_A_CHAT_PARTNER`).
- 마이페이지에 **구매 내역** 탭: `Product WHERE buyerId = me AND status = SOLD`.
- 거래완료 → 판매중 복귀 시 `buyerId · soldAt` 초기화 (확인 모달에 명시).
- 구매자에게 알림은 없음 (1차). 구매자는 마이페이지에서 발견.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 구매자 지정 없음 (상태만) | 바텀시트 · 탭 · 검증이 전부 사라짐 | 구매자 흐름이 완결되지 않음. "거래" 서비스인데 거래 사실이 데이터에 없음 |
| 구매자가 "구매 확정" 버튼으로 스스로 지정 | 양쪽 합의 | 흐름이 하나 더 (판매자 완료 → 구매자 확정). 1차엔 판매자 단독 지정이 당근과 같고 단순 |
| 별도 `Trade` 테이블 | 거래 이력 · 후기 확장 | 1차엔 상품당 거래가 최대 1건. 컬럼 둘로 충분. 후기가 들어오면 그때 테이블로 |
| 예약중에도 예약자 지정 | 일관성 | 예약은 자주 바뀌고 취소됨. 요구가 없는데 UI가 늘어남 |

### 트레이드오프

- 거래완료가 두 단계(상태 선택 → 상대 선택)가 된다. "선택 안 함"으로 한 번에 끝낼 수 있게 열어 둔다.
- 상품이 삭제돼도 구매 내역에는 **남긴다** (`withDeleted()`, "삭제됨" 라벨). 거래 사실은 판매자의 삭제로 사라지지 않는다 — 0006의 "모든 조회에 자동 주입"에 대한 명시적 예외 하나.
- `buyerId`가 `User`를 참조하므로 탈퇴(2차) 시 처리 규칙이 필요해진다.

### 바뀔 가능성과 되돌리는 법

낮음. 후기 · 매너온도 같은 기능이 들어오면 `Trade` 테이블로 승격하고 `buyerId · soldAt`을 거기로 옮긴다. 그때까지는 컬럼 둘.

## 0013 · 거래 수정을 1차 범위에 넣는다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 등록 폼 재사용 · `PATCH /products/{id}` · 상세 `⋯` 메뉴 · 사진 삭제 · 수정 URL 권한 |

**거래 수정은 1차 범위에 포함하고 등록 폼을 재사용합니다.** 채팅방을 유지하면서 오타·가격·사진을 변경할 수 있도록 정했습니다.

### 맥락

초기 범위에는 거래 수정이 없었습니다. 오타·가격·사진을 바꾸기 위해 삭제 후 재등록하면 기존 방의 전송이 막히고, 구매자는 새 상품에서 다시 대화를 시작해야 합니다. 기존 채팅을 유지하는 수정 흐름이 필요합니다.

### 선택

- 수정을 1차에 넣는다. 화면은 등록 폼 재사용 (`/products/{id}/edit`), 기존 사진 삭제 · 새 사진 추가 · 제목 · 가격 · 설명 변경.
- 상태는 수정 폼에서 바꾸지 않는다 (상태 변경은 별도 API · 별도 UI — 0012).
- 거래완료 상품도 수정 가능 (제목 · 설명 정정 용도). 가격 변경은 허용합니다. 후속 [데이터 모델 설계](architecture/backend.md#02--데이터-모델)에서 거래완료 시 `soldPrice`를 저장하도록 구체화했으며, 구매 내역은 거래 시점 가격을 유지합니다.
- 수정 이력 · "(수정됨)" 표시 없음.
- 동시 수정은 마지막 저장 승리 (낙관적 잠금 없음 — 1인 판매자가 두 탭에서 동시에 고치는 경우뿐).

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 수정 없음 (삭제 후 재등록) | 기능 하나 적음 | 채팅방 단절. 0006의 "삭제된 방 전송 불가"와 결합하면 사용자가 손해 |
| 가격만 수정 (인라인) | 가장 흔한 수정만 | 제목 오타 · 사진 교체도 흔함. 폼 재사용이라 전체 수정이 비용 차이 없음 |
| 수정 시 채팅 상대에게 시스템 메시지 "가격이 바뀌었어요" | 투명 | 시스템 메시지 타입이 생김 (0005 범위 확장). 2차 |

### 트레이드오프

- 폼이 두 모드(생성 · 수정)를 가진다. 초기값 · 제출 API · 성공 후 이동이 분기한다.
- 기존 사진 삭제는 파일 삭제를 수반한다 — 저장 실패 시 파일만 먼저 지워지는 순서 문제. 파일 삭제는 DB 커밋 후.
- 현재 상품 가격과 거래 시점 가격을 별도로 관리해야 합니다 (`soldPrice`, 후속 데이터 모델 설계 반영).

### 바뀔 가능성과 되돌리는 법

낮음. 빼려면 라우트 · `⋯` 메뉴 항목 · `PATCH` 하나를 제거하면 된다. 폼 컴포넌트는 생성 모드만 남는다.

## 0014 · PC 화면도 640px 단일 열로 간다

| 상태 | 결정 2026-11-09 |
| --- | --- |
| 영향 | 모든 화면의 레이아웃 · 브레이크포인트 · 목록 열 수 · 채팅 2단 여부 |

**본문은 최대 640px의 단일 열로 구성하고, 상품 목록은 두 열로 표시합니다.** 모바일과 PC에서 거래·채팅 흐름을 같은 구조로 유지합니다.

### 맥락

모바일 우선(360px)으로 설계하지만 데모는 PC 브라우저에서 열린다. 1024px 이상에서 (a) 본문을 640px로 제한해 중앙 정렬하거나 (b) 넓은 그리드 · 좌우 2단(채팅 목록 + 방)으로 재배치해야 한다.

### 선택

- 본문 최대 폭 **640px 중앙 정렬.** 하단 탭바는 그대로(PC에서도 하단). 배경은 연한 회색으로 본문 카드가 구분되게.
- 목록은 640px 안에서 **2열 그리드** (360px에서도 2열 — 카드 폭 약 160px, 정보량은 제목 2줄 · 가격 · 상태).
- 채팅은 2단 레이아웃 없음. PC에서도 목록 → 방 이동.
- 1024px에서 달라지는 것은 플로팅 등록 버튼이 헤더 [판매하기]로 바뀌는 것뿐.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| 1024px에서 3~4열 그리드 + 사이드바 | PC다운 밀도 | 화면 폭별 레이아웃과 컴포넌트 분기가 늘어 1차 구현·검증 범위가 커짐 |
| 채팅 2단 (좌 목록 · 우 방) | 데스크톱 메신저 UX | 라우팅(`/chats` 와 `/chats/{id}`가 한 화면) · 포커스 관리 · 읽음 처리(두 영역 동시 가시)가 전부 복잡해짐. 0007의 "보이는 상태" 정의가 흔들림 |
| 1열 리스트 (당근 앱 방식) | 정보량 많음 (설명 미리보기 가능) | 640px에서 1열은 카드가 너무 길어짐. 2열이 PC · 모바일 양쪽에서 균형 |

### 트레이드오프

- PC 화면 양옆이 빈다. "모바일 앱을 웹으로 옮긴" 인상 — 의도한 것이고, 서비스 성격(동네 거래)과 맞다.
- 넓은 화면의 장점(한눈에 더 많은 상품)을 버린다.

### 바뀔 가능성과 되돌리는 법

중간. 반응은 보고 정할 수 있다. Tailwind 컨테이너 폭(`max-w-[640px]`) 하나와 목록 그리드 열 수(`grid-cols-2 lg:grid-cols-3`)만 바꾸면 넓은 그리드는 쉽게 간다. 채팅 2단은 새 결정이 필요하다.

## 0015 · 최상위 폴더는 `{역할}-{대표 기술}`로 짓는다

| 상태 | 결정 2026-11-10 (개요 5절의 "예시 이름"을 확정) |
| --- | --- |
| 영향 | 저장소 최상위 구조 · 루트 README · 커밋 범위 표 · 공유 패키지 경로 · 워크스페이스 설정 · 배포 루트 디렉터리 |

**앱 폴더는 역할과 대표 기술로, 공유 패키지는 담긴 내용으로 구분합니다.** `frontend-next/`·`backend-node/`·`shared-schema/`를 최상위에 배치하는 예정 구조입니다.

### 맥락

프론트엔드·백엔드·공유 패키지의 역할과 실행 환경을 폴더 이름으로 구분할 필요가 있습니다. 앱 두 개와 공유 패키지 하나를 관리하는 규모에 맞춰 최상위에 배치합니다. 관련 경로와 배포 루트는 [개요 5절](overview.md#5-폴더-구조)에 정리했습니다.

### 선택

**실행되는 앱은 `{역할}-{대표 기술}`, 앱들이 함께 쓰는 패키지는 `shared-{담긴 것}`.** 최상위에 바로 둔다.

```
neighbo/
├─ frontend-next/    # 역할: 프론트엔드 · 대표 기술: Next.js (React 기반)
├─ backend-node/     # 역할: 백엔드 · 대표 기술: Node.js (Express)
├─ shared-schema/    # 프론트 · 백엔드가 함께 쓰는 Zod 스키마 · 타입 · 정규화 함수
├─ spikes/           # 운영 코드 아님
└─ docs/
```

| 규칙 | 이유 |
| --- | --- |
| 역할이 앞, 기술이 뒤 | 알파벳 정렬에서 같은 역할끼리 붙고, 읽는 순서가 "무엇을 하는가 → 무엇으로"가 된다 |
| 기술은 **하나만** — 그 앱을 대표하는 런타임 · 프레임워크 | `frontend-next-tailwind-tanstack`처럼 늘리면 이름이 의존성 목록이 된다. 나머지는 각 폴더 README의 "예정 스택"에 |
| 프론트는 `react`가 아니라 `next` | 이 앱의 렌더링 · 라우팅 · 프록시는 Next.js가 결정한다([프론트 01](architecture/frontend.md#01--렌더링-전략)). `react`로 쓰면 "SPA인가?"로 읽혀 서버 렌더 설계가 이름에서 사라진다. Next.js가 React 위에 있다는 것은 README 첫 줄에 적는다 |
| 백엔드는 `express`가 아니라 `node` | 런타임이 무엇인지가 배포 · 운영 판단(Railway, 상시 실행)을 가른다. 프레임워크는 바뀔 수 있어도 런타임은 거의 안 바뀐다 |
| 공유 패키지는 기술 대신 **내용** | 실행되지 않으므로 "무엇으로 돌아가는가"보다 "무엇이 들어 있나"가 중요하다 |
| `apps/` · `packages/` 같은 한 겹을 두지 않음 | 앱이 둘, 패키지가 하나뿐이라 묶을 이유가 없고, 최상위 목록에서 역할이 바로 보여야 한다 |

#### 워크스페이스

루트 `package.json`의 npm workspaces로 세 폴더를 묶는다. 패키지 이름은 폴더 이름과 같게 둔다.

```json
{ "private": true, "workspaces": ["frontend-next", "backend-node", "shared-schema"] }
```

```ts
import { productCreateSchema, normalizeEmail } from 'shared-schema';
```

#### 커밋 범위와의 관계

커밋 범위 낱말(`web` · `server`)은 그대로 둔다 — 범위는 "역할", 폴더는 "역할 + 기술"이라 기술이 바뀌어도 범위는 안 바뀐다. 대응은 [커밋 규칙](dev.md#범위) 표에 적는다. `shared-schema`만 고치는 커밋은 범위를 비우거나, 한쪽 역할 때문이면 그 역할 범위를 쓴다.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| `web/` · `server/` | 짧고 커밋 범위와 같은 낱말 | 기술 스택이 이름에 없어 폴더를 열어야 안다 |
| `frontend/` · `backend/` | 역할이 가장 분명 | 같은 이유. 그리고 설계 문서 이름(`frontend.md` · `backend.md`)과 겹쳐 링크에서 헷갈린다 |
| `apps/web` · `apps/server` · `packages/shared` | Turborepo · Nx 관례, 앱이 늘면 정리됨 | 최상위에서 역할이 안 보이고, 앱 둘에 비해 구조가 무겁다 |
| `frontend-react/` | 사용 중인 UI 라이브러리를 표시 | 렌더링·라우팅·프록시를 담당하는 Next.js를 대표 기술로 표시하기로 선택 |
| `client/` · `api/` | 흔함 | `api/`는 Next.js의 `app/api/` 경로와 겹친다 |

### 트레이드오프

- 이름이 길다. `cd frontend-next`는 `cd web`보다 손이 더 간다.
- **기술을 바꾸면 폴더 이름도 바뀐다.** 이름에 기술을 넣은 대가다. 그래서 기술 자리에는 가장 안 바뀔 것(프레임워크보다 런타임, 라이브러리보다 프레임워크)만 넣었다.
- 앱이 셋 이상으로 늘면(관리자 화면 등) `frontend-admin-next`처럼 역할을 쪼개야 하고, 그때는 `apps/` 한 겹이 더 나을 수 있다.

### 바뀔 가능성과 되돌리는 법

낮음. 바뀐다면 원인은 기술 교체이고, 그때 고칠 곳은 ① `git mv` ② 루트 `package.json` workspaces ③ 공유 패키지 import 경로(이름이 같으므로 패키지 이름만 바꾸면 됨) ④ Vercel · Railway의 루트 디렉터리 설정 ⑤ 커밋 규칙 범위 표 ⑥ 문서 링크. 문서 링크는 링크 검사 스크립트로 찾는다.

## 0016 · 방 안 순서와 읽음 위치는 시각이 아니라 방별 번호(`seq`)로 센다

| 상태 | 결정 2026-11-10 — 명세 검토에서 발견한 결함 수정 |
| --- | --- |
| 영향 | Message · ChatRoom · ChatRoomMember · 메시지 커서 · 재연결 복구 · 읽음 · 배지 · 소켓 이벤트 |
| 대체 | 0007의 "`lastReadAt` 시각 비교" 부분 (방 단위로 하나만 기록한다는 결정은 유지) |

**메시지 정렬·복구·읽음에는 방별 순번 `seq`를 사용합니다.** 방 행을 잠근 뒤 순번을 발급해 같은 방의 저장 순서가 커밋 순서와 일치하도록 설계했습니다.

### 맥락

처음 명세는 메시지 순서를 `(createdAt, id)`로, 읽음을 `lastReadAt = GREATEST(lastReadAt, now())`로 정했다. 구현 전에 검토하다 두 군데가 깨진다는 것을 찾았다.

**1. `now()`는 문장 시각이 아니라 트랜잭션 시작 시각이다.** Postgres의 `now()` · `@default(now())`는 트랜잭션이 시작한 순간의 값이다. 같은 방에 메시지 A · B가 동시에 저장되면:

```
A 트랜잭션 시작 (createdAt = 10:00:00.100) ── 상품 FOR SHARE 대기 ────────── 커밋 (10:00:00.350)
B 트랜잭션 시작 (createdAt = 10:00:00.200) ── 커밋 (10:00:00.250)
                                                      ↑ 클라이언트가 B를 받고 after = B로 복구 조회
```

클라이언트가 B까지 받은 뒤 `after = B`로 누락분을 물으면 `(createdAt, id) > B` 조건에 A(10:00:00.100)는 걸리지 않는다. **커밋은 B보다 늦었는데 시각은 B보다 앞선 A가 영영 빠진다.** 시각 커서는 "커밋 순서 = 시각 순서"일 때만 맞는데, 동시 트랜잭션에선 그 가정이 깨진다.

**2. 읽음을 서버 시각으로 찍으면 화면에 그리지 않은 메시지까지 읽음이 된다.** 클라이언트가 메시지 10개를 그리고 `room:read`를 보내는 사이에 11번째가 커밋되면, 서버의 `now()`는 11번째보다 뒤라 11번째도 읽음이 된다. 사용자는 본 적 없는 메시지의 배지를 잃는다.

### 선택

- `ChatRoom.lastSeq` (방의 마지막 번호), `Message.seq` (방 안에서 1부터 하나씩), 유니크 `(roomId, seq)`.
- 메시지 저장(T7)은 **`UPDATE "ChatRoom" SET "lastSeq" = "lastSeq" + 1, ... WHERE id = $1 RETURNING "lastSeq"`**로 번호를 받는다. 이 UPDATE가 방 행을 잠그므로 같은 방의 저장은 한 줄로 서고, **번호 순서 = 커밋 순서**가 된다. 다른 방끼리는 서로 막지 않는다.
- 커서 · 재연결 복구 · 정렬은 모두 `seq`. `room:join { after: seq }` → `WHERE roomId = ? AND seq > ?`.
- 읽음은 `ChatRoomMember.lastReadSeq`. 클라이언트가 **실제로 그린 마지막 `seq`**를 보낸다: `room:read { roomId, seq }`. 서버는 `GREATEST(lastReadSeq, LEAST($seq, room.lastSeq))` — 뒤로 가지 않고, 없는 번호를 앞질러 찍지도 않는다.
- 미읽음: 방 단위 유무는 `ChatRoom.lastSeq > ChatRoomMember.lastReadSeq` (보낸 사람은 저장 때 자기 `lastReadSeq = seq`), 방 안 개수는 `COUNT(Message WHERE roomId AND seq > lastReadSeq AND senderId <> me)`.
- 상대 읽음 표시: 상대 `lastReadSeq >= 내 마지막 메시지 seq`.
- `createdAt`은 화면에 시각을 보여주는 용도로만 남긴다.
- 덤: 클라이언트가 `message:new`로 `seq = 마지막 + 2`를 받으면 **사이에 빠진 것이 있다는 것을 안다** → 그 자리에서 `after`로 채운다. 시각 커서로는 알 수 없던 틈이다.

### 버린 대안

| 대안 | 장점 | 버린 이유 |
| --- | --- | --- |
| `clock_timestamp()`로 문장 시각 사용 | 스키마 변경 없음 | 시각을 찍는 순간과 커밋 순간 사이에 다른 트랜잭션이 끼면 같은 문제가 남는다. 확률만 줄 뿐 0이 아니다 |
| 전역 시퀀스(`BIGSERIAL`) | 잠금 없음 | 시퀀스 값은 **발급** 순서이지 **커밋** 순서가 아니다. 1번 발급 트랜잭션이 2번보다 늦게 커밋하면 같은 구멍 |
| 복구 때 "마지막 시각 - 5초"부터 겹치게 조회하고 id로 중복 제거 | 스키마 변경 없음 | 5초라는 수에 근거가 없다. 상품 `FOR SHARE` 대기가 길어지면 다시 빠진다. 고칠 수 없는 경합을 운에 맡기는 것 |
| 읽음을 메시지 id로 기록 | 그린 것만 읽음 | cuid는 순서가 없어 "이 id까지"를 비교할 수 없다. 결국 순서 있는 값이 필요 |

### 트레이드오프

- **같은 방의 메시지 저장이 직렬화된다.** 1:1 채팅에서 같은 방에 초당 수십 개가 동시에 들어올 일은 없고, 사용자당 전송 한도(초당 5)가 위를 막는다. 방이 다르면 서로 기다리지 않는다.
- 메시지 저장마다 `ChatRoom` 행 UPDATE — 원래도 마지막 메시지 필드를 갱신하고 있어 쓰기 수는 같다. 순서만 앞으로 당겼다(번호를 먼저 받아야 INSERT할 수 있다).
- **상품 · 채팅 목록은 그대로 시각 커서를 쓴다.** 목록은 "이미 본 것 이후를 빠짐없이 받아야 하는 흐름"이 아니라 새로고침하면 다시 그리는 스냅숏이다. 늦게 커밋된 상품이 첫 페이지와 둘째 페이지 사이에 끼어 잠시 안 보여도 다음 새로고침에서 나타나므로 잃는 것이 없다. 메시지는 한 번 빠지면 사용자가 알 방법이 없어 기준이 다르다.
- 클라이언트가 보낸 `seq`를 믿으면 "안 본 것을 봤다"고 거짓말할 수 있지만, 손해는 자기 배지뿐이다. 상대 화면의 "읽음"이 거짓이 될 수 있다는 점은 1:1 중고거래에서 허용한다.

### 바뀔 가능성과 되돌리는 법

낮다. 그룹 채팅이 와도 방별 번호는 그대로 쓴다(카카오톡 · 슬랙도 방 안 순번을 둔다). 메시지 삭제가 생겨도 번호는 비워 두면 된다 — 클라이언트의 틈 감지는 "서버에 물었는데 없음"을 정상으로 받는다.

### 이 결함을 어떻게 찾았나

명세를 "구현했다고 치고" 쓰기 작업마다 동시 실행 두 개를 그려 보는 검토에서 나왔다. 단일 사용자 시나리오로는 절대 드러나지 않고, 운영에서는 "가끔 메시지 하나가 안 보인다"는 재현 어려운 버그로 나타났을 것이다. 같은 검토에서 찾은 다른 결함은 [트러블슈팅 기록](troubleshooting.md)에 있다.

### 트레이드오프

- `sharp`와 `bcrypt`는 플랫폼별 바이너리를 받는다. 배포 이미지(`node:22-slim`)에서의 동작은 CI의 `image` 작업이 확인한다.
- **S3 호환 저장소 구현은 아직 없다.** `STORAGE_DRIVER=s3`이면 부팅에서 멈춘다(조용히 로컬로 떨어지지 않게). 지금 배포는 로컬 디스크를 쓰므로 **재배포하면 올린 사진이 사라진다.** 마무리 단계 전에 S3 호환 구현을 더한다.
- 직접 구현한 JWT는 표준의 일부(HS256, `exp`)만 다룬다. 범위를 넓히지 않는다.
