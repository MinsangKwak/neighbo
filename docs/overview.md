# 프로젝트 개요

[문서 목차](README.md)

**neighbo는 상품 탐색부터 채팅, 거래완료, 거래 내역 확인까지 연결하는 동네 중고거래 서비스입니다.** 1차 범위는 열 가지 기능이며, 각 기능의 정상 흐름과 오류·권한·동시 요청 처리 방식을 명세로 정리했습니다.

| 항목 | 내용 |
| --- | --- |
| 저장소 | `github.com/MinsangKwak/neighbo` |
| 상태 | 설계 문서 작성 완료·검토 반영 (2026-11-10). 다음은 기술 스파이크 나머지와 서비스 본체 구현 |
| 1차 범위 | 로그인 · 회원가입 · 중고 목록 · 거래 등록 · 거래 상세 · 거래 삭제 · 채팅 목록 · 채팅 · 마이페이지 · 채팅 알림 |
| 작업 방식 | 문서 먼저 — 기능별 요구사항 → 역할별 설계(백엔드 · 프론트엔드 · 흐름), 문서가 끝난 뒤 코드 시작 |

## 1. 목표

**판매자와 구매자가 상품을 확인하고, 채팅으로 약속을 잡고, 거래 결과를 각자의 내역에서 확인할 수 있도록 설계합니다.** 연결 끊김이나 중복 요청이 발생해도 거래 상태와 대화 기록이 일관되게 유지되는 것이 핵심 목표입니다.

| 영역 | 목표 동작 |
| --- | --- |
| 거래 | 상품 등록·수정·삭제, 상태 변경, 구매자 지정, 판매·구매 내역 조회 |
| 채팅 | 상품·구매자 조합마다 하나의 방, 메시지 저장·재전송·누락 복구, 읽음과 배지 동기화 |
| 권한·정합성 | 작성자만 상품을 변경하고, 참여자만 채팅에 접근하며, 중복 요청이 중복 데이터를 만들지 않음 |
| 화면·입력 | 로딩·빈 목록·오류 상태 안내, 입력 정규화, 필드별 검증 메시지 |
| 접근성 | 키보드 조작, 포커스 이동, 스크린리더 오류 안내, WCAG AA 명암비 |

현재 문서는 목표 동작과 검증 계획을 정의합니다. 실제 구현·검증 범위는 [설계·검증 현황](#9-설계검증-현황)에 구분했습니다.

### 제공 형태

- 데모 계정과 시드 데이터로 거래 흐름을 시연할 계획입니다.
- 당근마켓의 흐름과 정보 구조를 참고하되, 화면 디자인은 별도로 구성합니다.
- 후속 기능은 3절의 범위 표에서 관리합니다.

## 2. 서비스 구조 — 엔티티 · 프로세스 · 영향 범위

**서비스 구조는 핵심 엔티티, 업무 프로세스, 변경 영향 범위로 정리했습니다.** 요구사항을 변경할 때 이 표에서 관련 데이터·화면·API를 확인한 뒤 상세 설계에 반영합니다.

### 2.1 사용자와 핵심 시나리오

**한 사용자는 상품을 등록하면 판매자, 다른 상품에 채팅을 시작하면 구매자가 됩니다.** 1차 범위에는 관리자 역할이 없습니다.

```
판매자: 회원가입 → 로그인 → 거래 등록 → (채팅 알림) → 채팅 → 거래 상태 변경(구매자 지정) → 마이페이지에서 확인
구매자: 회원가입 → 로그인 → 중고 목록 → 거래 상세 → 채팅 시작 → 채팅 → 마이페이지 구매 내역에서 확인
```

이 두 줄이 끝까지 끊기지 않고 동작하면 1차 범위는 완료입니다. 나머지(삭제, 알림 배지, 목록 갱신)는 이 흐름을 받치는 기능입니다.

### 2.2 핵심 엔티티와 핵심 필드

핵심 엔티티는 여섯 개이며, 임시 파일 관리를 위한 `Upload`를 포함하면 테이블은 일곱 개입니다. [백엔드 설계의 데이터 모델](architecture/backend.md#02--데이터-모델)에 Prisma 스키마·제약·인덱스를 정의했습니다.

| 엔티티 | 한 줄 정의 | 핵심 필드 | 생명주기 |
| --- | --- | --- | --- |
| **User** | 가입한 사람. 판매자이자 구매자 | `email` `nickname` `avatarUrl` `tokenVersion` | 가입 → (탈퇴는 2차) |
| **Product** | 팔려고 올린 물건 하나 | `sellerId` `title` `price` `status` `buyerId` `deletedAt` | 등록 → 판매중 ⇄ 예약중 → 거래완료 → (삭제는 어느 상태에서든, soft) |
| **ProductImage** | 물건 사진. 순서 있음 | `productId` `url` `thumbnailUrl` `order` | 상품과 함께. 삭제 30일 후 파일 정리 |
| **ChatRoom** | 상품 하나 × 구매자 한 명의 방. 유니크 | `productId` `sellerId` `buyerId` `lastSeq` `lastMessageAt` `lastMessagePreview` | 구매자가 [채팅하기] → 영구 |
| **ChatRoomMember** | 방 참여자의 읽음 위치 | `roomId` `userId` `lastReadSeq` | 방 생성 시 두 행 |
| **Message** | 텍스트 한 줄 | `roomId` `senderId` `seq`(방 안 순서) `content` `tempId` `createdAt` | 전송 → 영구 (삭제 · 수정 없음) |

보조: **Upload** (상품에 연결되기 전 임시 파일, 24시간 후 정리). 1차에 **없는** 엔티티: Notification · Category · Favorite · Report · Review · Location. 없는 이유는 3절 "2차 이후" 표에.

### 2.3 핵심 업무 프로세스

| 프로세스 | 단계 | 걸치는 엔티티 | 규칙의 핵심 |
| --- | --- | --- | --- |
| **P1 물건 올리기** | 사진 업로드 → 상품 생성 → 목록 노출 | Upload → Product · ProductImage | 사진은 선택 즉시 업로드, 등록은 URL만 전송. 고아 업로드는 배치 정리 |
| **P2 거래 시작 (채팅)** | 상세 → [채팅하기] → 방 생성(또는 기존 방) → 첫 메시지 | Product → ChatRoom · ChatRoomMember → Message | 방은 `(productId, buyerId)` 유니크. 판매자는 자기 물건에 방을 못 만듦 |
| **P3 거래 마무리** | 판매자가 상태 변경 → 거래완료 시 구매자 지정 → 양쪽 마이페이지 반영 | Product(`status` `buyerId` `soldAt`) | [전이 표](features/05-product-detail.md) 밖의 전이는 `409`. 구매자는 채팅 상대 중에서만 |
| **P4 읽음과 알림** | 방 번호 `lastSeq` +1 → 메시지 저장 → 수신자 배지 push → 화면에 그린 번호까지 `lastReadSeq` 갱신 | Message → ChatRoom → ChatRoomMember | 배지 = 읽지 않은 **방** 수. Notification 테이블 없음 |
| **P5 내리기** | 삭제 확인 → `deletedAt` → 목록 · 검색 제외, 채팅방은 열람만 | Product → (ChatRoom 표시만) | 항상 soft. 모든 Product 조회에 `deletedAt IS NULL` 자동 주입 |

## 4. 기술 결정

**프론트엔드와 백엔드는 한 저장소에서 관리하고, 인증·권한·거래·채팅 로직은 별도 백엔드 서비스로 구현합니다.** 데이터 제약과 트랜잭션은 PostgreSQL에서, 처리 순서와 오류 응답은 Express 서비스 계층에서 관리하도록 설계했습니다.

아래 표는 1차 구현에 사용할 기술 선택입니다. 대안과 트레이드오프는 [결정 기록](decisions.md)에, 기술 동작과 실험 결과는 [기술 노트](tech-notes.md)에 정리했습니다. 선택을 변경하면 해당 결정과 영향 범위를 함께 기록합니다.

표의 "바뀔 가능성"은 이 선택이 1차 범위 안에서 뒤집힐 확률이고, "바꾸면 닿는 곳"은 그때 고쳐야 하는 범위입니다. **바뀔 가능성이 높은데 닿는 곳이 넓은 것**이 가장 조심해야 할 결정이며, 그런 항목은 인터페이스 뒤에 숨겨 교체 비용을 줄입니다.

| 영역 | 결정 | 왜 필요한가 (없으면 무엇이 안 되나) | 바뀔 가능성 | 바꾸면 닿는 곳 |
| --- | --- | --- | --- | --- |
| 프론트엔드 | Next.js 16 (App Router) + TypeScript | 목록 · 상세를 서버에서 렌더해 첫 화면과 OG 메타를 바로 제공. 없으면 SSR · 라우팅 · 이미지 리사이즈를 직접 조립 | 낮음 | 전부 |
| 스타일 | Tailwind CSS | 디자인 토큰을 `tailwind.config` 한 곳에 두고 [공통 컴포넌트](architecture/frontend.md#09--공통-컴포넌트)의 근거로 삼음. 임의 값(`w-[137px]`) 금지 | 낮음 | 모든 컴포넌트 |
| 백엔드 | Node.js + Express + TypeScript | 인증·검증·오류 처리는 미들웨어로, 권한·트랜잭션·소켓 이벤트 처리는 서비스 계층으로 분리 | 낮음 | 서버 전부 |
| DB · ORM | PostgreSQL 16 + Prisma 7 (`prisma.config.ts` · `@prisma/adapter-pg`) — 로컬 Docker Compose · 운영 Railway | 유니크 제약(채팅방 · 이메일) · 트랜잭션(메시지 저장 + 방 갱신)이 데이터 무결성의 근거. 개발 · 운영 같은 엔진으로 동작 차이 제거 | 낮음 | 스키마 · 리포지토리 계층 |
| 인증 | 이메일 · 비밀번호 · bcrypt · JWT를 httpOnly 쿠키에 | 세션 테이블 없이 stateless. 쿠키라 JS가 토큰을 못 읽음(XSS 완화). `tokenVersion`으로 비밀번호 변경 시 무효화 | 중간 (리프레시 토큰 · 소셜 로그인) | 인증 미들웨어 · 로그인 · 소켓 핸드셰이크 |
| API 경로 | Next.js Route Handler가 백엔드를 프록시 (같은 오리진) | 프론트 · 백엔드 도메인이 달라도 쿠키가 `SameSite=Lax`로 동작. CORS · `SameSite=None` 설정이 사라짐 | 중간 | 프록시 한 파일 · 쿠키 설정 |
| 실시간 | Socket.IO (WebSocket + 폴링 폴백) | 채팅·읽음·배지를 같은 연결로 전달. 재연결·룸·ack는 라이브러리를 사용하고, 누락 복구와 전송 재시도는 서비스에서 처리 ([실험 결과](tech-notes.md#websocket과-socketio)) | 낮음 | 채팅 · 알림 · 소켓 서버 |
| 이미지 저장 | `ImageStorage` 인터페이스 — 로컬 디스크(개발) · S3 호환(운영) | 업로드 · 리사이즈 · 삭제 세 메서드 뒤에 저장소를 숨김. 운영 저장소가 바뀌어도 호출부 무변경 | **높음** (Cloudflare R2 · Supabase Storage 등) | 구현체 한 파일 |
| 검증 | Zod 스키마를 `shared-schema/`에서 프론트 · 백엔드 공유 | 같은 규칙을 두 번 쓰지 않음. 서버가 최종 검증자 | 낮음 | 스키마 패키지 |
| 데이터 조회 (프론트) | TanStack Query | 캐시 · 재조회 · 낙관적 갱신 · 뒤로가기 복원을 한 규칙으로 | 낮음 | 모든 조회 훅 |
| 테스트 | 백엔드 API 통합 테스트(Vitest + supertest + 진짜 PostgreSQL) · 프론트 컴포넌트(Testing Library) · E2E 핵심 시나리오 2개(Playwright) | 수용 조건과 1:1. 층별 역할은 [테스트 전략](dev.md#테스트-전략--수용-조건-하나에-테스트-하나) | 낮음 | — |
| 배포 | 프론트 Vercel · 백엔드 Railway | GitHub 연결 자동 배포, Postgres 원클릭, WebSocket · 상시 실행. 환경 매핑은 [브랜치 · 배포 전략](dev.md#브랜치--배포-전략--main은-언제나-배포-가능하게) | 중간 | 환경 변수 · 워크플로 |

### 의존성 추가 규칙

**새 의존성은 해결할 문제, 도입 비용, 교체 범위를 확인한 뒤 추가합니다.** 다음 내용을 [결정 기록](decisions.md)에 남깁니다.

1. 기존 코드나 표준 API로 해결하기 어려운 문제와 대안
2. 라이브러리가 담당하는 동작과 서비스에서 별도로 처리해야 하는 부분
3. 제거·교체 시 변경할 코드, 설정, 데이터

작은 유틸리티는 표준 API와 유지보수 비용을 먼저 검토합니다.

### 추가 검토

현재 설계에 반영된 결정은 [결정 기록](decisions.md)과 [경우의 수](features/00-common.md#경우의-수-표기)에 있습니다. 반영된 판단 중 추가 확인이 필요한 항목은 [검토 요청](decisions.md#검토-요청)에서 관리합니다.

## 5. 폴더 구조

**앱 폴더는 `{역할}-{대표 기술}`, 공유 패키지는 `shared-{내용}`으로 구분합니다.** 역할과 실행 환경을 이름에서 확인할 수 있도록 정했습니다. 아래는 구현 단계까지 포함한 예정 구조이며, 루트 `package.json`·공유 패키지는 아직 없고, 워크플로는 문서 검사 하나만 있습니다. 상세 기준은 [결정 0015](decisions.md#0015--최상위-폴더는-역할-대표-기술로-짓는다)에 있습니다.

```
neighbo/
├─ README.md              # 서비스 소개 · 설계 현황 · 구성 · 문서 링크
├─ LICENSE                # MIT
├─ package.json           # npm workspaces — 아래 세 폴더를 묶음 (구현 단계)
├─ frontend-next/         # 프론트엔드 · Next.js — README가 프론트엔드 설계의 입구
├─ backend-node/          # 백엔드 · Node.js — README가 백엔드 설계의 입구
├─ shared-schema/         # 공유 — Zod 스키마 · 타입 · 정규화 함수 (구현 단계)
├─ spikes/                # 기술 실험 코드 (서비스 코드 아님)
├─ scripts/               # check-docs.py — 문서 링크 · 앵커 · 표 검사
├─ docs/
│  ├─ README.md           # 문서 목차
│  ├─ overview.md         # 개요 (이 문서)
│  ├─ features/           # 기능 하나 = 한 장 — 요구사항 + 경우의 수 (00 공통 ~ 10 채팅 알림)
│  ├─ architecture/       # flow.md · frontend.md · backend.md — 역할마다 한 장
│  ├─ decisions.md        # 결정 기록 16개 + 검토 요청
│  ├─ troubleshooting.md  # 설계 결함 · 스파이크 문제의 원인과 해결
│  ├─ tech-notes.md       # 기술 노트 — 동작 원리 · 실험 결과
│  └─ dev.md              # 커밋 · 브랜치 · 테스트 · AI 작업·검증
└─ .github/               # 워크플로(문서 검사 · 구현 단계에 lint · 테스트 추가) · PR 템플릿
```

**요구사항은 기능별로, 처리 방식은 역할별로 관리합니다.** 예를 들어 중복 채팅방 생성에 대해 프론트엔드는 버튼 잠금과 응답 처리를, 백엔드는 유니크 제약과 기존 방 반환을 담당합니다. 기능별 요구사항은 `docs/features/`의 기능 문서에, 여러 기능에 걸친 처리 방식은 `docs/architecture/`의 설계 문서에 둡니다. 2026-11-10에 64개였던 문서를 이 구조로 합쳤습니다 — 기능 하나를 보려고 경우의 수 · 요구사항 · 프론트엔드 · 백엔드 네 곳을 오가지 않도록.

| 폴더 | 역할 | 대표 기술 | 배포 | 커밋 범위 |
| --- | --- | --- | --- | --- |
| `frontend-next/` | 프론트엔드 | Next.js (React 기반) | Vercel 루트 디렉터리 | `web` |
| `backend-node/` | 백엔드 | Node.js (Express) | Railway 루트 디렉터리 | `server` |
| `shared-schema/` | 공유 | Zod | 두 앱이 빌드 때 포함 | (비움) |

## 7. 품질 기준

**아래 항목은 "있으면 좋은 것"이 아니라 각 기능의 완료 조건입니다.** 요구사항의 수용 조건에 기능별로 구체화합니다.

| 영역 | 기준 |
| --- | --- |
| 상태 | 모든 데이터 화면은 로딩 · 빈 목록 · 에러 세 상태의 UI가 정의되어 있다 |
| 권한 | 소유자 검사는 서버에서 한다. 프론트의 버튼 숨김은 편의이고 보안이 아니다 |
| 입력 검증 | 프론트와 서버가 같은 스키마로 검증한다. 서버 검증 실패는 필드별 메시지로 돌아온다 |
| 접근성 | 키보드만으로 열 가지 기능을 완료할 수 있다. 폼 오류는 `aria-describedby`로 연결된다. 명암비 WCAG AA |
| 반응형 | 모바일(360px) 우선, PC(1024px 이상)에서도 깨지지 않는다 |
| 동시성 | 채팅방 생성 · 거래 상태 변경은 중복 요청에도 한 번만 반영된다 |
| 테스트 | 수용 조건마다 대응하는 테스트가 있다. 테스트 이름은 수용 조건 문장을 그대로 쓴다 ([테스트 전략](dev.md#테스트-전략--수용-조건-하나에-테스트-하나)) |
| 성능 | 모바일(4G · 중급 기기) p75 기준 LCP ≤ 2.5초 · INP ≤ 200ms · CLS ≤ 0.1. 목록 · 상세 API는 시드 규모(상품 1만 · 메시지 10만)에서 p95 ≤ 300ms, 쿼리마다 `EXPLAIN ANALYZE`로 인덱스 사용 확인 |
| 보안 | 사용자 입력은 원문 저장 · 출력 시 이스케이프, 쓰기 요청은 `Origin` 검사, 업로드는 매직 바이트 검사. 비밀값은 환경 변수로만 |
| 문서 | 코드가 문서와 다르면 같은 PR에서 문서를 고친다 |
| 원인 노트 | 버그를 고칠 때 "무엇을 고쳤다"가 아니라 **"왜 생겼다"**를 남긴다. 증상 → 가설 → 확인 방법 → 원인 → 수정 → 재발 방지. 한 기술 안의 문제는 [기술 노트](tech-notes.md)에, 설계 결함과 여러 층에 걸친 문제는 [트러블슈팅 기록](troubleshooting.md)에 쌓고 회귀 테스트를 단다 |
| 영향 범위 | 변경 PR은 2.4 매트릭스의 해당 행을 인용하고, 표시된 열을 모두 확인했음을 적는다 |
