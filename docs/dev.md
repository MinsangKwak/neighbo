# 개발 규칙

[문서 목차](README.md)

**커밋 · 브랜치 · 구현 순서 · 테스트 · AI 작업 검증의 규칙을 한 곳에 둡니다.** 코드 단계의 PR은 이 문서의 규칙을 따릅니다.

## 커밋 메시지 · 변경 이유를 찾을 수 있게 쓰기

**한 커밋에는 한 가지 변경 목적을 담고, 제목에는 달라진 결과를 적습니다.** 본문에는 이유와 필요한 검증 근거를 남깁니다. 폴더명보다 `git log -- 경로`로 해당 영역의 변경 이력을 읽을 수 있게 하는 것이 기준입니다.

### 형식

```text
<종류>(<범위>): <제목>

<왜 바꿨는지 · 무엇을 택했는지>
Refs: #12
```

| 자리 | 규칙 |
| --- | --- |
| 종류 | 아래 표의 값 하나. 소문자 |
| 범위 | 선택. `web` · `server` · `docs` · `infra` 중 하나. 둘 이상에 걸치면 비운다 |
| 제목 | 한국어로 변경 결과를 72자 안에 작성. 끝에 마침표를 붙이지 않으며, 상세 방법은 본문에 기록 |
| 본문 | 선택. 이유가 있을 때만. 이슈·리뷰·PR이 출처면 `Refs:` 줄에 번호 |
| 꼬리표 | `Co-Authored-By:` · `Signed-off-by:` 같은 줄은 그대로 둔다 |

### 종류

| 종류 | 언제 |
| --- | --- |
| `feat` | 사용자가 보는 새 기능·동작 |
| `fix` | 잘못된 동작을 고침 |
| `style` | 디자인·CSS·문구 배치만. 동작은 그대로 |
| `refactor` | 동작은 같고 구조만 바꿈 |
| `docs` | 문서만 |
| `test` | 검사만 |
| `data` | 시드 데이터·스냅샷·이미지 갱신 |
| `ci` | 워크플로·배포·훅 설정 |
| `release` | 판 올림. `release: v1.2.0 — 한 줄 요약` |
| `sync` | 브랜치 동기화 병합. `sync: dev → main — v1.2.0` |
| `chore` | 위에 없는 잡일. 되도록 쓰지 않는다 |

주제가 둘이면 커밋을 나눕니다. 제목을 `·`로 이어 여러 주제를 담는 것은 `release`에만 허용합니다.

### 범위

| 범위 | 가리키는 곳 |
| --- | --- |
| `web` | `frontend-next/` 와 프론트엔드 설계 `docs/architecture/frontend.md` |
| `server` | `backend-node/` 와 백엔드 설계 `docs/architecture/backend.md` |
| `docs` | 그 밖의 `docs/` 아래 문서. 종류가 `docs`이면 범위는 비워도 된다 |
| `infra` | 배포 · 환경 변수 · 컨테이너 · 워크플로 · 루트 `package.json` |

`shared-schema/`만 고치는 커밋은 범위를 비우고, 한쪽 역할 때문에 고치면 그 역할 범위를 쓴다. 범위 낱말은 역할이고 폴더 이름은 역할 + 기술이라, 기술이 바뀌어 폴더 이름이 바뀌어도 범위는 유지한다 ([결정 0015](decisions.md#0015--최상위-폴더는-역할-대표-기술로-짓는다)).

### PR과 병합 커밋

PR 제목도 같은 꼴로 씁니다 — PR 목록이 커밋 목록과 같은 말로 읽히게 하기 위해서입니다. 병합은 리베이스 병합이라 브랜치의 역할별 커밋이 그대로 남습니다([브랜치 전략](#왜-스쿼시가-아닌가)). 동기화 PR은 `sync: dev → main`으로 통일합니다. `git merge`가 만든 `Merge …` 제목의 커밋은 검사에서 제외합니다.

### 브랜치

기능 하나 = 브랜치 하나 = PR 하나입니다. 흐름 · 보호 규칙 · 배포 환경은 [브랜치 · 배포 전략](#브랜치--배포-전략--main은-언제나-배포-가능하게)에 있습니다.

| 무엇 | 이름 | 예 |
| --- | --- | --- |
| 기능 브랜치 | `종류/짧은-이름` (ASCII, 커밋 종류와 같은 낱말) | `feat/product-list` · `fix/chat-unread-badge` · `docs/data-model` |
| 동기화 브랜치 | `sync-main-vX.Y.Z` | `sync-main-v1.2.0` |

| 브랜치 | 역할 |
| --- | --- |
| `dev` | 개발, 일반 변경의 PR 대상 |
| `main` | 검증된 변경 통합 · 배포 기준 |

브랜치 안에서 커밋을 역할별로 쪼개고, PR은 리베이스 병합해 그 커밋들을 그대로 남깁니다. 병합한 브랜치는 로컬·원격에서 지웁니다.

### 예

```text
feat(web): 중고 목록에서 거래완료 글을 흐리게 보여준다
fix(server): 채팅방을 같은 상품·같은 구매자로 두 번 만들지 않는다
style(web): 상품 카드의 가격을 제목 아래 한 줄로 내린다
test(server): 거래 삭제는 작성자만 할 수 있는지 검사한다
docs: 데이터 모델 명세
release: v1.0.0 — 1차 범위 열 가지 기능
sync: dev → main — v1.0.0
```

### 검사

| 어디 | 무엇 | 켜는 법 |
| --- | --- | --- |
| 로컬 `commit-msg` 훅 | 저장 전에 제목 꼴을 본다 | 저장소에서 한 번 `git config core.hooksPath .githooks` (훅과 검사기는 코드 단계에서 추가) |
| 작업 세션 | PR을 열기 전에 `--range origin/dev..HEAD`로 커밋 제목을 모두 본다 | 자동 |

검사기는 제목 한 줄만 보고 본문은 보지 않습니다 — 규칙은 제목에만 있습니다.

### DCO 서명

`git commit -s`로 커밋해 `Signed-off-by:` 줄을 남깁니다. 서명은 해당 내용을 이 저장소의 조건으로 기여할 권리가 있다는 확인입니다.

## 호스팅 비용과 옮길 계획

지금 백엔드와 DB는 Railway의 Trial(가입 후 30일 · $5 크레딧)에서 돕니다. Trial이 끝나면 월 $1 크레딧으로 줄어 상시 가동으로는 한 달을 채우지 못합니다. 그 전에 기간 제한 없는 무료 플랜으로 옮깁니다.

| 대상 | 옮길 곳 | 조건 (2026-11-11에 각 서비스 문서로 확인) | 걸리는 점 |
| --- | --- | --- | --- |
| 백엔드 | Render 무료 웹 서비스 (Docker) | 월 750시간, 15분 동안 요청 · 소켓 메시지가 없으면 꺼지고 다음 요청에 약 1분 뒤 켜짐. 리전에 Singapore가 있다 | 0.1 CPU에서 마이그레이션 · 시드까지의 부팅 시간은 재 보지 않았다 |
| DB | Supabase 무료 Postgres (사진과 같은 프로젝트) | 500MB, 일주일 동안 쓰지 않으면 멈추고 대시보드에서 직접 되살려야 한다 | 풀러를 거친 접속에서 마이그레이션 · 권고 잠금이 도는지 확인하지 않았다. Render의 무료 Postgres는 30일 뒤 만료라 쓰지 않는다 |
| 사진 | Supabase Storage (`STORAGE_DRIVER=s3`, 엔드포인트 `…/storage/v1/s3`) — 옮김 | 파일 1GB · 전송 월 5GB | 운영에서 사진 주소가 Supabase로 나가는 것을 확인했다 |

옮길 때 바뀌는 것은 환경 변수뿐입니다. 백엔드는 저장소 루트의 `Dockerfile` 하나로 뜨고, DB는 `DATABASE_URL`, 사진은 `STORAGE_DRIVER`와 `S3_*`로 정해집니다. Vercel의 `API_URL`을 새 백엔드 주소로 바꾸고, 백엔드의 `ALLOWED_ORIGIN`은 그대로 둡니다. 꺼졌다 켜지는 호스트에서는 켜질 때마다 시드가 돌아 데모 상품이 처음 상태로 돌아갑니다.

### 옮기는 절차

저장소 루트의 `render.yaml`이 백엔드 설정(Docker · Singapore · 무료 · 환경 변수 이름)을 담고 있습니다. 비밀값은 파일에 없고 대시보드에서 직접 넣습니다. **아직 이 절차로 옮겨 본 적은 없습니다.**

| 순서 | 할 일 | 확인 |
| --- | --- | --- |
| 1 | Supabase 대시보드 → Connect에서 **Session pooler** 접속 문자열을 복사한다. 마이그레이션(`prisma migrate deploy`)은 세션 단위 기능을 쓰므로 Transaction pooler(6543)가 아니라 세션 쪽이어야 한다 | 문자열의 포트가 5432 |
| 2 | Render → New → Blueprint로 이 저장소를 고르고, 묻는 값(`DATABASE_URL` · `JWT_SECRET` · `PROXY_SECRET` · `DEMO_PASSWORD` · `S3_ACCESS_KEY_ID` · `S3_SECRET_ACCESS_KEY`)을 넣는다. `PROXY_SECRET` · `DEMO_PASSWORD`는 Vercel에 넣은 값과 같아야 한다 | 로그에 마이그레이션 → 시드 → `boot` 순서, `/readyz`가 200 |
| 3 | Vercel의 `API_URL`을 Render 주소로 바꾸고 다시 배포한다 | 홈에 상품이 보이고 로그인 · 채팅 전송이 된다 |
| 4 | Railway 서비스를 멈춘다 | — |

DB는 새로 시작합니다 — 지금 Railway의 데이터는 시드와 확인용 계정뿐이라 옮기지 않습니다. 사진은 이미 Supabase에 있어 그대로 보입니다.

| 옮긴 뒤 달라지는 것 | 이유 · 대응 |
| --- | --- |
| 15분 동안 요청이 없으면 꺼지고, 다음 요청은 켜질 때까지(약 1분) 기다린다 | 무료 플랜의 조건. 화면은 목록 자리에 오류와 [다시 시도]를 보인다 |
| 매일 03:00 · 04:00의 배치는 그 시각에 서버가 켜져 있을 때만 돈다 | 스케줄러가 서버 프로세스 안에 있다. 데모 상품은 켜질 때마다 시드가 처음 상태로 되돌리지만, 데모 계정의 방 · 관심 초기화와 파일 정리는 건너뛸 수 있다. 켜질 때 밀린 배치를 돌리는 처리는 아직 없다 |
| Supabase 프로젝트는 일주일 동안 쓰지 않으면 멈춘다 | 대시보드에서 직접 되살린다. 그동안 `/readyz`는 503, `/healthz`는 200이다 |

## 브랜치 · 배포 전략 · main은 언제나 배포 가능하게

**명세 단계는 문서 브랜치에서 변경을 검토한 뒤 `main`에 반영하고, 서비스 구현부터 `dev` 통합 브랜치를 추가합니다.** 구현 단계는 작업 브랜치 → `dev` → `main` 순서이며, 역할별 커밋을 보존하는 리베이스 병합을 사용합니다. 배포·CI·보호 규칙은 아래 계획에 따라 코드 단계에서 설정합니다.

### 왜 이 구조인가

중요한 것은 전략의 이름이 아니라 브랜치 전략이 문서로 있고 PR과 리뷰 흔적이 남는 것입니다. 순수 Git Flow(release · hotfix 포함 5단)는 정기 릴리스가 있는 패키지 소프트웨어를 위한 모델이고, 상시 배포하는 웹 서비스에는 과합니다. 반대로 `main` 하나만 두는 GitHub Flow는 미리보기 환경과 운영 환경을 나누기 어렵습니다. 그래서 둘의 중간 — GitHub Flow에 통합 브랜치 `dev` 하나를 더한 구조 — 를 택했습니다. 소규모 팀에서 가장 널리 쓰이는 형태이기도 합니다.

### 브랜치

| 브랜치 | 역할 | 수명 | 배포 환경 | 직접 push |
| --- | --- | --- | --- | --- |
| `main` | 검증된 변경 통합. 언제나 배포 가능한 상태 | 영구 | **운영** — Vercel Production · Railway Production | 금지 |
| `dev` | 개발 통합. 일반 변경의 PR 대상 | 영구 | **미리보기** — Vercel Preview · Railway Staging | 금지 |
| `feat/*` `fix/*` `style/*` `refactor/*` `docs/*` `test/*` `ci/*` | 작업 하나 | 수 시간 ~ 수 일. 병합 후 삭제 | PR마다 Vercel Preview URL | 허용 |
| `sync-main-vX.Y.Z` | `dev` → `main` 동기화 PR 전용 | PR 하나 | — | 허용 |

작업 브랜치 이름은 `종류/짧은-이름` (ASCII, 커밋 종류와 같은 낱말)이며, 이슈가 있으면 번호를 앞에 둡니다: `feat/12-product-list`, `fix/31-chat-unread-badge`, `docs/3-data-model`.

#### 두지 않는 브랜치

| 브랜치 | 두지 않는 이유 | 대신 |
| --- | --- | --- |
| `release/*` | 릴리스 전 안정화 기간이 필요할 만큼 변경이 쌓이지 않는다. 쌓이면 PR을 더 작게 쪼개는 것이 답 | `dev` → `main` 동기화 PR + `main` 태그 `vX.Y.Z` |
| `hotfix/*` | 운영 긴급 수정도 `fix/*` 브랜치로 `main`에 직접 PR하면 된다. 이름만 다른 브랜치를 늘리지 않는다 | `fix/*` → `main` PR, 병합 후 `main` → `dev` 역방향 PR로 되돌려 반영 |

### 흐름

```
이슈 발행 → dev에서 브랜치 → 커밋(역할별) → PR(dev 대상) → CI 통과 → 리베이스 병합 → 브랜치 삭제
                                                                              ↓ 기능 묶음이 완성되면
                                                             sync PR(dev → main) → 태그 vX.Y.Z → 운영 배포
```

| 단계 | 명령 · 행동 | 규칙 |
| --- | --- | --- |
| 1. 이슈 | GitHub Issue 발행. 제목은 커밋 제목과 같은 꼴 | 기능 문서(`docs/features/`)의 수용 조건 묶음 하나 = 이슈 하나. 수용 조건을 이슈 본문에 체크리스트로 복사 |
| 2. 브랜치 | `git switch dev && git pull && git switch -c feat/12-product-list` | 항상 최신 `dev`에서 |
| 3. 커밋 | `git commit -s` | [커밋 규칙](#커밋-메시지--변경-이유를-찾을-수-있게-쓰기). 역할별로 쪼갠다 — 모델 · API · 화면 · 테스트 · 문서를 한 커밋에 섞지 않는다 |
| 4. PR | `gh pr create --base dev` | 제목은 커밋 제목 꼴. 본문은 아래 템플릿. `Closes #12` |
| 5. 검사 | CI 자동 실행 | lint · 타입 검사 · 테스트. 하나라도 빨강이면 병합 버튼이 잠긴다 |
| 6. 병합 | Rebase and merge | 브랜치의 역할별 커밋이 그대로 `dev` 위에 한 줄로 올라간다. 병합 전 `git rebase -i`로 "오타 수정" 같은 중간 커밋은 역할 커밋에 합쳐 둔다. 원격 브랜치 자동 삭제 |
| 7. 릴리스 | `sync-main-vX.Y.Z` 브랜치에서 `sync: dev → main — vX.Y.Z` PR | 병합 후 태그. 릴리스 노트는 GitHub Release에 한국어로 |

#### 버전

`vMAJOR.MINOR.PATCH`. 1차 범위 열 가지 기능이 모두 끝나면 `v1.0.0`. 그 전까지는 `v0.x.0`으로 기능 묶음마다 올립니다. 태그는 `main`에만 달고, 한 번 단 태그는 옮기지 않습니다.

#### 왜 스쿼시가 아닌가

처음 안은 스쿼시 병합이었다. 그런데 [커밋 규칙](#커밋-메시지--변경-이유를-찾을-수-있게-쓰기)은 "모델 · API · 화면 · 테스트 · 문서를 한 커밋에 섞지 않는다"이고, 스쿼시는 PR 하나를 커밋 하나로 뭉갠다 — **두 규칙이 서로를 무효로 만들고 있었다.** `git log -- backend-node/`로 서버 쪽 변경만 읽으려면 역할 커밋이 `dev` · `main`에 살아 있어야 한다. 그래서 한 줄 이력(linear history)은 유지하되 커밋을 보존하는 리베이스 병합으로 바꿨다. 대가는 "PR 하나 = 커밋 하나"의 단순함과 PR 단위 되돌리기(`git revert` 한 번)이며, 대신 PR 번호를 각 커밋 본문 `Refs:`에 남겨 묶음을 찾는다.

### 1인 프로젝트 보완 — 리뷰어가 없을 때

**승인자가 없다는 사실을 숨기지 않고, 리뷰가 하던 일을 두 장치로 대신합니다.**

| 리뷰가 하던 일 | 대신하는 장치 |
| --- | --- |
| 깨진 코드 병합 차단 | CI 필수 상태 검사. 실패하면 병합 불가 |
| "이 변경이 요구사항을 만족하는가" 확인 | PR 본문의 수용 조건 체크리스트 — 이슈에서 복사해 와서 하나씩 체크 |
| 빠뜨린 상태 · 접근성 · 권한 점검 | PR 본문의 셀프 리뷰 체크리스트 (아래) |
| 변경 이유 기록 | PR 본문 "문제와 결과" 절 + 커밋 본문 |

#### PR 템플릿

코드 단계에서 `.github/PULL_REQUEST_TEMPLATE.md`로 둡니다. 내용은 다음과 같습니다.

```markdown
## 문제와 결과
<!-- 어떤 상황에서 무엇이 필요했고, 변경 후 어떻게 동작하는가 -->

Closes #

## 수용 조건
<!-- 이슈의 수용 조건을 복사해 와서 체크 -->
- [ ]

## 검증
<!-- 실행한 검사와 결과. UI 변경은 모바일(360px) · PC 화면 첨부 -->

## 셀프 리뷰
- [ ] 로딩 · 빈 상태 · 에러 상태가 모두 있다 (화면 변경 시)
- [ ] 권한 검사는 서버에 있다 (삭제 · 수정 · 상태 변경 시)
- [ ] 키보드만으로 이 기능을 끝까지 쓸 수 있다 (화면 변경 시)
- [ ] 문서(docs/)가 코드와 어긋나지 않는다
- [ ] 커밋이 역할별로 나뉘어 있다

## 호환성
<!-- 저장 키 · URL · API 응답 모양 · 환경 변수가 바뀌면 적는다. 없으면 "없음" -->
```

### 브랜치 보호 규칙

GitHub → Settings → Branches에서 `main`과 `dev`에 같은 규칙을 겁니다. 설정값을 그대로 적어 두어 재현할 수 있게 합니다.

| 설정 | 값 | 이유 |
| --- | --- | --- |
| Require a pull request before merging | 켬 | 직접 push 차단 |
| Required approvals | 0 | 승인자가 없다. 위 보완 장치로 대신 |
| Require status checks to pass | 켬 — `lint` · `typecheck` · `test` | 코드 단계에서 워크플로 이름 확정 후 지정 |
| Require branches to be up to date | 켬 | 오래된 `dev` 기준으로 병합하지 않는다 |
| Require linear history | 켬 | 병합 커밋 없이 한 줄 이력 — 리베이스 병합만 허용 |
| Allow force pushes · deletions | 끔 | — |

저장소 설정 → General → Pull Requests에서는 **Allow rebase merging만 켜고** merge commit · squash는 끕니다. "Automatically delete head branches"를 켭니다.

### 라벨

커밋 종류 · 범위와 같은 낱말을 씁니다. 이슈와 PR에 둘 다 붙입니다.

| 묶음 | 라벨 |
| --- | --- |
| 종류 | `feat` `fix` `style` `refactor` `docs` `test` `ci` |
| 범위 | `web` `server` `infra` |
| 상태 | `blocked` (다른 이슈를 기다림) · `question` (결정 필요) |

### 배포

| 환경 | 트리거 | 프론트 | 백엔드 | DB |
| --- | --- | --- | --- | --- |
| PR 미리보기 | 작업 브랜치 push | Vercel Preview (PR마다 URL) | — (Staging API를 바라봄) | Staging |
| Staging | `dev` 병합 | Vercel Preview (dev 고정 URL) | Railway staging 서비스 | Railway Postgres (staging) |
| Production | `main` 병합 | Vercel Production | Railway production 서비스 | Railway Postgres (production) |

- 환경 변수는 각 플랫폼의 환경 변수 화면에서 관리하고, 저장소에는 `.env.example`만 둡니다. 전체 목록과 검증 규칙은 [백엔드 11 구성과 시드](architecture/backend.md#11--구성과-시드).
- DB 마이그레이션은 배포 파이프라인에서 `prisma migrate deploy`로 자동 적용합니다. 수동 적용은 하지 않습니다.
- 샘플 데이터는 `SEED_SAMPLE=1`인 환경에만 넣습니다. Production은 데모 계정 둘과 데모 상품 6개가 기본이고, Staging이 생기기 전에는 양이 많을 때의 화면을 보려고 한시로 켭니다 ([시드 데이터](architecture/backend.md#4-시드-데이터)).

### 문서 단계에서의 적용

**명세 단계에서는 `dev`를 아직 두지 않습니다.** `dev`의 역할은 staging 배포인데 배포할 코드가 없기 때문입니다. 지금은 이렇게 갑니다.

| 지금 (명세) | 코드 첫 커밋부터 |
| --- | --- |
| `docs/짧은-이름` 브랜치에 역할별 커밋 → `main`에 fast-forward 병합 (리베이스 병합과 같은 결과) | 위 흐름 그대로 — `dev`를 만들고 PR 대상으로 |
| 브랜치 보호 규칙 없음 | `main` · `dev`에 보호 규칙, CI 필수 검사 |

초기 문서 몇 개는 브랜치 없이 `main`에 직접 커밋했습니다 — 이 규칙을 정하기 전의 일이라 이력에 그대로 둡니다. 2026-11-10 명세 전체 검토(`docs/review-principles`)부터 브랜치를 거칩니다.

## 구현 순서 · 뒤 단계가 앞 단계 위에 서게

**기능 문서의 수용 조건을 여섯 단계로 묶고, 단계마다 "두 계정으로 여기까지 써 볼 수 있다"를 끝 조건으로 둡니다.** 단계 안에서는 기능 하나 = 이슈 하나 = 브랜치 하나이고, PR은 백엔드(스키마 · API · 테스트) → 프론트엔드(화면 · 테스트) 순서의 역할별 커밋으로 채웁니다.

| 단계 | 만드는 것 | 수용 조건 | 끝 조건 | 먼저 끝나 있어야 하는 것 |
| --- | --- | --- | --- | --- |
| 0 뼈대 | workspaces · `shared-schema` · 두 앱 초기화 · 환경 변수 검증 · 프록시 · 에러 형식 · 요청 ID · CI(lint · typecheck · test) · Docker Compose · 첫 마이그레이션 · Staging 배포 | AC-CM 중 인증 밖의 것 | 빈 홈 화면과 `/healthz`가 Staging에서 뜨고, 프록시를 지난 요청 ID가 백엔드 로그에 찍힌다 | — (스파이크 완료. 쿠키 `SameSite` · CSRF의 브라우저 확인을 이 단계 첫 PR에서) |
| 1 인증 | 가입 · 로그인 · 로그아웃 · 세션 연장 · 보호 경로 · rate limit · 데모 계정 시드 | AC-SU · AC-LI · AC-CM 인증 | 가입 → 로그아웃 → 로그인, 다른 기기 무효화 | 0 |
| 2 상품 | 업로드 · 등록 · 수정 · 목록 · 검색 · 상세 · 상태 변경 · 삭제 | AC-PC · AC-PL · AC-PD(채팅 제외) · AC-PX | 판매자가 올린 물건을 구매자가 목록에서 찾아 상세까지 | 1 |
| 3 채팅 | 방 생성 · 소켓 연결 · 전송 · 복구 · 읽음 · 채팅 목록 | AC-PD 채팅 · AC-CH · AC-CL | 두 브라우저로 대화, 한쪽 네트워크를 끊었다 붙여도 빠짐 · 중복 없음 | 2 |
| 4 마이 · 알림 | 마이페이지 · 구매자 지정 · 구매 내역 · 프로필 · 비밀번호 · 배지 · 토스트 | AC-MP · AC-NT · AC-PD 구매자 지정 | [개요 2.1](overview.md#21-사용자와-핵심-시나리오)의 두 시나리오가 끝까지 | 3 |
| 5 마무리 | 정리 배치 · 데모 초기화 · E2E 2개 + 끊김 1개 · axe · 성능 측정 · Production 배포 | 남은 AC · [품질 기준](overview.md#7-품질-기준) | 테스트 없는 AC 0개, Web Vitals · p95 목표 충족 | 4 |

| 규칙 | 이유 |
| --- | --- |
| 단계가 끝나면 두 계정으로 처음부터 직접 써 보고(워크스루), 어긋난 곳은 다음 단계 전에 고친다 | 뒤 단계가 앞 단계의 결함 위에 쌓이지 않게 |
| 구현하다 명세와 다르게 해야 하면 같은 PR에서 명세를 고치고 이유를 결정 기록 · 트러블슈팅에 남긴다 | 문서가 코드보다 낡지 않게 |
| [구현하며 확인할 것](troubleshooting.md#구현하며-확인할-것)의 항목은 해당 단계 첫 PR에서 실측한다 | 미뤄 둔 불확실성을 가장 먼저 없앤다 |
| 단계 0에서 화면 하나(홈)와 API 하나(`/healthz`)를 배포까지 먼저 잇는다 | 배포 경로의 문제(T-02 · T-04 · T-08)는 기능이 쌓이기 전에 드러나야 싸다 |

## 테스트 전략 · 수용 조건 하나에 테스트 하나

**수용 조건 251개를 기준으로 구현 단계의 검증 범위와 도구를 정했습니다.** 각 조건은 해당 규칙을 담당하는 계층에서 검증하고, 프론트엔드는 화면 반응·접근성, E2E는 판매자·구매자의 거래 흐름을 확인합니다. 단위 · 통합 · 소켓 · 컴포넌트 테스트와 E2E 13개는 CI에서 돌고, 접근성 자동 검사 · 끊김 시나리오 · PC 폭 E2E는 아직 없습니다.

### 1. 층과 도구

| 층 | 도구 | 무엇을 | 무엇을 하지 않나 | 대략의 수 |
| --- | --- | --- | --- | --- |
| 공유 스키마 단위 | Vitest | 정규화 함수(`normalizeEmail` · `normalizeText`) · grapheme 길이 · Zod 스키마 경계값 | 화면 · DB | 입력 경우의 수(`*-IN-*`) 대부분 |
| 백엔드 통합 | Vitest + supertest + 실제 PostgreSQL | API 하나를 HTTP로 불러 응답 · DB 상태 · 발행된 실시간 이벤트를 함께 확인. 권한 · 트랜잭션 · 제약 · 멱등성 | 목(mock) DB — 제약과 잠금은 진짜 DB에서만 드러난다 | AC의 절반 이상 |
| 백엔드 동시성 | 같은 도구 + `Promise.all`로 요청 동시 발사 | 유니크 경합 · 조건부 UPDATE · `seq` 순서 · `FOR SHARE` | — | 경합 경우의 수(`*-CC-*`)마다 |
| 소켓 | Vitest + `socket.io-client` 2~3개 | 조인 · 전송 · 복구 · 만료 · 페이로드 한도 | — | [B09 7절](architecture/backend.md#7-테스트) |
| 프론트 컴포넌트 | Vitest + Testing Library | 상태별 화면(로딩 · 빈 · 에러 · 권한), 폼 정규화 · 오류 연결, 포커스 이동, 소켓 상태 기계(가짜 소켓) | 스타일 · 픽셀 | 화면 상태 · 접근성 AC |
| E2E | Playwright (모바일 Pixel 7 · 배치 검사는 360px과 1280px) | 흐름 3개(가입 → 등록 → 채팅 → 예약 → 거래완료, 수정 · 삭제 뒤 열람 전용 방, 프로필 · 비밀번호 변경, 판매자 프로필, 관심)를 판매자 · 구매자 두 브라우저 컨텍스트로 끝까지. 배치 3개(버튼 글자 꺾임과 이름 · 글자 일치, [물건 올리기] 위치, 없는 파일 요청) | 경우의 수 전수 — 느리고 깨지기 쉽다. 네트워크 끊기(`setOffline`)는 아직 없다 | 흐름 5 + 배치 3 + 공통 조건 5 |
| 접근성 자동 (계획) | `@axe-core/playwright` | E2E가 지나는 모든 화면에서 위반 0 | 키보드 흐름 — 그건 E2E 시나리오에 직접 | 화면 수만큼 |

### 2. 이름 규칙 — 문서와 테스트를 잇는 줄

```ts
// 테스트 이름 = AC 번호 + 수용 조건 문장
it('AC-PD-13 같은 구매자가 같은 상품에 채팅하기를 두 번 눌러도 방은 하나다', async () => { ... });
```

- CI가 `01-requirements.md`의 AC 번호 목록과 테스트 이름의 AC 번호를 비교해 **테스트가 없는 AC를 출력**한다. 0이 될 때까지 기능은 끝나지 않는다.
- 트러블슈팅 기록의 결함마다 회귀 테스트를 둔다 — 이름은 `T-01 …`. 한 번 찾은 결함이 다시 들어오는 것을 막는다.

### 3. 백엔드 통합 테스트의 기준

| 기준 | 이유 |
| --- | --- |
| DB는 진짜 PostgreSQL 16 (Docker), 테스트 파일마다 스키마를 비우고 마이그레이션 | 유니크 · CHECK · `FOR SHARE` · `now()`의 의미는 SQLite나 목에서 다르다. T-01은 진짜 DB에서만 재현된다 |
| 응답을 공유 스키마로 `parse` | 문서(API 명세)와 다른 키 · `null` 대신 생략 · 해시 노출을 잡는다 |
| 실시간 이벤트는 가짜 `Realtime` 구현으로 기록 | 서비스가 커밋 **후에** 알렸는지까지 확인 ([B09 5절](architecture/backend.md#5-http-서비스에서-소켓으로-알리기)) |
| 삭제된 상품 누수 검사 | 삭제 상품 하나를 만든 뒤 모든 목록 · 개수 API를 돌려 새지 않는지 — Prisma 자동 주입의 빈틈을 결과로 잡는다 |
| 시각은 주입 | 토큰 만료 · 30일 정리 배치는 시계를 바꿔 끼워 검증. `setTimeout`으로 기다리지 않는다 |

### 4. CI 필수 검사

| 검사 | 실패하면 |
| --- | --- |
| `lint` (ESLint · `socket.emit(` 직접 호출 금지 등 규칙 포함) | 병합 불가 |
| `typecheck` (`tsc --noEmit`, `strict`) | 병합 불가 |
| `test` (단위 · 통합 · 소켓 · 컴포넌트) | 병합 불가 |
| `e2e` (모든 PR. 실패하면 화면 기록과 스크린샷을 `e2e-report`로 올린다) | 병합 불가 |
| AC 대응표 (`scripts/check-ac.py`) | 실패는 아니고 작업 로그에 "번호를 단 테스트가 없는 AC" 목록. 지금 269개 중 263개 — 남은 6개는 스크롤 위치 · 포커스 유지 · 소켓 이벤트 목록처럼 브라우저 안의 움직임이나 구조에 관한 것과 lint로 강제하는 것이다 |
| 문서 링크 검사 | 경로·앵커 오류 수정 후 병합 |

E2E는 로컬에서 `npm run e2e -w frontend-next`로 돕니다. 마이그레이션이 적용된 빈 DB(`E2E_DATABASE_URL`, 기본 `neighbo_e2e`)가 필요하고, 백엔드(4100)와 운영 빌드의 프론트엔드(3100)는 실행기가 직접 띄웁니다. 설치된 Chrome을 쓰려면 `PW_CHANNEL=chrome`을 붙입니다. 테스트마다 새 계정을 만들어 앞선 실행의 데이터와 섞이지 않습니다.

### 5. 흔들리는 테스트

흔들리는 테스트는 `skip`하지 않고 원인을 찾아 [트러블슈팅](troubleshooting.md)에 남깁니다. 대부분 시간(실제 대기) · 순서(병렬 테스트가 같은 행) · 네트워크(외부 호출) 중 하나이며, 각각 시계 주입 · 테스트마다 다른 데이터 · 외부 호출 금지로 막습니다.

### 6. 하지 않는 것

| 하지 않는 것 | 이유 |
| --- | --- |
| 커버리지 % 목표 | 숫자는 AC 대응표로 대신한다. 커버리지는 "어디를 안 돌렸나"를 볼 때만 쓴다 |
| 스냅샷 테스트 | 무엇이 맞는지 말하지 않고 "달라졌다"만 말한다 |
| 프론트에서 서버 규칙 재검증 | 권한 · 상태 전이는 백엔드 테스트가 맡는다. 프론트는 그 거절을 어떻게 보여주는지만 |

## AI 작업·검증 기록

**문서 초안과 실험 코드는 AI 도구와 함께 작성하고, 실행 결과·스키마·공식 문서 대조로 내용을 검토합니다.** 서비스 범위와 설계 판단은 검토 항목으로 남기며, 실행하지 않은 내용은 계획으로 구분합니다. 기존 Claude 기여 기록은 커밋의 `Co-Authored-By:`에서 확인할 수 있습니다.

### 1. 나눈 역할

| 사람이 | AI가 |
| --- | --- |
| 무엇을 만들지 · 어디까지 만들지 (범위, 우선순위) | 경우의 수 · 수용 조건 · 설계 문서 초안 |
| 초안의 누락 상황과 범위 검토 | 검토 결과에 따른 시나리오·문서 보완 |
| AI가 혼자 내린 판단을 확인하거나 뒤집기 → [검토 요청](decisions.md#검토-요청) | 확인받지 못한 판단을 숨기지 않고 검토 요청에 적기 |
| 폴더 이름 · 라이선스 · 문서 원칙 같은 저장소 규칙 | 규칙을 모든 문서에 일관되게 반영 |

### 2. 검증 방법

| 장치 | 막는 것 | 실제로 잡은 것 |
| --- | --- | --- |
| 스파이크 실행 | "라이브러리가 이렇게 동작할 것"이라는 추측 | 실험이 재시작이 아니라 의도된 종료를 흉내 냄 (S-03), 유령 전송 (S-04) |
| 스키마 검증기 | 버전이 지난 문법 | Prisma 7의 `url` 제거 (S-05) |
| 링크 검사 스크립트 | 문서끼리 가리키는 곳이 사라짐 | 제목을 바꾸며 깨진 앵커 |
| 렌즈별 명세 검토 | 단일 요청에선 맞는 설계 | 트러블슈팅 T-01 ~ T-11 |
| 공식 문서 대조 | 현재 버전과 다른 API 설명 | Next.js 16 `proxy.ts` (T-07) |

### 3. 규칙

- **수치와 버전은 출처를 적는다.** "4.5MB" 같은 값은 어디서 왔는지(플랫폼 한도)를 같은 문장에 둔다.
- **스파이크 결과는 관찰만 적는다.** 실행 결과에 없는 결론은 "검증하지 못한 것"으로 따로 적는다 ([WebSocket 기술 노트](tech-notes.md#websocket과-socketio)).
- **AI가 고른 답은 검토 요청에 남긴다.** 각 행에 고른 답 · 이유 · 다른 선택지를 적어 사람이 번호로 뒤집을 수 있게 한다.
- **구현 단계의 검토 결과를 PR에 남긴다.** 변경 내용과 검증 범위를 확인하고, 아직 검증하지 않은 항목을 구분한다.
