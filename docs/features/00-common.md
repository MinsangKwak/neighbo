# 00 · 공통 — 모든 기능에 걸치는 요구사항과 경우의 수

[문서 목차](../README.md) · 다음: [01 · 회원가입](01-signup.md) · 설계: [흐름](../architecture/flow.md) · [프론트엔드](../architecture/frontend.md) · [백엔드](../architecture/backend.md)

**모든 기능 문서가 따르는 표기와, 열 가지 기능에 공통으로 적용되는 요구사항 · 경우의 수를 모았습니다.** 기능 문서(01~10)는 각 기능의 요구사항과 경우의 수를 한 장에 담고, 여기 있는 공통 규칙은 반복하지 않고 ID로 참조합니다. 각 기능은 유저 스토리, 권한, 수용 조건 순서로 구성했습니다. 수용 조건에는 [경우의 수](#경우의-수-표기)의 ID를 연결했으며, 구현과 테스트는 이 조건을 기준으로 진행합니다.

표기: **AC-기능-번호** = 수용 조건. 근거 열 = [경우의 수](#경우의-수-표기) ID · 결정 기록. 소켓 동작은 [WebSocket 기술 노트](../tech-notes.md#websocket과-socketio) 스파이크로 확인한 뒤 확정했습니다.

**역할 열** — 같은 수용 조건을 두 역할이 각자 어떻게 맡는지 적습니다. 원칙은 하나입니다: **규칙은 백엔드가 강제하고, 프론트는 그 규칙을 사용자가 어기기 전에 알려 줍니다.** 프론트가 버튼을 숨겨도 백엔드는 같은 판단을 다시 하고, 백엔드가 거절해도 프론트는 사용자가 무엇을 할 수 있는지 보여줍니다. `—`는 그 역할이 할 일이 없다는 뜻입니다.

## 경우의 수 표기

**각 기능 문서의 "경우의 수" 절은 상황과 기대 동작을 정리한 검토 자료입니다.** 입력, 권한, 상태, 동시성, 네트워크, 접근성, 데이터 경계를 나누어 작성했습니다. 최종 수용 조건은 [요구사항](00-common.md)에 있으며, 각 조건에서 이 표의 ID를 참조합니다.

### 표기

| 열 | 뜻 |
| --- | --- |
| ID | `기능약어-분류-번호`. 예 `SU-IN-03` = 회원가입 · 입력 · 3번. 요구사항과 테스트 이름에서 이 ID를 참조한다 |
| 상황 | 사용자가 무엇을 했고 시스템이 어떤 상태인가. 한 행에 한 상황 |
| 기대 동작 (제안) | 화면에 무엇이 보이고, 서버는 무엇을 하고, 데이터는 어떻게 바뀌는가 |
| 결정 | `—` 제안대로 가도 됨 · `❓` 검토자가 정해야 함 · `⛔` 1차 범위 밖으로 보내자는 제안 |

분류 약어:

| 약어 | 분류 | 묻는 질문 |
| --- | --- | --- |
| `OK` | 정상 | 의도대로 썼을 때 무엇이 보이는가 |
| `IN` | 입력 · 검증 | 비었거나 · 길거나 · 형식이 틀리거나 · 경계값일 때 |
| `AU` | 권한 · 인증 | 로그인 안 했거나 · 남의 것이거나 · 세션이 만료됐을 때 |
| `ST` | 상태 | 대상이 삭제 · 예약 · 완료 · 차단 상태일 때 |
| `CC` | 동시성 | 두 번 눌렀거나 · 두 탭이거나 · 상대와 동시에 바꿨을 때 |
| `NW` | 네트워크 · 실패 | 느리거나 · 끊겼거나 · 서버가 500을 냈을 때 |
| `A11Y` | 접근성 | 키보드 · 스크린리더 · 확대 · 고대비에서 |
| `UI` | 화면 · 반응형 | 360px · 1024px · 긴 글 · 빈 목록에서 |
| `DT` | 데이터 경계 | 0개 · 1개 · 1,000개 · 아주 긴 값 · 특수문자 · 이모지 |
| `SEC` | 보안 | 조작된 요청 · 스크립트 삽입 · 반복 요청 |

### 작성 규칙

- **한 행에 한 상황.** "비었거나 너무 길 때"는 두 행이다.
- **기대 동작은 세 겹으로.** 화면(사용자가 보는 것) · 서버(응답 코드와 처리) · 데이터(무엇이 바뀌는가). 셋 중 해당 없는 것은 생략한다.
- **"적절히 처리한다"는 금지.** 어떤 문구가 어디에 뜨는지, 포커스가 어디로 가는지까지 적는다.
- **범위 밖이면 `⛔`로 적고 지우지 않는다.** 왜 1차에서 빼는지가 남아야 2차에서 다시 꺼낼 수 있다.
- 공통 파일에 있는 상황은 기능 파일에서 반복하지 않고 `→ CM-NW-01`처럼 참조한다.

### 검토 순서

1. 공통 → 회원가입 → 로그인 순으로 읽는다. 뒤 기능이 앞 기능의 결정을 전제한다.
2. `❓` 행마다 결정을 적는다. 결정은 표의 "기대 동작" 열을 고치고 `❓`를 `—`로 바꾼다. 구조를 가르는 결정(개요 2.4 매트릭스에서 열이 셋 이상)은 [결정 기록](../decisions.md)에 한 장을 쓰고 표에서 링크한다.
3. 모든 `❓`가 사라지면 수용 조건을 쓴다. 소켓 동작 관련 12개 항목은 [WebSocket 기술 노트](../tech-notes.md#websocket과-socketio)의 스파이크 결과를 반영했다. 수용 조건은 이 표를 유저 스토리와 조건으로 압축한 것이고, 조건마다 경우의 수 ID를 단다.
