# 문서 목차

**서비스 범위와 수용 조건은 공통 문서에, 처리 방식은 프론트엔드·백엔드 설계 문서에 정리했습니다.** 개요 → 경우의 수 → 요구사항 순서로 읽은 뒤 필요한 역할별 문서로 이동할 수 있습니다.

## 공통

| 순서 | 문서 | 답하는 질문 | 상태 |
| --- | --- | --- | --- |
| 00 | [개요](00-overview.md) | 목표·범위·엔티티·업무 흐름·변경 영향 | 작성 |
| 00+ | [경우의 수](cases/README.md) | 기능마다 일어날 수 있는 모든 상황과 그때의 동작 (01의 입력) | 작성 — 결정 필요 0건 |
| 01 | [요구사항](01-requirements.md) | 각 기능은 누가 · 언제 · 어떤 조건에서 어떻게 동작하는가 — 수용 조건 251개, 조건마다 프론트 · 백엔드 역할 | 작성 |
| — | [트러블슈팅 기록](troubleshooting.md) | 무엇이 깨졌고, 왜 깨졌고, 어떻게 찾았나 — 명세 결함 10 · 스파이크 5 | 작성 |
| — | [설계·검증 현황](capabilities.md) | 항목별 설계 내용과 검증 범위, 서비스 구현 예정 항목 | 작성 |

## 역할별 설계

| 역할 | 문서 | 답하는 질문 | 상태 |
| --- | --- | --- | --- |
| 백엔드 | [백엔드 설계](backend/README.md) — 요청 계층 · **데이터 모델** · 트랜잭션 · 권한 · 멱등성 · 에러 코드 · 보호 장치 · 로그 · 소켓 서버 · API 명세 | 프론트가 무엇을 보내든 규칙이 깨지지 않으려면 | 작성 (10) |
| 프론트엔드 | [프론트엔드 설계](frontend/README.md) — 렌더링 · 상태 · 캐시 · 에러 · 폼 · 포커스 · 소켓 클라이언트 | 서버의 규칙을 사용자가 이해할 수 있는 화면으로 바꾸려면 | 작성 (7) |
| 백엔드 | [API 명세](backend/10-api.md) | 서버와 어떤 모양으로 주고받는가 — HTTP 25 · 소켓 9 | 작성 |
| 프론트엔드 | 화면 명세 · 컴포넌트 | 화면마다 무엇이 보이고, 반복되는 조각은 무엇인가 | 예정 |

데이터 모델·API는 백엔드 문서에, 화면·컴포넌트는 프론트엔드 문서에 배치합니다 ([개요 5절](00-overview.md#5-폴더-구조)).

## 문서 간 연결

요구사항의 수용 조건은 경우의 수 ID와 연결됩니다. 역할별 설계는 해당 조건의 처리 방식을, API 명세는 요청·응답 형식을 정의합니다. 구조가 변경되면 관련 문서와 링크를 같은 변경에 반영합니다.
